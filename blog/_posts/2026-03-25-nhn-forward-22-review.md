2022년 11월, 삼성역에서 열린 NHN Forward 22에 참여했다. 그중 인상 깊었던 두 세션 —
NHN Dooray의 "안정적인 백엔드" 세션과 NHN Commerce의 "Elasticsearch 기반 검색엔진"
세션 — 에서 배운 내용을 사내 세미나로 공유했었는데, 그때 정리한 내용을 다시 옮겨본다.
두 세션 모두 "실제 서비스가 커지면서 마주친 문제를 어떻게 풀었는가"라는 공통된
축을 갖고 있어서, 듣고 나서도 오래 남았다.

## 세션 1: Dooray가 겪은 두 종류의 장애 — 메모리와 연쇄 실패

Dooray 팀은 사용자가 늘면서 겪은 장애 원인을 크게 두 갈래로 나눠 설명했다.

### 메모리 오류: GC가 못 따라가는 상황

JVM의 Garbage Collector는 Stack에서 도달 불가능한(Unreachable) Heap 객체를 회수해서
메모리를 확보한다. 이 회수가 정상적으로 따라가지 못하는 상황이 메모리 오류다.
Dooray는 이 문제를 사후 대응(장애 발생 → 전파 → 관제팀 모니터링 → 로그 확인 →
덤프 → 재기동)만으로는 한계가 있다고 보고, 예방적 장치를 추가했다.

- 1분 주기 크론탭으로 프로세스 상태를 확인하고, 이상 시 서버를 재실행.
- JVM 실행 옵션에 `OutOfMemoryError` 발생 시 프로세스를 즉시 kill하는 옵션을 추가해서,
  좀비 상태로 응답만 느려지는 것보다 빠르게 재시작되도록 유도.

이 접근이 흥미로운 이유는, "메모리 누수를 완전히 막는다"가 아니라 "메모리 문제가
생겼을 때 빠르게 감지하고 죽였다가 다시 살리는 쪽"을 택했다는 점이다. 근본 원인
제거보다 장애 지속 시간을 최소화하는 쪽에 무게를 둔 실용적 트레이드오프다.

### 연쇄 실패(Cascading Failure)와 HTTP 429

두 번째 축은 하나의 서비스 문제가 다른 서비스로 번지는 연쇄 실패다. 어떤 서비스가
응답하지 않을 때 재시도를 반복하면 대기 시간이 늘고, 그 부하가 다시 다른 서비스로
전파되는 구조다. Dooray는 이걸 막기 위해 "모든 문제를 가시화"하는 데 집중했다고
한다 — Spring Boot Actuator로 메트릭을 수집하고 그라파나로 시각화하는 조합이다.

특히 인상적이었던 건 HTTP 429(Too Many Requests)를 다루는 방식이다.

- 429는 **에러 응답이 아니라는 점**을 먼저 짚었다 — 클라이언트에게 "지금은 안 되니
  나중에 다시 시도하라"는 정상적인 제어 신호로 취급한다는 뜻이다.
- Actuator의 `MetricsEndpoint`로 Active Thread 수를 실시간으로 측정하고, 기준점
  (세션에서는 85로 소개)을 넘으면 `TooManyRequestException`을 던져 요청을 걷어낸다.

이 방식은 결국 Circuit Breaker 패턴과 같은 목적(장애 전파 차단)을 메트릭 기반의
임계값 체크로 직접 구현한 셈이다. Resilience4j 같은 라이브러리 없이도, Actuator +
그라파나 조합만으로 같은 문제를 풀 수 있다는 걸 보여준 사례였다.

## 세션 2: NHN Commerce의 Elasticsearch 검색엔진

두 번째 세션은 NHN Commerce(SHOP BY)에서 왜, 어떻게 Elasticsearch를 도입했는지에
대한 이야기였다.

### ELK에서 Beats로 — Logstash를 걷어낸 이유

ELK(Elasticsearch, Logstash, Kibana)에 데이터 수집기 Beats를 더해 Elastic Stack으로
운영 중이라고 소개했다. 흥미로운 건 Logstash를 실제로는 쓰지 않는다는 점이었다.
Logstash는 실시간 파이프라인 기반의 데이터 수집·변환 엔진이라 기능이 많은 만큼
오버헤드도 크고, NHN Commerce는 Beats만으로 가공·필터링을 끝낼 수 있어서
Logstash 없이 경량 구성으로 운영한다고 한다. "기능이 많은 도구를 항상 쓰는 게
아니라, 필요한 만큼만 쓴다"는 선택이 드러나는 부분이었다.

### 전체색인/부분색인 — 정합성을 스케줄러 두 개로 푼다

상품 데이터는 MySQL에 저장되고, 이걸 Elasticsearch로 밀어넣는 색인 작업이 필요하다.
정합성을 맞추기 위해 두 가지 스케줄러를 병행한다.

- **전체색인**: 매일 새벽, 모든 상품 데이터를 CSV로 뽑아 통째로 재색인. 이때
  Elasticsearch의 alias를 이용해 백업용 인덱스를 별도로 보관한다.
- **부분색인**: Spring 스케줄러로 10초 주기로 변경된 상품만 반영.

이 둘을 병행할 때 핵심 문제는 "전체색인이 도는 동안 부분색인이 겹치면 중복 색인이
발생한다"는 것인데, 전체색인 쪽에서 부분색인 진행 여부를 판단해서 충돌을 피하는
방식으로 풀었다고 한다. alias로 백업 인덱스를 유지하는 것도 전체색인이 실패했을 때
바로 이전 인덱스로 되돌릴 수 있게 하는 안전장치로 읽힌다.

### 검색 품질: 사용자 사전과 동의어 사전

형태소 분석기가 의도와 다르게 단어를 쪼개는 문제(예: "운동화"가 "운동"+"화"로
분리되는 경우)를 사용자 정의 사전으로 막고, 동의어 사전으로 검색 재현율을
높인다. 두 사전 모두 서버에 자동 배포하는 파이프라인을 구축해서, 사전이 바뀔
때마다 수동 배포하지 않도록 했다는 점도 언급됐다.

### 쿼리 성능

- `match`와 `term` 쿼리를 상황에 맞게 같이 사용 (전문 검색 vs 정확한 값 매칭).
- 상품 카테고리처럼 자주 함께 조회되는 정보를 하나의 필드로 모아 저장해서 조인성
  조회를 줄임.
- Nginx 캐시를 앞단에 둬서 반복 요청의 부하를 줄임.

## 두 세션을 관통하는 것

돌아보면 두 세션 모두 "문제를 완전히 없앤다"가 아니라 **감지하고, 격리하고, 빠르게
복구하는 쪽**에 무게를 뒀다는 공통점이 있었다. Dooray는 메모리 누수 자체를 잡기보다
OOM 시 프로세스를 죽이고 재기동하는 쪽을, 연쇄 실패는 막기보다 429로 빠르게 걷어내는
쪽을 택했다. NHN Commerce도 색인 정합성을 완벽한 트랜잭션으로 보장하기보다 전체/부분
색인 이중화와 alias 백업으로 문제가 생겨도 되돌릴 수 있는 구조를 택했다. 다른
회사가 실제 트래픽 앞에서 내린 선택을 들어볼 기회가 흔치 않은데, "이상적인 해법"보다
"운영 가능한 해법"을 고르는 감각을 배운 자리였다.
