# JPA 엔티티와 값 객체(Value Object) - 무엇이 다르고, 언제 무엇을 사용할까?

JPA로 도메인 모델을 설계할 때, 우리는 모든 것을 엔티티로 만들고 싶은 유혹에 빠지기 쉽습니다. 하지만 객체 지향의 원칙과 데이터베이스 설계의 효율성을 고려하면, 값 객체(Value Object)의 중요성을 이해하고 적절히 활용하는 것이 훨씬 중요합니다.

이번 글에서는 엔티티와 값 객체의 명확한 구분 기준, 그리고 값 객체를 JPA에서 어떻게 활용하는지 구체적인 예시와 함께 살펴보겠습니다.

* * *

## 핵심 판단 기준 — "독립적인 생명주기가 있는가?"

설계할 때 가장 먼저 던져야 할 질문은 이것입니다.

> **이 객체를 독립적으로 조회하거나 수정할 일이 있는가?**
    
    
    독립적으로 조회/수정할 일이 있나?
            ↙               ↘
           YES               NO
            ↓                 ↓
       @Entity            @Embeddable
      (ManyToOne)      (ElementCollection)

예를 들어 **주문상품(OrderItem)** 은 취소, 수정, 직접 조회가 필요하고 다른 엔티티(Item)도 참조합니다. 반면 **주소(Address)** 는 Member에 종속된 단순 값이며, 그 자체를 독립적으로 다룰 일이 없습니다. 이 차이가 엔티티와 값 객체를 나누는 핵심입니다.

* * *

## 값 객체를 사용하는 이유 (장점)

일반적으로 사용하는 엔티티는 고유 식별자(Id)를 기준으로 동일 여부를 판단합니다. 하지만 '주소'와 같이 변하지 않는 객체들은 값 객체로서 활용하기 좋습니다.

값 객체는 **변경 불가능(Immutable)** 하게 설계하는 것이 일반적입니다. 한 번 생성되면 내부 상태를 변경할 수 없으므로, 예상치 못한 부작용을 줄이고 코드의 안정성을 높입니다.

JPA에서는 @Embedded와 @ElementCollection을 통해 값 객체를 효과적으로 매핑할 수 있습니다. 이는 복잡한 엔티티 관계를 줄여줍니다.

java
    
    
    // Address.java (값 객체 - @Embeddable)
    @Embeddable
    public class Address {
        private String city;
        private String street;
        private String zipcode;
    
        protected Address() {}
    
        public Address(String city, String street, String zipcode) {
            if (city == null || city.isEmpty()) {
                throw new IllegalArgumentException("City cannot be empty.");
            }
            this.city = city;
            this.street = street;
            this.zipcode = zipcode;
        }
    
        public String getCity() { return city; }
        public String getStreet() { return street; }
        public String getZipcode() { return zipcode; }
    
        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (o == null || getClass() != o.getClass()) return false;
            Address address = (Address) o;
            return Objects.equals(city, address.city) &&
                   Objects.equals(street, address.street) &&
                   Objects.equals(zipcode, address.zipcode);
        }
    
        @Override
        public int hashCode() {
            return Objects.hash(city, street, zipcode);
        }
    }
    
    // Member.java
    @Entity
    public class Member {
        @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
        private String name;
    
        @Embedded
        private Address homeAddress; // Member 테이블에 city, street, zipcode 컬럼이 추가됨
    
        protected Member() {}
        public Member(String name, Address homeAddress) {
            this.name = name;
            this.homeAddress = homeAddress;
        }
    
        public Long getId() { return id; }
        public String getName() { return name; }
        public Address getHomeAddress() { return homeAddress; }
    
        // 값 객체는 불변이므로, 주소를 변경하려면 새로운 Address 객체로 교체
        public void setHomeAddress(Address homeAddress) {
            this.homeAddress = homeAddress;
        }
    }

> **참고:** Set, Map 같은 컬렉션에서 값 객체를 올바르게 비교하려면 equals()와 hashCode()를 반드시 오버라이딩해야 합니다.

## @Embedded vs @ElementCollection

@Embedded가 단일 값 객체를 **같은 테이블의 컬럼** 으로 저장한다면, @ElementCollection은 값 객체의 **컬렉션을 별도 테이블** 로 관리합니다.

java
    
    
    // ProductImage.java (값 객체 - @Embeddable)
    @Embeddable
    public class ProductImage {
        private String url;
        private String caption;
    
        protected ProductImage() {}
        public ProductImage(String url, String caption) {
            this.url = url;
            this.caption = caption;
        }
    
        public String getUrl() { return url; }
        public String getCaption() { return caption; }
    
        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (o == null || getClass() != o.getClass()) return false;
            ProductImage that = (ProductImage) o;
            return Objects.equals(url, that.url) && Objects.equals(caption, that.caption);
        }
    
        @Override
        public int hashCode() {
            return Objects.hash(url, caption);
        }
    }
    
    // Product.java
    @Entity
    public class Product {
        @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
        private String name;
        private int price;
    
        @ElementCollection(fetch = FetchType.LAZY)
        @CollectionTable(name = "product_images",
                         joinColumns = @JoinColumn(name = "product_id"))
        @OrderColumn(name = "image_index") // 순서 보장용 컬럼 (선택 사항)
        private List<ProductImage> images = new ArrayList<>();
    
        protected Product() {}
        public Product(String name, int price) {
            this.name = name;
            this.price = price;
        }
    
        public void addImage(ProductImage image) { this.images.add(image); }
        public void removeImage(ProductImage image) { this.images.remove(image); }
    }

### @CollectionTable 옵션 정리

@CollectionTable은 필수는 아니며, 지정하지 않으면 기본적으로 부모엔티티명_필드명 으로 테이블 이름이 생성됩니다.

java
    
    
    @CollectionTable(
        name = "product_images",          // 별도 테이블 이름
        joinColumns = @JoinColumn(name = "product_id") // 부모 엔티티와의 조인 컬럼
    )

@OrderColumn을 선언하면 컬렉션 테이블에 순서용 인덱스 컬럼이 자동으로 추가됩니다.

## 핵심 차이점 정리

어노테이션기능 요약DB 저장 방식equals/hashCode 필요  @Embedded | 단일 값 객체를 엔티티 내부에 포함 | 부모 엔티티 테이블에 컬럼으로 추가 (별도 테이블 X) | 필요  
---|---|---|---  
@ElementCollection | 값 객체 컬렉션을 포함 (List, Set 등) | 별도 테이블 생성, 부모 PK를 FK로 가짐 | 필요

## 그렇다면 @OneToMany / @ManyToOne은 언제 쓰는가?

@ElementCollection이 적합하지 않은 경우가 있습니다. 바로 **독립적인 생명주기가 필요하거나, 다른 엔티티를 참조하거나, 자체 비즈니스 로직** 이 있는 경우입니다.

**주문상품(OrderItem)** 이 대표적인 예입니다.

java
    
    
    // OrderItem은 Embeddable로 표현할 수 없음
    @Entity
    public class OrderItem {
    
        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "order_id")
        private Order order;
    
        @ManyToOne(fetch = FetchType.LAZY)
        private Item item;        // ← 다른 엔티티 참조 → Embeddable 불가!
    
        private int orderPrice;
        private int count;
    
        // 자체 비즈니스 로직도 존재
        public void cancel() {
            item.addStock(count);
        }
    }

@Embeddable은 다른 엔티티를 참조할 수 없기 때문에, 이런 경우엔 반드시 @Entity + @ManyToOne을 사용해야 합니다.

### 실무에서의 관계 매핑 패턴

실무에서는 연관관계 매핑 방향에 대한 관례가 있습니다.

**일대다(1:N) 관계 → @ManyToOne 단방향만 사용**

java
    
    
    // Order에 굳이 이걸 넣지 않음
    @Entity
    public class Order {
        // @OneToMany(mappedBy = "order")
        // private List<OrderItem> orderItems;  ← 실무에서 보통 생략
    }
    
    // FK를 가진 쪽에서만 매핑
    @Entity
    public class OrderItem {
        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "order_id")
        private Order order;  // 이것만으로 충분
    }

@OneToMany 컬렉션을 생략하는 이유는, 필요할 때 쿼리로 가져오면 충분하기 때문입니다. 양방향 매핑은 코드 복잡도와 N+1 문제 등 성능 비용만 늘어날 수 있습니다.

**다대다(N:M) 관계 → @ManyToMany 직접 사용 금지, 중간 엔티티로 분해**

@ManyToMany는 실무에서 거의 사용하지 않습니다. 이유는 JPA가 자동 생성하는 중간 테이블에 **추가 컬럼을 넣을 수 없고** , 직접 제어도 불가능하기 때문입니다. 요구사항은 반드시 확장되기 때문에 처음부터 중간 엔티티로 설계하는 것이 관례입니다.

java
    
    
    // Order (1) ── OrderItem (중간 엔티티) ── Item (1)
    //        (N)                         (N)
    
    @Entity
    public class OrderItem {
        @ManyToOne
        private Order order;    // FK: order_id
    
        @ManyToOne
        private Item item;      // FK: item_id
    
        private int count;      // 중간 테이블에 추가 컬럼 자유롭게 가능
        private int orderPrice;
    }

### 관계 매핑 선택 요약
    
    
    다대다(N:M)  →  중간 엔티티로 분해 (ManyToOne × 2)
    일대다(1:N)  →  ManyToOne 단방향만

* * *

## 최종 정리

상황선택  단순 값, 독립 조회 불필요, 다른 엔티티 참조 없음 | @Embeddable + @Embedded 또는 @ElementCollection  
---|---  
독립 조회/수정 필요, 다른 엔티티 참조, 비즈니스 로직 존재 | @Entity + @ManyToOne  
일대다 관계 | @ManyToOne 단방향  
다대다 관계 | 중간 엔티티로 분해 후 @ManyToOne × 2  
  
> 결국 **"이 객체가 독립적인 생명주기를 가지는가"** 가 모든 선택의 출발점입니다.
