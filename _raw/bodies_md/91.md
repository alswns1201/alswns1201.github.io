### 기존 Kafka의 아키텍처 : Zookeeper 모드

## 1\. 브로커(Broker)의 핵심 역할

브로커는 단순히 메시지가 지나가는 통로가 아니라, 매우 똑똑한 **데이터 창고** 역할을 합니다.

  * **메시지 수신 및 저장:** 프로듀서(데이터를 보내는 쪽)로부터 메시지를 받아 로컬 디스크에 파일 형태로 저장합니다.
  * **메시지 전달:** 컨슈머(데이터를 읽는 쪽)가 요청하면 저장된 메시지를 꺼내서 보내줍니다.
  * **분산 처리:** 데이터를 혼자 다 갖는 게 아니라, 여러 브로커가 나누어서 가집니다. (예: 1번 데이터는 A 브로커, 2번 데이터는 B 브로커)



## 2\. 브로커를 이해하기 위한 필수 개념 3가지

브로커 안에서 데이터가 어떻게 관리되는지 알면 카프카의 80%를 이해한 것과 다름없습니다.

### ① 토픽(Topic)과 파티션(Partition)

  * **토픽:** 데이터의 종류(카테고리)입니다. 예: 결제_데이터, 로그_데이터.
  * **파티션:** 하나의 토픽을 여러 개로 쪼갠 단위입니다. 브로커가 여러 대 있을 때, 이 파티션들을 각 브로커에 골고루 분산시켜서 저장합니다. (병렬 처리의 핵심!)



### ② 복제(Replication) - 서버가 죽어도 괜찮아

실무에서 가장 중요한 개념입니다. 브로커 한 대가 고장 나도 데이터가 사라지면 안 되기 때문에, **똑같은 데이터를 다른 브로커에도 복사** 해 둡니다.

  * **Leader(리더):** 읽기/쓰기를 담당하는 대장 파티션.
  * **Follower(팔로워):** 리더를 복제하고 대기하는 쫄병 파티션.



### ③ 컨트롤러(Controller)

여러 브로커 중 한 대가 '반장' 역할을 수행합니다. 어떤 브로커가 죽었는지 감시하고, 죽었다면 그 브로커가 가졌던 리더 권한을 다른 살아있는 브로커에게 넘겨주는 관리직입니다.

## 왜 브로커를 여러 대 두나요? (실무 이유)

  1. **용량 확장:** 데이터가 너무 많아지면 서버 한 대의 하드디스크로는 부족합니다. 브로커를 늘리면 저장 공간이 무한히 늘어납니다.
  2. **부하 분산:** 접속자가 몰릴 때 여러 브로커가 나눠서 처리하면 속도가 빨라집니다.
  3. **고가용성:** 서버 점검이나 장애 상황에서도 서비스가 멈추지 않습니다.



따라서 Zookeeper는 이러한 브로커들을 관리를 하는 역할을 합니다. 

## 1\. Zookeeper의 3가지 핵심 역할

브로커가 '데이터 창고'라면, Zookeeper는 '관리 사무소'에 비유할 수 있습니다.

### ① 브로커의 상태 관리 (Heartbeat)

어떤 브로커가 현재 살아있는지, 죽었는지 실시간으로 체크합니다. 브로커가 실행되면 Zookeeper에 "나 출근했어!"라고 알리고, 연결이 끊기면 Zookeeper는 "A 브로커가 퇴근(장애)했다!"라고 다른 브로커들에게 알립니다.

### ② 컨트롤러(Controller) 선출 - 브로커 중 하나를 선정.

여러 대의 브로커 중 딱 한 대는 **'컨트롤러(반장)'** 역할을 해야 합니다. Zookeeper는 브로커들 사이에서 투표를 진행해 누가 반장이 될지 결정합니다.

### ③ 토픽 및 파티션 메타데이터 관리

  * 어떤 토픽이 생성되었는지?
  * 그 토픽의 파티션은 몇 개인지?
  * **Replica(복제본)**들이 어느 브로커에 흩어져 있는지?
  * 현재 각 파티션의 **Leader(대장)**는 누구인지? 이러한 핵심 명부를 Zookeeper가 꽉 쥐고 있습니다.



주피커 모드 vs Kraft 모드 차이는 그럼 무엇일까 ? 

### ① 실행 순서와 의존성 (Dependency)

  * **Zookeeper 모드:** 반드시 Zookeeper가 **완전히 부팅된 후** 에 Kafka 브로커를 띄워야 합니다. 안 그러면 브로커가 관리자를 못 찾아서 실행 직후 죽어버립니다. (depends_on 설정 필수)
  * **KRaft 모드:** 그냥 Kafka만 띄우면 끝입니다. 의존성 고민이 사라집니다.



### ② 메타데이터 저장 위치 (Storage)

  * **Zookeeper 모드:** 토픽 이름, 파티션 개수 같은 정보가 **Zookeeper 전용 데이터 디렉토리** 에 쌓입니다.
  * **KRaft 모드:** 모든 정보가 **Kafka의 로그 디렉토리**(@metadata라는 특수 토픽)에 함께 저장됩니다. 따라서 볼륨(Volume) 설정을 할 때 Kafka 폴더만 잘 관리하면 됩니다.



### ③ 초기화 과정 (Format)

KRaft 모드에는 Zookeeper 모드에 없는 **'클러스터 ID 생성 및 포맷'** 단계가 있습니다.

  * Docker 이미지 내부적으로 처리되긴 하지만, 처음 서버를 띄울 때 "이 브로커들은 하나의 팀이야"라고 정의하는 CLUSTER_ID를 발급받아 저장하는 과정이 추가됩니다.



주키퍼를 사용하게 되면 주키퍼서버와 카프카 서버를 순서대로 띄어서 yml를 관리해야합니다.
    
    
    services:
      zookeeper:
        image: bitnami/zookeeper:latest
        ports:
          - "2181:2181"
        environment:
          - ALLOW_ANONYMOUS_LOGIN=yes # 테스트용 보안 비활성화
    
      kafka:
        image: bitnami/kafka:latest
        ports:
          - "9092:9092"
        environment:
          # 핵심: 주키퍼 위치를 알려줘야 함
          - KAFKA_CFG_ZOOKEEPER_CONNECT=zookeeper:2181
          - ALLOW_ANONYMOUS_LOGIN=yes
        depends_on:
          - zookeeper # 주키퍼가 먼저 떠야만 실행됨

반면에 Kraft 모드를 사용하여 카프카를 띄우고 싶다면,
    
    
    services:
      kafka:
        image: bitnami/kafka:latest
        ports:
          - "9092:9092"
        environment:
          # 1. 관리 역할 설정 (브로커이자 컨트롤러)
          - KAFKA_CFG_PROCESS_ROLES=controller,broker
          # 2. 노드 ID 설정
          - KAFKA_CFG_NODE_ID=1
          # 3. 투표단 설정 (누가 관리자인지 명시)
          - KAFKA_CFG_CONTROLLER_QUORUM_VOTERS=1@kafka:9093
          # 4. 리스너 설정 (9092는 데이터용, 9093은 관리 통신용)
          - KAFKA_CFG_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093
          - KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092
          - KAFKA_CFG_CONTROLLER_LISTENER_NAMES=CONTROLLER

  * **PROCESS_ROLES=controller,broker** : "데이터도 저장하고(broker), 반장 노릇(controller)도 해라"라는 뜻입니다.
  * **CONTROLLER_QUORUM_VOTERS** : Zookeeper 대신 자기들끼리(혹은 지정된 관리자들끼리) 통신할 주소를 적습니다. 여기서는 자기 자신(1@kafka:9093)을 관리자로 지정한 것입니다.
  * **ADVERTISED_LISTENERS :** 실제 주소 적기
