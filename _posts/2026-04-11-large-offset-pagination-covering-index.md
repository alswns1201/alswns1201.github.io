대용량 게시글 목록을 페이지네이션으로 조회할 때, 단순히 `LIMIT`/`OFFSET`만 쓰면
페이지가 뒤로 갈수록 급격히 느려진다. 1,200만 건짜리 테이블에 직접 이 현상을
재현하고 원인을 추적해봤다.

## 문제 재현

```sql
SELECT * FROM article
WHERE board_id = 1
ORDER BY article_id DESC
LIMIT 30 OFFSET 1499980;
```

30건을 조회하는 데 7초가 걸렸다. `EXPLAIN` 결과:

```
1 SIMPLE article ALL 6322381 10.0 Using where; Using filesort
```

`type: ALL`은 풀 테이블 스캔이 일어났다는 뜻이고, `Using filesort`는 정렬을 위해
파일 단위 정렬까지 발생했다는 뜻이다. 인덱스 없이 조건 전체를 필터링하고 정렬했으니
느릴 수밖에 없다.

## 1차 개선: 인덱스

```sql
CREATE INDEX idx_board_id_article_id ON article(board_id ASC, article_id DESC);
```

`board_id`로 먼저 좁히고 `article_id` 정렬 순서까지 인덱스에 반영해두면, DB가
정렬된 상태의 데이터를 그대로 순회할 수 있다. 결과: 0.04초로 개선.

여기서 정렬 기준을 `created_at`이 아니라 시간 기반 UUID로 설계한 ID(`article_id`)로
잡은 이유가 있다 — 대규모 분산 환경에서는 여러 요청이 동시에 들어와 같은 타임스탬프를
가진 행이 다수 존재할 수 있다. `created_at`만으로 정렬하면 동시간대 데이터의 순서가
불안정(비결정적)해진다. 시간 기반이면서도 유일성이 보장되는 ID를 정렬 기준으로 쓰면
이 문제가 사라진다.

## 그런데 페이지가 뒤로 갈수록 다시 느려진다

같은 인덱스를 쓰는데도 90번째 페이지를 넘어가면 다시 6초 이상 걸린다. 원인을 알려면
인덱스의 두 종류를 구분해야 한다.

- **Clustered Index**: 책의 "페이지 번호" 자체. 데이터가 PK 순서로 물리적으로
  정렬돼 저장된다. MySQL InnoDB에서는 PK가 곧 클러스터 인덱스다.
- **Secondary Index**: 책 뒤의 "찾아보기". 키워드(`board_id` 등)와 그 데이터가
  있는 페이지 번호(PK)만 적혀 있다.

`SELECT *`를 하면, Secondary Index로 PK를 찾은 뒤 다시 Clustered Index(실제 데이터
본체)로 들어가는 과정이 행마다 반복된다. 이게 **랜덤 I/O**다. OFFSET이 커질수록 이
"찾아 들어갔다 버리는" 행의 개수가 그만큼 늘어난다 — offset 1,499,980이면 150만
번의 불필요한 데이터 본체 접근이 발생한 뒤에야 진짜 필요한 30건을 찾는다.

## 2차 개선: 커버링 인덱스

**커버링 인덱스(Covering Index)**는 인덱스에 담긴 정보만으로 쿼리에 답할 수 있는
경우를 말한다. `board_id, article_id`만 필요하다면 Secondary Index만 훑어도 되고,
데이터 본체(Clustered Index)로 들어갈 필요가 없다.

```sql
-- 컬럼을 인덱스에 있는 것만 조회 → 데이터 본체 접근 없음
SELECT board_id, article_id FROM article
WHERE board_id = 1
ORDER BY article_id DESC
LIMIT 30 OFFSET 1499980;
```

같은 조건인데 조회 컬럼만 바꿨을 뿐인데 7초 → 0.1초로 줄어든다. 이제 이 방식으로
PK만 먼저 빠르게 뽑고, 그 30개에 대해서만 실제 테이블을 조인한다.

```sql
SELECT * FROM (
    SELECT article_id FROM article
    WHERE board_id = 1
    ORDER BY article_id DESC
    LIMIT 30 OFFSET 1499980
) t
LEFT JOIN article ON t.article_id = article.article_id;
```

내부 쿼리는 인덱스만 훑어서 빠르고(0.1초), 외부 조인은 걸러진 30건에 대해서만
데이터 본체에 접근한다.

## 그런데 이것도 근본적인 해법은 아니다

커버링 인덱스는 **행 하나를 스캔하는 비용**을 줄여준 것이지, **스캔해야 하는 행의
개수**를 줄인 게 아니다. OFFSET이 1,500,000이면 여전히 150만 건을 인덱스 상에서
순회하고 버려야 한다 — 비용의 크기(상수 계수)가 작아졌을 뿐, 알고리즘 복잡도는
여전히 offset에 비례해서 커진다(O(offset)). 이 테이블이 지금보다 10배, 100배 커지면
커버링 인덱스를 써도 뒷페이지는 다시 느려진다.

진짜로 이 복잡도 자체를 없애는 방법은 **키셋(Keyset) 페이지네이션**이다. "몇 번째
행부터"가 아니라 "마지막으로 본 ID 다음부터"를 조건으로 건다.

```sql
SELECT * FROM article
WHERE board_id = 1 AND article_id < :lastSeenId
ORDER BY article_id DESC
LIMIT 30;
```

이러면 스킵해야 할 행 자체가 없다 — 인덱스에서 `lastSeenId` 위치를 바로 찾아
그다음부터 30건만 읽으면 끝난다. offset이 얼마든 성능이 거의 일정하다.

다만 이 방식엔 트레이드오프가 있다: **임의의 페이지 번호로 바로 점프할 수 없다.**
"마지막으로 본 ID"를 알아야 다음 페이지를 요청할 수 있으므로 순차 이동(다음/이전)만
가능하다. 그래서 원문에서 언급한 두 UX 패턴 — 페이지 번호 방식과 무한 스크롤 —
중 페이지 번호를 직접 입력해 임의의 페이지로 이동해야 하는 UI라면 키셋 방식을 그대로
쓸 수 없고, 무한 스크롤처럼 순차적으로만 다음 데이터를 가져오면 되는 UI라면 키셋
페이지네이션이 정확히 맞아떨어진다.

## 정리: 최적화 로드맵

1. **문제**: OFFSET 방식은 앞선 행을 전부 읽어야 해서 커질수록 느려진다 (풀 스캔).
2. **1차 개선(인덱스)**: 정렬된 인덱스로 탐색 범위를 줄인다.
3. **한계**: OFFSET이 커지면 인덱스를 타도 랜덤 I/O 비용이 커진다.
4. **2차 개선(커버링 인덱스)**: 인덱스만으로 PK를 먼저 추려서 랜덤 I/O 횟수를 최소화한다 — 상수 계수 개선.
5. **근본 해결(키셋 페이지네이션)**: "몇 번째"가 아니라 "어디부터"로 조건을 바꿔 알고리즘 복잡도 자체를 O(1)에 가깝게 만든다 — 대신 임의 페이지 점프를 포기한다.

어떤 방식을 쓸지는 결국 UI 요구사항(임의 페이지 이동이 필요한가)과 데이터 규모가
결정한다.
