요즘엔 TypeScript와 Next.js를 주로 다루고 있지만, 오늘은 프론트엔드 개발의 핵심인 JavaScript 기반 React의 기초부터 심화까지, 제가 경험하며 얻은 인사이트를 공유하고자 합니다. 특히 React 애플리케이션의 성능과 예측 가능성을 좌우하는 상태 변화 관리와 렌더링에 대해 깊이 있게 다뤄볼 예정입니다.

useCallback: 불필요한 함수 재생성 방지로 렌더링 최적화

### 1\. React, 왜 사용하는가? - 컴포넌트화와 렌더링의 기본

React를 사용하는 가장 보편적이고 강력한 이유는 바로 **컴포넌트화(Componentization)** 입니다. 

  * 독립적인 UI 조각: 각 컴포넌트는 UI의 독립적인 조각이며, 자신만의 로직과 상태를 가질 수 있습니다. 마치 레고 블록처럼, 이 컴포넌트들은 서로에게 영향을 주지 않으면서도 쉽게 조합하여 복잡한 UI를 구성할 수 있습니다.
  * 재사용성과 유지보수성: 한 번 만든 컴포넌트는 여러 곳에서 재사용될 수 있어 개발 효율을 높이고, 문제가 발생했을 때 해당 컴포넌트만 수정하면 되므로 유지보수가 용이합니다.



React 프로젝트를 시작할 때는 일반적으로******Create React App (CRA)****** 도구를 사용합니다.
    
    
    npm create-react-app [프로젝트명]
    # 또는
    npx create-react-app [프로젝트명]

이 명령어를 통해 [프로젝트명]이라는 디렉토리에 React 개발에 필요한 기본적인 환경이 자동으로 설정됩니다. 이 환경에서 우리는 컴포넌트를 만들고, 상태를 관리하며, 사용자 인터랙션에 반응하는 동적인 웹 애플리케이션을 만들게 됩니다.

### React 프로젝트 파일 구조

React 프로젝트의 파일 구조는 정답이 없지만, 효율적인 개발과 유지보수를 위해 몇 가지 일반적인 패턴이 있습니다. 프로젝트의 규모와 팀의 선호도에 따라 달라질 수 있습니다.

가장 일반적인 src 폴더 내부 구조 (Create React App 기준):

    │   └── styles/

    │   ├── common/        // 자주 사용되는 일반적인 컴포넌트 (버튼, 인풋 등)

    │   └── helpers.js     // 기타 공통 유틸리티
    ├── constants/         // 애플리케이션 전반에 사용되는 상수
    │   └── index.js       // API 엔드포인트, 에러 메시지, MOCK_DATA 등
    ├── services/          // API 통신, 데이터 처리 등 비즈니스 로직

구조 선택 팁:

  * 규모에 따라: 작은 프로젝트는 components/common, pages 등으로 단순하게 시작하고, 프로젝트가 커지면 components/featureName 또는 features/auth, features/products와 같이 기능별로 디렉토리를 나누는 것이 좋습니다.
  * 응집도: 관련된 파일들을 함께 두어 응집도를 높이는 것이 중요합니다. 예를 들어, ProductCard 컴포넌트의 스타일, 로직, 테스트 파일은 모두 components/ProductCard 디렉토리 안에 두는 식입니다.
  * 명확성: 파일 이름과 디렉토리 이름은 그 역할과 내용을 명확히 드러내야 합니다.



React 애플리케이션의 핵심 동작 원리는 **상태(State)가 변경되면 컴포넌트가 다시 렌더링된다** 는 것입니다. 사용자의 입력, 외부 데이터의 수신 등 다양한 요인으로 컴포넌트의 상태가 바뀌면, React는 해당 컴포넌트를 다시 그리고(re-render) 변경된 UI를 사용자에게 보여줍니다. 이때 불필요한 렌더링을 줄이는 것이 성능 최적화의 핵심이 됩니다.

React Hooks는 함수형 컴포넌트에서 상태와 생명주기 기능을 사용할 수 있게 해주는 강력한 도구입니다. 그 중 대표적인 useState에 대해서 알아보겠습니다.

### useState: 컴포넌트 내부의 임시적인 UI 상태 관리

useState는 컴포넌트 내부에서 변경될 수 있는 상태를 관리하는 가장 기본적인 Hook입니다. 이 훅은 주로 단일 컴포넌트 내에서 비교적 독립적으로 사용되는 일시적인(ephemeral) UI 상태들을 관리할 때 적합합니다.

  * 언제 사용하나?
    * 사용자의 입력 필드 값 (예: 폼 입력)
    * 토글 버튼의 활성화/비활성화 상태
    * 카운터 값
    * 모달 창의 열림/닫힘 상태
    * 다른 컴포넌트와 이 상태를 공유할 필요가 거의 없고, 폼 제출 후 상태가 대부분 초기화되는 경우 useState가 가장 간단하고 효율적인 방법입니다.



예시: 간단한 카운터 컴포넌트
    
    
    import React, { useState } from 'react';
    
    function Counter() {
      const [count, setCount] = useState(0); // count는 상태 변수, setCount는 상태 업데이트 함수
    
      const increment = () => {
        setCount(prevCount => prevCount + 1); // 이전 상태를 기반으로 업데이트
      };
    
      const decrement = () => {
        setCount(prevCount => prevCount - 1);
      };
    
      return (
        <div>
          <p>현재 카운트: {count}</p>
          <button onClick={increment}>증가</button>
          <button onClick={decrement}>감소</button>
        </div>
      );
    }
    
    export default Counter;

### useEffect: 컴포넌트 생명주기와 사이드 이펙트 관리

useEffect는 함수형 컴포넌트 내에서 사이드 이펙트(Side Effects) 를 수행할 때 사용됩니다.  
사이드 이펙트란? 데이터 페칭, DOM 직접 조작, 구독 설정/해제 등 컴포넌트의 렌더링 결과에 직접적인 영향을 주지 않으면서 외부와 상호작용하는 모든 작업을 의미합니다. useEffect는 주로 컴포넌트의 생명주기(마운트, 업데이트, 언마운트)에 맞춰 동작합니다.

  * 언제 사용하나?
    * 데이터 페칭: 컴포넌트가 마운트되거나 특정 상태가 변경될 때 서버에서 데이터를 불러와야 할 때.
    * DOM 직접 조작: React가 관리하지 않는 DOM을 직접 변경해야 할 때 (예: 특정 라이브러리 연동).
    * 이벤트 리스너 등록/해제: 전역 이벤트 리스너를 등록하고 컴포넌트가 언마운트될 때 해제해야 할 때.
    * 타이머 설정/해제: setTimeout, setInterval 등을 사용할 때.
    * 폼 관리 예시:
      * 외부 데이터로 폼 초기화: 기존 데이터를 불러와 폼을 미리 채워야 할 때 (예: "모임 수정" 화면에서 기존 모임 정보를 불러와 폼에 채우기).
      * 폼 유효성 검사를 실시간으로 표시: 모든 입력에 대해 실시간으로 유효성 메시지를 보여주고 싶을 때.



#### useState vs useEffect 분석

#### **\- useState 는 컴포넌트 내부의 "직접적인 UI 상태"를 관리합니다.-**

**\- useEffect 는 컴포넌트가 렌더링된 "이후"에 발생하는 "사이드 이펙트"를 관리합니다.**

정리 하자면, 다른 컴포넌트와 연관이 없다면 useState로만 관리하고 useEffect는 외부 api로 초기값을 세팅한다거나 실시간으로 체크해서 데이터를 바꿔야 하는 일을 맡게 됩니다.

예시: 데이터 페칭 및 document.title 업데이트
    
    
    import React, { useState, useEffect } from 'react';
    
    function PostViewer() {
      const [post, setPost] = useState(null);
      const [postId, setPostId] = useState(1);
    
      // postId가 변경될 때마다 새로운 게시물 데이터를 불러옴
      useEffect(() => {
        const fetchPost = async () => {
          try {
            const response = await fetch(`https://jsonplaceholder.typicode.com/posts/${postId}`);
            const data = await response.json();
            setPost(data);
          } catch (error) {
            console.error("데이터 불러오기 실패:", error);
            setPost(null);
          }
        };
    
        fetchPost();
    
        // 클린업 함수 (컴포넌트 언마운트 또는 의존성 변경 시 실행)
        return () => {
          // 필요한 경우 여기서 리소스 정리 (예: 구독 해제)
        };
      }, [postId]); // 의존성 배열: postId가 변경될 때만 이 effect가 재실행됩니다.
    
      // 게시물 제목이 변경될 때마다 document.title 업데이트
      useEffect(() => {
        if (post) {
          document.title = post.title;
        }
      }, [post]); // 의존성 배열: post 객체가 변경될 때만 이 effect가 재실행됩니다.
    
      return (
        <div>
          <p>게시물 ID: {postId}</p>
          <button onClick={() => setPostId(prevId => prevId + 1)}>다음 게시물</button>
          {post ? (
            <div>
              <h3>{post.title}</h3>
              <p>{post.body}</p>
            </div>
          ) : (
            <p>게시물을 불러오는 중이거나 없습니다.</p>
          )}
        </div>
      );
    }
    
    export default PostViewer;

### useCallback: 불필요한 함수 재생성 방지로 렌더링 최적화

useCallback은 함수의 메모이제이션(memoization) 을 위한 훅입니다. 특정 함수가 컴포넌트가 리렌더링될 때마다 불필요하게 다시 생성되지 않도록 방지하여 성능 최적화에 기여합니다.

  * **왜 필요한가?**  
React 컴포넌트가 리렌더링될 때, 그 컴포넌트 내부에 정의된 함수들도 (비록 코드는 동일하더라도) JavaScript 엔진 입장에서는 새로운 함수 인스턴스로 생성됩니다. **만약 이 새로운 함수 인스턴스가 자식 컴포넌트의 ****prop 으로 전달되면, 자식 컴포넌트가 React.memo (또는 클래스 컴포넌트의 PureComponent)로 감싸져 있더라도 prop이 변경되었다고 판단하여 불필요하게 리렌더링됩니다.**
  * useCallback의 역할:  
useCallback으로 함수를 감싸면, 의존성 배열의 값이 변경될 때만 해당 함수가 새로 생성됩니다. 의존성 배열이 비어있다면([]), 컴포넌트가 처음 마운트될 때 한 번만 생성되고 이후 리렌더링 시에는 항상 같은 함수 인스턴스를 사용합니다.



useCallback 사용법:
    
    
    import React, { useCallback } from 'react';
    
    const memoizedCallback = useCallback(
      () => {
        // 이 함수는 의존성 배열의 값이 변경될 때만 새로 생성됩니다.
      },
      [dependency1, dependency2], // 의존성 배열
    );

  * 첫 번째 인자: 메모이제이션할 함수 정의.
  * 두 번째 인자 (의존성 배열): 이 배열 안에 있는 값들이 변경될 때만 memoizedCallback 함수가 새로 생성됩니다. 배열이 비어있다면 ([]), 컴포넌트가 처음 마운트될 때 한 번만 생성되고 이후 리렌더링 시에는 항상 같은 함수 인스턴스를 사용합니다.



**언제 useCallback****을 써야 할까?** (주요 사용 사례)

  1. React.memo와 함께 자식 컴포넌트에 prop으로 함수를 전달할 때:
     * **부모 컴포넌트에서 useCallback으로 함수를 메모이제이션하여 자식에게 전달하면, 자식 컴포넌트가 React.memo로 최적화되어 있을 때 불필요한 리렌더링을 방지할 수 있습니다. 이것이 useCallback의 가장 주된 사용 목적입니다.**



예시: useCallback과 React.memo의 시너지
    
    
    import React, { useState, useCallback, memo } from 'react';
    
    // 자식 컴포넌트 (React.memo로 래핑하여 props 변경 시에만 리렌더링)
    // memo를 사용하면 props가 같다면 리렌더링하지 않음
    const Button = memo(({ onClick, label }) => {
      console.log(`${label} Button Rendered`);
      return <button onClick={onClick}>{label}</button>;
    });
    
    function ParentComponent() {
      const [count, setCount] = useState(0);
      const [text, setText] = useState('');
    
      // count가 변경될 때만 이 함수가 새로 생성됨
      const handleClickCount = useCallback(() => {
        setCount(prevCount => prevCount + 1);
      }, []); // 빈 배열: 컴포넌트 마운트 시 한 번만 생성
    
      // text가 변경될 때만 이 함수가 새로 생성됨
      const handleTextInput = useCallback((event) => {
        setText(event.target.value);
      }, []); // 빈 배열: 컴포넌트 마운트 시 한 번만 생성
    
      return (
        <div>
          <h1>부모 컴포넌트</h1>
          <p>카운트: {count}</p>
          <input type="text" value={text} onChange={handleTextInput} placeholder="텍스트 입력" />
          <p>입력 텍스트: {text}</p>
    
          {/* handleClickCount는 useCallback으로 메모이제이션 되었으므로,
              ParentComponent가 텍스트 입력으로 인해 리렌더링 되어도 Button은 리렌더링되지 않음 */}
          <Button onClick={handleClickCount} label="카운트 증가" />
    
          {/* useCallback을 사용하지 않은 함수를 전달하면 매번 Button이 리렌더링 됨 */}
          <Button onClick={() => console.log('Hello')} label="Hello 출력 (렌더링 됨)" />
        </div>
      );
    }
    
    export default ParentComponent;

위 코드에서 보면

\- _ParentComponent가 텍스트 입력으로 인해 리렌더링 되어도 Button은 리렌더링되지 않음_

\- _useCallback을 사용하지 않은 함수를 전달하면 매번 Button이 리렌더링 됨_

이 두 주석을 살펴보면 handleTextInput으로 ParentComponent가 리렌더링되더라도, **handleClickCount 는 useCallback으로 인해 같은 함수 인스턴스를 유지하므로 Button 컴포넌트는 불필요하게 리렌더링되지 않습니다.**

### useState를 넘어선 전역 상태 관리 (store)

컴포넌트의 규모가 커지거나 여러 컴포넌트 간에 동일한 상태를 공유해야 할 때는 useState만으로는 한계가 있습니다. 이럴 때 우리는 전역 상태 관리(Global State Management) 패턴을 고려합니다. 흔히 "store"라고 부르는 전역 상태 저장소를 통해 애플리케이션의 어디서든 접근하고 변경할 수 있는 상태를 관리합니다. store (예: Redux, Zustand, Recoil, Jotai 또는 React Context API)는 다음과 같은 상황에서 고려해볼 만합니다.

  1. **전역적으로 공유되어야 하는 상태** :
     * 로그인 사용자 정보: 현재 로그인한 사용자 정보 (MOCK_CURRENT_USER 같은 목업 데이터가 실제 사용자 정보로 대체될 경우). 이 정보는 대부분의 페이지/컴포넌트에서 필요할 것입니다.
     * 장바구니, 알림 메시지, 다크 모드 설정 등 여러 컴포넌트에서 접근하고 변경해야 하는 상태.
     * Toast 컴포넌트의 showToast 함수처럼 여러 컴포넌트에서 재사용되는 기능. (만약 Toast 상태 자체를 Context API로 관리하여 showToast 함수를 어디서든 호출할 수 있도록 만들 수 있다면 전역 상태 관리 패턴을 고려할 수 있습니다.)



**주요 전역 상태 관리 솔루션 종류**

  * **React Context API** : React에 내장된 기능으로, 작은 규모의 전역 상태나 테마, 사용자 정보 등 자주 바뀌지 않는 데이터를 컴포넌트 트리에 걸쳐 전달하기 좋습니다. props drilling (props를 여러 단계의 컴포넌트로 전달해야 하는 불편함)을 피할 수 있습니다.
  * **Redux** : 가장 오래되고 강력한 전역 상태 관리 라이브러리 중 하나입니다. 예측 가능한 상태 관리, 강력한 디버깅 도구, 미들웨어 확장성 등 장점이 많지만, 보일러플레이트(boilerplate) 코드가 많아 학습 곡선이 높을 수 있습니다.
  * **Zustand, Recoil, Jotai** : 비교적 최근에 등장한 라이브러리들로, Redux보다 훨씬 가볍고 사용하기 쉽다는 장점이 있습니다. React Hook과 유사한 방식으로 전역 상태를 관리하며, 작은 설정으로도 강력한 기능을 제공합니다.



### 결론

1. useState (상태 변경 및 렌더링 유발)

  * **역할:** 컴포넌트의 특정 상태 값을 관리하고, 이 값이 변경되면 **컴포넌트의 리렌더링을 유발** 합니다.
  * **동작:** setCount(newCount)와 같이 useState의 setter 함수를 호출하면, React는 해당 컴포넌트를 다시 렌더링하도록 스케줄링합니다. 즉, 컴포넌트 함수가 처음부터 다시 실행됩니다.



2. useEffect (렌더링 후 부수 효과 실행)

  * **역할:** 컴포넌트가 **렌더링된 이후** 에 특정 부수 효과(side effect)를 수행하도록 합니다. 이 부수 효과는 DOM 조작, 데이터 fetching, 구독 설정, 타이머 설정 등이 될 수 있습니다.
  * **동작:** useEffect는 컴포넌트가 마운트될 때 한 번 실행되고, 이후에는 **컴포넌트가 리렌더링될 때마다 (혹은 의존성 배열의 값이 변경될 때만) 실행됩니다.**



둘의 관계

useState의 상태 변경은 **컴포넌트가 리렌더링되는 원인** 이 됩니다. 그리고 이 **리렌더링이 발생하면, useEffect가 실행될 기회를 얻게 됩니다.**

다시 말해:

  1. 어떤 이벤트(예: 버튼 클릭)로 인해 useState의 상태가 변경됩니다.
  2. useState는 해당 컴포넌트의 **리렌더링을 트리거** 합니다.
  3. 컴포넌트가 리렌더링됩니다 (함수 실행).
  4. 리렌더링이 완료된 후, React는 useEffect 훅을 확인하고, **의존성 배열의 값(dependencies)이 변경되었다면 useEffect 내의 콜백 함수를 실행**합니다.



**이는 useEffect가 렌더링을 직접적으로 유발하는 것이 아니라, 렌더링에 "반응"하여 동작한다는 것을 의미합니다.**

JavaScript 기반 React는 웹 개발의 강력한 도구이며, 컴포넌트화와 효율적인 상태 및 렌더링 관리가 그 핵심입니다. useState로 지역 상태를 관리하고, useEffect로 사이드 이펙트를 처리하며, useCallback과 같은 훅으로 불필요한 렌더링을 줄여 성능을 최적화할 수 있습니다. 더 나아가, 애플리케이션의 규모가 커질 때는 Context API나 다른 전역 상태 관리 라이브러리를 통해 효율적으로 상태를 공유할 수 있습니다.
