LLM을 실제 서비스에 적용하다 보면 세 가지 개념이 자주 등장한다. Skill Prompt, Tool Use, MCP. 비슷해 보이지만 역할과 동작 방식이 완전히 다르다.

## 1\. Skill Prompt

### 개념

Skill Prompt는 LLM에게 **행동 규칙이나 도메인 지식을 텍스트로 주입** 하는 방식이다. 보통 .md 파일로 작성해두고 System Prompt 또는 User Prompt에 삽입해서 사용한다.

### 동작 방식
    
    
    .md 파일 로드 → System/User Prompt에 삽입 → LLM이 읽고 규칙에 따라 응답
    

LLM이 외부 무언가를 호출하는 게 아니라, 프롬프트 안에 담긴 지침을 읽고 **스스로 판단해서 따르는** 것이다.

### 실제 코드 예시
    
    
    @Value("classpath:skills/math-parser.md")
    private Resource mathSkillResource;
    
    // .md 파일을 읽어서 프롬프트에 삽입
    this.skillPrompt = StreamUtils.copyToString(
        mathSkillResource.getInputStream(), StandardCharsets.UTF_8
    );
    
    MessageCreateParams.builder()
        .addUserMessage(skillPrompt + "\n\n" + userInput)
        .build();
    

### 한계

LLM이 지침을 **지키려고 노력** 하지만 보장은 없다. 복잡한 문제일수록 형식이 흔들리거나 필드를 빠뜨릴 수 있다. 결과물이 확률적이다.

### 언제 쓰나

  * 분석 방법, 답변 스타일, 도메인 규칙을 지정할 때
  * 출력 형식보다 **"어떻게 생각할지"** 를 제어할 때



## 2\. Tool Use (Function Calling)

### 개념

Tool Use는 LLM이 **외부 함수를 호출** 할 수 있게 하는 메커니즘이다. 개발자가 함수의 이름, 설명, 입력 스키마를 JSON으로 정의하면, LLM이 대화 중 필요하다고 판단할 때 해당 함수 호출을 요청한다. 실제 실행은 개발자가 작성한 코드가 담당한다.

### 동작 방식
    
    
    도구 정의 (JSON 스키마)
        → LLM이 "이 도구 써야겠다" 판단
        → tool_use 블록 응답
        → 개발자 코드가 실제 API 호출
        → 결과를 LLM에 다시 전달
        → 최종 응답 생성
    

중요한 점은 **LLM이 직접 API를 호출하지 않는다** 는 것이다. LLM은 "이 도구를 이 인자로 써달라"는 신호만 보내고, 실제 호출은 개발자 코드가 처리한다.

### 실제 코드 예시
    
    
    // 1. 도구 정의
    Tool parseTool = Tool.builder()
        .name("parse_math_problems")
        .description("이미지에서 수학 문제를 추출")
        .inputSchema(/* JSON 스키마 */)
        .build();
    
    // 2. LLM에 도구와 함께 요청
    MessageCreateParams.builder()
        .tools(List.of(ToolUnion.ofTool(parseTool)))
        .toolToolChoice("parse_math_problems") // 반드시 이 도구 사용 강제
        .build();
    
    // 3. LLM 응답에서 tool_use 블록 꺼내서 개발자가 처리
    response.content().stream()
        .flatMap(block -> block.toolUse().stream())
        .findFirst()
        .map(toolUse -> {
            // 여기서 실제 로직 실행
        });
    

### Skill Prompt와의 차이

Tool Use를 JSON 스키마 강제에 사용하면 Skill Prompt와 결정적으로 다른 점이 있다.

Skill Prompt로 형식 지정 Tool Use 스키마 강제

강제 주체 | LLM (확률적) | API 레벨 (결정적)  
---|---|---  
앞뒤 텍스트 | 붙을 수 있음 | 절대 안 붙음  
필드 누락 | 가능 | required면 불가  
파싱 코드 | try/catch 필수 | 바로 역직렬화 가능  
  
### 언제 쓰나

  * 구조화된 JSON 출력을 **반드시** 보장해야 할 때
  * 외부 API(날씨, 계산기, DB 등)를 LLM 판단에 따라 호출해야 할 때
  * 호출 로직을 개발자가 직접 제어해야 할 때



## 3\. MCP (Model Context Protocol)

### 개념

MCP는 Anthropic이 만든 **표준 프로토콜** 로, LLM과 외부 서비스를 연결하는 방식을 규격화한 것이다. 개발자는 MCP 서버 URL만 연결해두면, LLM이 대화 맥락을 보고 필요한 시점에 **알아서 호출** 한다.

### Tool Use와의 차이

Tool Use는 외부 API를 호출하는 중간 코드를 개발자가 직접 작성한다. MCP는 그 중간 코드가 MCP 서버 안에 이미 구현되어 있다. 개발자는 연결만 한다.
    
    
    Tool Use:
    LLM → tool_use 신호 → 개발자 코드 → 외부 API
    
    MCP:
    LLM → MCP 서버 → 외부 API
          (이미 구현된 서버)
    

### 동작 방식
    
    
    MCP 서버 URL 등록 (한 번만)
        → LLM이 대화 중 필요하다고 판단
        → MCP 서버에 직접 요청
        → MCP 서버가 외부 API 호출 및 결과 반환
        → LLM이 결과로 최종 응답 생성
    

### 실제 코드 예시
    
    
    // 연결만 해두면 끝
    mcp_servers: [
        {
            type: "url",
            url: "https://gmailmcp.googleapis.com/mcp/v1",
            name: "gmail-mcp"
        },
        {
            type: "url",
            url: "https://drivemcp.googleapis.com/mcp/v1",
            name: "drive-mcp"
        }
    ]
    // LLM이 필요하면 알아서 Gmail, Drive 호출
    

### 

  * Gmail, Google Drive, Slack 같이 **이미 MCP 서버가 존재하는 서비스** 를 연동할 때
  * 호출 타이밍과 로직을 LLM에게 완전히 위임할 때
  * 여러 서비스를 하나의 표준 방식으로 연결할 때



## 세 가지 비교 요약

Skill Prompt Tool Use MCP

역할 | 행동 규칙 주입 | 함수 호출 메커니즘 | 외부 서비스 연결 표준  
---|---|---|---  
실행 주체 | LLM (추론) | 개발자 코드 | MCP 서버  
호출 코드 작성 | 불필요 | 개발자가 직접 작성 | MCP 서버가 담당  
결과 보장 | 확률적 | 결정적 (스키마 강제 시) | 결정적  
재사용성 | 프롬프트 복사 | 앱마다 재구현 | 서버 하나로 공유  
  
## 

세 가지는 대립 관계가 아니라 **계층적으로 함께 쓰인다**.
    
    
    Skill Prompt  →  "수학 문제를 이렇게 분석해"       (행동 지침)
    Tool Use      →  분석 결과를 JSON으로 반드시 반환   (출력 보장)
    MCP           →  필요하면 외부 DB에 저장            (서비스 연결)
    

각각의 역할이 명확하게 분리되어 있기 때문에, 하나가 다른 하나를 대체하는 게 아니라 각자 맡은 레이어에서 동작한다.
