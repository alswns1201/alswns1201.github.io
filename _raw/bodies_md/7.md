Rest API 의 유행이 시작하며 대부분의 API 통신은 REST API 통신을 하고 있다고 생각했습니다. 하지만 IT 기술은 계속 해서 발전하고 최근  GRPC 통신이라는기술이 도입되면서, 조금 더 편리한 데이터 통신을 할수 있었습니다.  
실무에서 사용해본 GRPC에 대해서 이야기 해봅시다. **Spring boot 환경에서의 GRPC API** 를 주고 받아 볼 예정입니다.

### 기존 데이터 통신 방식의 문제점

  1. Java Serialization 과 같은 특정 언어에서 지원하는 직렬화를 사용시 특정 언어에 종속된다.
  2. JSON or XML 사용 방식은 큰 부하를 발생 시킨다.  
웹 프레임워크의 도움을 받아 간편한게 객체 값을 JSON으로 파싱 또는 JSON을 객체로 파싱하여 사용 할 수 있다. 하지만 내부적으로는 파싱을 위해 상당한 리소스를 사용해야 할 수 도 있다. 위 문제점을 해결하기 위해 사용하는게 Protocol Buffer이다.



### 동장 방식 및 SpringBoot 설정

RPC에서 클라이언트-서버 통신은 클라이언트 API 요청이 로컬 작업이거나 요청이 내부 서버 코드인 것처럼 작동합니다.

우선 다행이도 SPRING BOOT에서는 dependency를 제공 하고 있는것 같습니다.

  * o.grpc:grpc-netty-shaded
  * io.grpc:grpc-protobuf
  * io.grpc:grpc-stub



3가지 impementation을 통합으로 관리해 주는 net.devh:grpc-spring-boot-starter

이번 업무에서는 Client에서 통신이였기 때문에 하나 더 추가할 것이 있었다.

### 서비스 정의 파일 (Protobuf)

.proto 확장자 라고 부르며 아래는 예시 파일 입니다.
    
    
    syntax = "proto3";
    
    package helloworld;
    
    service Greeter {
      rpc SayHello (HelloRequest) returns (HelloResponse);
    }
    
    message HelloRequest {
      string name = 1;
    }
    
    message HelloResponse {
      string message = 1;
    }

gRPC 서버-클라이언트 간 이렇게 통신하기로 약속 한다는 의미 이며 인터페이스 와 DTO 를 생성 한다고 생각하면 됩니다.   
.proto 이 처럼 크게 **1) 서비스 정의, 2) 메시지 정의** 를 해줍니다.  
  
gRPC 서버측에서 사용하는 .proto 파일을 받아서 프로젝트 /src/main/proto/안에 넣는것이 일반적인 경로입니다. 바로 넣는다고 되는 것은 아니고, 위에 프로토파일이 있다면 이를 Java 코드로 변환을 해야 한다. Gradle에서는 protobuf-gradle-plugin을 사용할 수 있습니다
    
    
    plugins {
      id 'com.google.protobuf' version '0.9.2'
    }
    protobuf {
        protoc {
            artifact = 'com.google.protobuf:protoc:3.17.3'
        }
        generateProtoTasks {
            all()*.plugins {
                grpc {}
            }
        }
    }

플러그인에 com.google.protobuf 를 추가하고, protobuf 설정을 적용 하면 Spring boot에서

### .proto 문법

  * rpc : 메소드를 포함 할수 있으며, 각 rpc 메소드는 클라이언트와 서버간의 통신을 정의


    
    
    service ServiceName {
        rpc SetItem (SetItemRequest) returns (GetRequest) {
            option (google.api.http) = {
                post: "url"
                body: "*"
            };
        }
    }

위에서 사용되는 코드에 대해서 알아 봅시다.**  
ServiceName** : gRPC 서버에서 제공하는 서비스의 이름  
**SetItem** : Method 이름  
**GetRequest** : GetRequest는 클라이언트가 이 메소드를 호출할 때 전달하는 요청 메시지입니다.  
(따로 SetItemRequest 와 GetRequest 는 .proto에 Message로 정의되어 집니다. )
    
    
    message SetItemRequest {
        string key = 1;
        // json data
        string value = 2;
    }
    
    message GetRequest {
        string key = 1;
        repeated Data data =2;
    
        message Data {
            string pcust_nmbr = 1;
            string check_date = 2;
            string srvc_code = 3;
            string rept_code = 4;
            string cnty_code = 5;
        }
    }

  * repeated : 0개 이상의 반복을 나타내며 순서가 유지된다. 즉, 필드가 여러개 값을 가질 수 있음을 의미한다.
  * optional : 값이 없어도 되며 없는 경우 기본값이 들어 간다. (string -> "" , int32 -> 0)
  * =숫자 : 숫자는 Field Number를 의미한다. 데이터를 직렬화 할때 사용 , 버전 관리 호환성 유지에 도움을 준다.
  * 중첩 메시지 : 객체지향에서 클래스 안에 다른 클래스를 정의하는 것과 유사


    
    
    message SetPaperDataItem {
        string srvc_code = 1;
        string rept_code = 2;
        string cnty_code = 3;
        string chck_date = 4;
        string pcust_nmbr = 5;
        string pcust_name = 6;
        string brth_date = 7;
        repeated PaperWeight paper_weight_list = 8;
        repeated Diagnosis diagnosis_list = 9;
        
        message PaperWeight {
            repeated Data data = 1;
    
            message Data {
                string code = 1;
                string name = 2;
                string value = 3;
            }
        }
    
        message Diagnosis {
            repeated Data data = 1;
    
            message Data {
                string code = 1;
                string name = 2;
                // string or DataList

                message ListData {
                    repeated Data data = 1;
                    message DataItem {
                        string code = 1;

                    }
                }
            }
        }
    }

### gRPC의 장점

gRPC 서비스의 성능 최적화  
HTTP/2 최적화: gRPC는 HTTP/2를 기반으로 하므로, HTTP/2의 특성을 잘 활용하여 성능을 최적화합니다.  
서버 리소스 관리: 서버의 CPU, 메모리, 네트워크 자원을 고려하여 가용성을 높이는 설정을 고려합니다.  
Stream 처리: gRPC의 스트리밍 기능을 사용하면 실시간 통신이나 대용량 데이터를 효율적으로 처리할 수 있습니다.

**Synchronous의 Syn** : 그리스어로 '함께' + chrono는 '시간'이라는 뜻이다. 즉, Synchronous는 작업 시간을 함께 맞춰서 실행한다 라는 뜻으로 해석된다. 작업을 맞춰 실행한다는 말은 요청한 작업에 대해 완료 여부를 따져 순차대로 처리하는 것을 말합니다.

아래는 springboot에서 stub에 channel을 적용하여 사용한 코드 입니다.
    
    
        public CodefGrpcService(@Value("${grpc.ip}")String ip , @Value("${grpc.port}")int port) throws SSLException {
    
    
            SslContextBuilder sslContextBuilder = GrpcSslContexts.forClient()
                    .trustManager(InsecureTrustManagerFactory.INSTANCE);
    
            SslContext sslContext = sslContextBuilder.build();
    
            this.channel =  NettyChannelBuilder
                    .forAddress(ip, port)
                    .sslContext(sslContext)
                    .overrideAuthority(ip)  // 호스트명 검증 우회
                    .build();
    
            this.blockingStub = FromageServiceGrpc.newBlockingStub(channel);
            this.futureStub =FromageServiceGrpc.newFutureStub(channel);
        }
