**\- 한 번의 응답을 어떻게 메모리 효율적으로 처리할 것인가 **

**\- 수많은 페이지 반복을 어떻게 안정적으로 끝까지 처리할 것인가**

nextUrl 기반으로 페이지네이션된 API를 순회하면서 result 값을 DB에 적재하는 로직을 만들 때는 두 가지 축을 구분해서 접근하는 것이 좋다. 하나는 한 번의 응답을 어떻게 메모리 효율적으로 처리할 것인가이고, 다른 하나는 수많은 페이지 반복을 어떻게 끝까지 안정적으로 처리할 것인가이다.

### 한 번의 응답을 메모리 효율적으로 처리하기

가장 흔한 함정은 응답 전체를 문자열이나 트리로 통째로 읽는 방식이다.
    
    
    byte[] allBytes = inputStream.readAllBytes();
    JsonNode root = objectMapper.readTree(allBytes);

이 방식은 두 단계에서 메모리를 크게 소비한다. readAllBytes()가 스트림 전체를 끝까지 읽어 하나의 byte 배열로 만드는 시점에 응답 크기만큼의 연속된 메모리가 필요하고, readTree()가 그 바이트를 파싱해 JsonNode 트리 객체 그래프로 만드는 시점에는 자바 객체 오버헤드가 더해져 원본 크기보다 몇 배 큰 메모리가 필요해진다. 필요한 최대 메모리가 응답 크기에 비례해서 계속 커진다는 것이 핵심 문제다.

대안은 HTTP 계층과 파싱 계층 모두에서 스트리밍 방식을 쓰는 것이다.
    
    
    public class StreamingJsonFetcher {
    
        private final HttpClient httpClient = HttpClient.newHttpClient();
        private final JsonFactory jsonFactory = new JsonFactory();
        private final ObjectMapper objectMapper = new ObjectMapper();
        private static final int CHUNK_SIZE = 500;
    
        public void fetchAll(String startUrl) throws IOException, InterruptedException {
            String url = startUrl;
            while (url != null) {
                url = fetchOnePage(url);
            }
        }
    
        private String fetchOnePage(String url) throws IOException, InterruptedException {
            HttpRequest request = HttpRequest.newBuilder(URI.create(url)).GET().build();
    
            // 응답 바디를 InputStream으로 받는다 - byte[]나 String으로 먼저 통째로 만들지 않는다
            HttpResponse<InputStream> response =
                    httpClient.send(request, HttpResponse.BodyHandlers.ofInputStream());
    
            String nextUrl = null;
            List<ResultDto> chunk = new ArrayList<>(CHUNK_SIZE);
    
            try (InputStream body = response.body();
                 JsonParser parser = jsonFactory.createParser(body)) {
    
                while (parser.nextToken() != null) {
                    String fieldName = parser.getCurrentName();
    
                    if ("result".equals(fieldName)) {
                        parser.nextToken(); // START_ARRAY로 이동
                        while (parser.nextToken() != JsonToken.END_ARRAY) {
                            // 배열 원소 하나(JSON object)만 트리로 변환 - 원소 단위로만 메모리 사용
                            ResultDto dto = objectMapper.readValue(parser, ResultDto.class);
                            chunk.add(dto);
    
                            if (chunk.size() >= CHUNK_SIZE) {
                                batchInsert(chunk);
                                chunk.clear();
                            }
                        }
                    } else if ("nextUrl".equals(fieldName)) {
                        parser.nextToken();
                        nextUrl = parser.getValueAsString();
                    }
                }
            }
    
            if (!chunk.isEmpty()) {
                batchInsert(chunk);
            }
            return nextUrl;
        }
    
        private void batchInsert(List<ResultDto> chunk) {
            jdbcTemplate.batchUpdate(
                "INSERT INTO result_table (id, value) VALUES (?, ?)",
                chunk,
                chunk.size(),
                (ps, dto) -> {
                    ps.setLong(1, dto.getId());
                    ps.setString(2, dto.getValue());
                }
            );
        }
    }

#### InputStream으로 받는다는 것의 의미

HttpResponse.BodyHandlers.ofString()을 쓰면 HttpClient 내부에서 소켓으로부터 응답을 끝까지 다 읽어 byte 배열로 모은 뒤 문자열로 디코딩한다. 이 시점에 응답 크기만큼의 메모리가 이미 소비된 상태다. 반면 ofInputStream()을 쓰면 HttpClient는 응답을 끝까지 미리 읽지 않고, 소켓 버퍼에서 필요한 만큼씩만 읽어 넘겨주는 스트림을 반환한다. 이 스트림에서 read를 호출하는 시점에 실제로 네트워크에서 데이터를 가져온다.

다만 InputStream을 받는 것 자체가 메모리 절약을 보장하지는 않는다. 받은 스트림에 대해 readAllBytes()를 호출해버리면 결국 전체를 한 번에 메모리로 끌어오는 것과 동일해진다. 진짜 이점을 보려면 스트림을 소비하는 파싱 계층도 끝까지 한 번에 읽지 않고 필요한 만큼만 순차적으로 읽어나가야 한다. HTTP 계층에서 스트림으로 받는 것과 파싱 계층에서도 스트리밍 방식으로 처리하는 것이 둘 다 갖춰져야 전체 파이프라인이 메모리 효율적이게 된다.

#### 토큰 단위로 읽는다는 것의 의미

JsonParser는 내부적으로 크지 않은 고정 크기의 버퍼만 가지고 있다. nextToken()을 호출하면 파서는 내부 버퍼에 아직 해석할 데이터가 남아있는지 확인하고, 비어 있으면 그때 InputStream으로부터 딱 버퍼 크기만큼만 추가로 읽어온다. 버퍼 안의 바이트를 해석해서 토큰 하나를 만들어 반환하는 과정이 파일 끝에 도달할 때까지 반복된다.

JSON 문서 {"result": [{"id":1}, {"id":2}], "nextUrl": "..."}를 JsonParser로 읽으면 대략 다음과 같은 토큰 시퀀스가 순서대로 나온다.
    
    
    START_OBJECT
    FIELD_NAME       ("result")
    START_ARRAY
    START_OBJECT
    FIELD_NAME       ("id")
    VALUE_NUMBER_INT (1)
    END_OBJECT
    START_OBJECT
    FIELD_NAME       ("id")
    VALUE_NUMBER_INT (2)
    END_OBJECT
    END_ARRAY
    FIELD_NAME       ("nextUrl")
    VALUE_STRING     ("...")
    END_OBJECT

토큰화 단위는 키-값 쌍이 아니라 그보다 잘게 쪼개진 단위다. FIELD_NAME(키)과 그에 대응하는 값은 하나로 묶인 토큰이 아니라 각각 별개의 토큰이고, 여기에 더해 START_OBJECT나 END_ARRAY처럼 값이 아니라 구조의 시작과 끝을 나타내는 토큰도 존재한다. 다만 objectMapper.readValue(parser, ResultDto.class)처럼 상위 레벨 메서드를 쓰면, 그 메서드 내부에서 START_OBJECT부터 END_OBJECT까지의 토큰들을 자동으로 순회해서 객체 하나로 조립해주기 때문에, 코드를 작성하는 입장에서는 객체 하나 단위로 읽는다는 감각으로 다뤄도 무방하다.

#### 통째로 읽는 방식과의 차이

두 방식 모두 결국 네트워크에서 바이트를 읽어온다는 점은 같지만, 차이는 그 바이트들을 동시에 얼마나 오래, 얼마나 많이 메모리에 붙잡아두는가에 있다.

통째로 읽는 방식은 응답을 다 모을 때까지 계속 메모리에 쌓아두기 때문에 최대 메모리 사용량이 응답 크기에 비례해서 계속 커진다. 스트리밍 처리 방식은 파서가 지나간 토큰은 바로 버려지고, 조립된 객체도 청크 크기만큼 쌓이면 DB에 저장한 뒤 참조를 끊기 때문에, 어느 순간에도 메모리에 살아있는 데이터의 양이 파서 내부 버퍼와 현재 청크 크기 정도로 상한이 고정된다. 이 상한은 원본 응답이 얼마나 크든 바뀌지 않는다.

### 수많은 페이지 반복을 안정적으로 처리하기

이 부분은 메모리보다는 시간, 안정성, 장애 복구의 문제에 가깝다.

전체를 하나의 긴 프로세스로 처리하면, 중간에 API가 타임아웃되거나 애플리케이션이 재시작될 때 처음부터 다시 시작해야 한다. 마지막으로 성공한 url을 DB나 Redis에 체크포인트로 기록해두고, 재시작 시 그 지점부터 이어서 처리하도록 설계하는 것이 중요하다. 이 경우 DB insert는 반드시 멱등성을 가져야 한다. 같은 url을 두 번 처리해도 중복 저장되지 않도록 유니크 제약 조건과 upsert 방식을 함께 쓴다.

nextUrl이 응답에 포함되어야만 다음 페이지를 알 수 있는 구조라면 본질적으로 순차 처리일 수밖에 없다. 이런 경우에는 처리량을 늘리는 것보다 재시도와 체크포인트를 통한 안정성 확보에 집중하는 편이 맞다. 외부 API 호출이 반복되는 만큼 일시적인 네트워크 오류나 rate limit에 대비한 지수 백오프 재시도, 반복 실패 시 회로를 차단하는 처리도 필요하다.

이 정도 규모의 처리라면 직접 루프를 짜는 것보다 Spring Batch의 Chunk-oriented Step 구조를 검토할 만하다. ItemReader가 nextUrl을 따라가며 스트리밍으로 읽고 ItemWriter가 청크 단위로 배치 삽입하는 구조를 쓰면, 체크포인트와 재시작, 트랜잭션 경계 관리를 프레임워크가 대신 처리해준다. 직접 구현한다면 위에서 정리한 파이프라인 구조를 그대로 코드로 옮기면 된다.

### 정리

메모리 사용량은 청크 크기로 고정하고 전체 진행 상황은 체크포인트로 외부화하는 것이 핵심이다. 이렇게 설계하면 응답이 아무리 크거나 페이지가 아무리 많아도 애플리케이션의 메모리 사용량과 장애 복구 가능성은 일정하게 유지된다.
