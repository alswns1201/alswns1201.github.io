# [Spring] 단위 테스트 vs 통합 테스트, 언제 무엇을 써야 할까? (feat. AssertJ)

안녕하세요, 개발자 여러분!  
지난 [단위 테스트 포스팅](https://www.google.com/url?sa=E&q=%EB%A7%81%ED%81%AC)에서는 "주인공 배우의 연기 리허설"에 비유하여, 테스트 대상을 철저히 고립시키고 가짜 객체(Mock)를 이용해 내부 로직의 흐름을 검증하는 방법에 대해 알아보았습니다.

오늘은 그 다음 단계인 **통합 테스트(Integration Test)**에 대해 이야기하며, 단위 테스트와 무엇이 다르고, 언제 사용해야 하는지, 그리고 어떻게 작성하는지 자세히 알아보겠습니다.

### 1\. 테스트의 피라미드: 단위 테스트와 통합 테스트의 위치

소프트웨어 테스트는 종종 '테스트 피라미드'에 비유됩니다.

  * **단위 테스트 (피라미드의 가장 넓은 기반)** : 가장 작고, 가장 빠르며, 가장 많이 작성해야 하는 테스트입니다. 각 부품(클래스, 메서드)이 설계도대로 정교하게 만들어졌는지를 검증합니다.
  * **통합 테스트 (피라미드의 중간)** : 여러 부품을 실제로 조립하여, 부품 간의 상호작용이 원활한지, 전체 시스템의 일부가 시나리오대로 잘 동작하는지를 검증합니다.
  * **E2E 테스트 (피라미드의 최상단)** : 실제 사용자의 관점에서 처음부터 끝까지 전체 애플리케이션의 흐름을 테스트합니다. 가장 느리고 비용이 많이 듭니다.



우리는 이 중 가장 중요한 기반인 **단위 테스트** 와 그 바로 위 단계인 **통합 테스트** 에 집중할 것입니다.

구분 | **단위 테스트 (Unit Test)** | **통합 테스트 (Integration Test)**  
---|---|---  
**목표** | "이 부품, 설계도대로 잘 만들어졌나?" | "부품들을 조립하니, 제대로 작동하나?"  
**환경** | 가짜(Mock) 객체로 주변 환경을 통제 | 실제 Spring 컨테이너, 실제 DB(인메모리)  
**검증 대상** | 클래스 내부의 논리적 흐름, 분기문 | 컴포넌트 간의 상호작용, DB 연동, 트랜잭션  
**속도** | 매우 빠름 | 느림  
**안정성** | 외부 요인 없음 (항상 동일한 결과) | DB 상태, 외부 설정 등에 영향받을 수 있음

### 2\. AssertJ와 import static의 비밀

테스트 코드를 작성하다 보면 assertThat이라는 구문을 자주 봅니다. 그런데 왜 import가 아닌 import static을 사용해야만 할까요?
    
    
    import static org.assertj.core.api.Assertions.assertThat;

  * **일반 import**: import java.util.List; 처럼 클래스 전체를 가져옵니다. 사용할 때는 List list = ... 처럼 클래스 이름을 붙여야 합니다.
  * **static import** : 클래스의 **정적(static) 멤버(메서드나 변수)만** 을 직접 가져옵니다. assertThat은 Assertions 클래스의 static 메서드이므로, static import를 하면 Assertions.assertThat() 대신 assertThat()으로 바로 사용할 수 있게 됩니다.



이것은 단순히 코드를 짧게 만드는 것을 넘어, 테스트 코드를 **"나는 ~라고 단언한다(assert that)"** 와 같은 자연스러운 문장처럼 읽히게 만들어 가독성을 크게 향상시켜 줍니다.

### 3\. 통합 테스트 작성하기: @SpringBootTest

이제 실제 회원가입 시나리오가 DB까지 올바르게 흘러가는지 검증하는 통합 테스트를 작성해 보겠습니다.

**핵심 어노테이션:**

  * @SpringBootTest: 실제 Spring Boot 애플리케이션을 실행할 때와 거의 동일하게 모든 Bean을 로드하여 테스트 환경을 구성합니다.
  * @Transactional: **테스트의 마법!** 각 테스트 메서드가 끝날 때마다 데이터베이스에 가해진 모든 변경 사항을 **자동으로 롤백(ROLLBACK)** 시켜줍니다. 덕분에 각 테스트는 항상 깨끗한 DB 상태에서 시작할 수 있습니다.



#### AuthService 통합 테스트 예시
    
    
    import org.springframework.beans.factory.annotation.Autowired;
    import org.springframework.boot.test.context.SpringBootTest;
    import org.springframework.transaction.annotation.Transactional;
    import static org.assertj.core.api.Assertions.assertThat;
    
    @SpringBootTest
    @Transactional // 각 테스트 후 DB 롤백을 위해 필수!
    class AuthServiceIntegrationTest {
    
        // 이제는 @Mock이 아닌, Spring 컨테이너가 생성한 '진짜' Bean들을 주입받습니다.
        @Autowired private AuthService authService;
        @Autowired private UserRepository userRepository;
        @Autowired private CrewRepository crewRepository;
        @Autowired private CrewMemberRepository crewMemberRepository;
        
        // 외부 API 호출이 필요한 OAuthProvider는 Mocking 처리하는 것이 좋습니다.
        // 여기서는 Service의 일부 로직만 테스트한다고 가정하겠습니다.
    
        @Test
        @DisplayName("신규 유저가 크루장으로 가입 시, 모든 데이터가 DB에 올바르게 저장된다.")
        void registerOrLoginUser_integration_test() {
            // given: 테스트에 필요한 데이터 준비
            // 외부 API를 통해 받아왔을 법한 가상의 프로필 정보
            OAuthUserProfile fakeProfile = new OAuthUserProfile();
            fakeProfile.setEmail("integration-test@example.com");
            fakeProfile.setProviderId("kakao-12345");
    
            // 프론트엔드에서 넘어왔을 법한 가상의 요청 DTO
            OAuthLoginRequestDto requestDto = new OAuthLoginRequestDto();
            requestDto.setName("통합테스터");
            requestDto.setCrewName("통합테스트크루");
            requestDto.setCrewMemberRole(CrewMemberRole.CREW_LEADER);
            // ...
    
            // when: 실제 서비스 로직 실행
            // 이 과정에서 User, Crew, CrewMember가 DB에 INSERT 됩니다.
            User resultUser = authService.registerOrLoginUser(fakeProfile, requestDto);
    
            // then: DB 상태를 직접 검증!
            // 1. User가 잘 저장되었는가?
            User foundUser = userRepository.findById(resultUser.getId()).orElseThrow();
            assertThat(foundUser.getEmail()).isEqualTo("integration-test@example.com");
    
            // 2. Crew가 잘 저장되었는가?
            Crew foundCrew = crewRepository.findByName("통합테스트크루").orElseThrow();
            assertThat(foundCrew).isNotNull();
    
            // 3. 둘을 연결하는 CrewMember가 잘 생성되었는가?
            //    (findByUserAndCrew는 Repository에 직접 정의해야 하는 쿼리 메서드입니다)
            CrewMember foundMember = crewMemberRepository.findByUserAndCrew(foundUser, foundCrew).orElseThrow();
            assertThat(foundMember.getRole()).isEqualTo(CrewMemberRole.CREW_LEADER);
            
            // 4. JPA 연관관계가 잘 설정되었는지, 크기는 1개인지 검증
            List<CrewMember> members = crewMemberRepository.findAllByCrew(foundCrew);
            assertThat(members).hasSize(1);
        }
    } // 이 메서드가 끝나는 순간, @Transactional에 의해 DB에 저장된 모든 데이터는 롤백됩니다.

### 4\. 언제 어떤 테스트를 써야 할까?

  * **단위 테스트를 기본으로 하세요.**
    * 새로운 클래스나 메서드를 만들면, 그 기능의 모든 경우의 수(성공, 실패, 예외 등)를 커버하는 단위 테스트를 먼저 작성하는 습관을 들이는 것이 좋습니다. 빠르고 안정적이며, 좋은 설계를 유도합니다.
  * **통합 테스트는 '연결점'을 검증할 때 사용하세요.**
    * **Controller - Service - Repository - DB** 의 전체 흐름이 중요한 **핵심 기능**(회원가입, 주문 등)
    * **@Transactional**의 동작이 중요한 복잡한 DB 작업
    * **외부 설정(.yml)**이나 **메시지 큐, 외부 API** 와의 연동이 올바르게 동작하는지 확인할 때



두 종류의 테스트는 서로를 보완합니다. 튼튼한 단위 테스트로 각 부품의 품질을 보장하고, 중요한 시나리오에 대한 통합 테스트로 조립 후의 안정성까지 확보한다면, 훨씬 더 견고하고 신뢰성 있는 소프트웨어를 만들 수 있을 것입니다.
