## Next.js와 Spring Boot로 똑똑하게 BFF 아키텍처 구축하기 (실전 로그인 예제)

혹시 프론트엔드에서 백엔드 API를 직접 호출하고 계신가요? 많은 프로젝트에서 일반적인 방식이지만, 프로젝트가 복잡해지면서 보안, 성능, 유지보수 측면에서 한계에 부딪히곤 합니다.

오늘은 이러한 한계를 극복하고, 더 안전하고 유연한 웹 애플리케이션을 만드는 **BFF(Backend for Frontend) 아키텍처** 에 대해 알아보고자 합니다. Next.js와 Spring Boot를 사용한 실제 로그인 처리 사례를 통해 BFF가 왜 강력한 패턴인지 직접 확인해 보세요.

### 1\. BFF (Backend for Frontend)가 뭔가요?

BFF는 단어 그대로 **프론트엔드를 위한 백엔드** 를 의미합니다.

전통적인 방식에서는 하나의 거대한 백엔드 API 서버가 웹, 모바일 등 모든 클라이언트의 요청을 처리했습니다. 하지만 BFF 패턴에서는 각 프론트엔드(웹, iOS, Android 등)가 자신만을 위한 전담 백엔드를 가집니다.

이 BFF는 **프론트엔드와 실제 백엔드(Microservices, Legacy API 등) 사이의 중개자** 역할을 합니다. 마치 클라이언트만을 위한 전담 매니저와 같죠.

### 2\. BFF, 언제 우리에게 필요할까요? (도입 고려 시나리오)

"좋은 건 알겠는데, 꼭 써야 하나?"라는 의문이 드실 겁니다. BFF는 모든 프로젝트의 정답은 아니지만, 다음과 같은 고민을 하고 있다면 도입을 적극적으로 고려해볼 만합니다.

#### 시나리오 1: 여러 API를 조합해야 하나의 화면을 그릴 수 있을 때

쇼핑몰의 '상품 상세 페이지'를 상상해 보세요. 이 페이지 하나를 완성하기 위해 우리는 아마도 여러 API를 호출해야 할 겁니다.

  * /products/{id}: 상품 기본 정보 API
  * /products/{id}/reviews: 상품 리뷰 목록 API
  * /users/{userId}/coupons: 현재 사용자가 가진 쿠폰 API
  * /recommendations?productId={id}: 연관 추천 상품 API



BFF가 없다면, 프론트엔드는 이 4개의 API를 각각 호출하고, 모든 응답이 올 때까지 로딩 상태를 관리하며, 받은 데이터를 클라이언트 측에서 조합해야 합니다. 이는 **네트워크 요청 횟수를 증가시키고 프론트엔드 로직을 복잡하게 만듭니다.**

**💡 BFF의 해결책** : 프론트엔드는 /view/product-detail/{id} 와 같이 BFF에 단 하나의 요청만 보냅니다. 그러면 BFF가 내부적으로 4개의 백엔드 API를 호출하여 데이터를 깔끔하게 조합하고, 화면에 꼭 필요한 최종 데이터만 한 번에 응답합니다.

#### 시나리오 2: 민감하거나 불필요한 데이터를 숨기고 싶을 때

사용자 정보를 가져오는 API가 있다고 가정해 봅시다. 백엔드는 보통 다음과 같이 사용자의 모든 정보를 담은 객체를 반환합니다.

Generated json
    
    
    // 백엔드 응답
    {
      "id": 123,
      "name": "홍길동",
      "email": "gildong@example.com",
      "profileImage": "url...",
      "grade": "VIP",
      "internalAdminNote": "2024년 블랙 프라이데이 이벤트 대상자" // <-- 클라이언트에 노출되면 안 되는 정보
    }

프론트엔드에서는 이름과 프로필 사진만 필요한데, 내부 관리용 메모(internalAdminNote) 같은 민감 정보까지 클라이언트로 전송되는 것은 보안상 위험합니다.

**💡 BFF의 해결책** : BFF가 중간에서 이 응답을 받아, 프론트엔드에 필요한 데이터만 선별하여 전달합니다.

Generated json
    
    
    // BFF가 프론트엔드에 전달하는 최종 응답
    {
      "name": "홍길동",
      "profileImage": "url..."
    }

#### 시나리오 3: 프론트엔드에서 처리하기 부담스러운 연산이 있을 때

수백 개의 상품 목록을 받아와서, 특정 조건(할인율, 재고 유무, 사용자 등급)에 따라 필터링하고 정렬하는 복잡한 로직이 필요하다고 해봅시다. 이 모든 연산을 사용자의 브라우저(클라이언트)에서 수행하면, 특히 저사양 디바이스에서는 성능 저하가 발생할 수 있습니다.

**💡 BFF의 해결책** : 데이터 필터링, 정렬, 계산과 같은 무거운 작업들을 성능 좋은 BFF 서버에 위임합니다. 프론트엔드는 그저 최종 결과물을 받아 화면에 그리기만 하면 되므로, 사용자 경험(UX)이 크게 향상됩니다.

#### 시나리오 4: 외부 Open API를 조합하여 새로운 기능을 만들 때

날씨 API와 지도 API를 연동하여 "현재 위치의 날씨를 지도에 표시하는" 기능을 만든다고 상상해 보세요. 이때 각 API의 키를 안전하게 관리해야 하고, 두 API의 응답을 조합하는 로직이 필요합니다.

**💡 BFF의 해결책** : BFF는 API 키를 process.env 같은 안전한 곳에 보관하고, 외부 API들과의 통신을 전담합니다. 프론트엔드는 키 노출 걱정 없이 BFF가 만들어준 새로운 API 엔드포인트(_API/weather-map?lat=...&lng=...)만 호출하면 됩니다.

### 3\. 실전 예제: Next.js(BFF)와 Spring Boot(백엔드)를 이용한 로그인 처리

이제 저희 프로젝트의 로그인 처리 사례를 통해 BFF 아키텍처가 어떻게 이 문제들을 해결하는지 살펴보겠습니다. 이 사례는 위에서 언급한 **시나리오 2(민감 정보 숨기기)**와 밀접한 관련이 있습니다. JWT 토큰은 그 자체로 민감 정보이기 때문이죠.

#### 아키텍처 흐름

**[사용자 브라우저] ↔︎ [Next.js 서버 (BFF)] ↔︎ [Spring Boot 서버 (백엔드)]**

  1. 사용자는 브라우저에서 로그인 버튼을 클릭하여 Next.js 서버(BFF)로 요청을 보냅니다.
  2. Next.js 서버는 요청을 받아 Spring Boot 서버(백엔드)로 다시 전달합니다.
  3. Spring Boot 서버는 로그인 로직을 처리하고, 순수한 **JWT 토큰 문자열** 을 응답합니다.
  4. Next.js 서버는 이 JWT 문자열을 받아, **httpOnly 쿠키로 포장**하여 최종적으로 브라우저에 응답합니다.



#### Step 1. Spring Boot 백엔드: 순수한 JWT 발급기

Spring Boot의 컨트롤러는 웹 환경을 신경 쓰지 않고, 오직 인증 로직 수행과 JWT 문자열 반환이라는 핵심 역할에만 집중합니다.

Generated java
    
    
    // Spring Boot: AuthController.java
    @RestController
    @RequestMapping("/api/auth")
    @RequiredArgsConstructor
    public class AuthController {
        // ... (이전과 동일) ...
        @PostMapping("/login/{provider}")
        public ResponseEntity<String> login(/*...*/) {
            String jwtToken = authService.createJwtToken(user);
            // [핵심] 오직 토큰 문자열만 응답 본문에 담아 반환
            return ResponseEntity.ok(jwtToken);
        }
    }

#### Step 2. Next.js Route Handler (BFF): 웹을 위한 똑똑한 중개자

Next.js의 Route Handler가 바로 BFF의 핵심입니다. 백엔드로부터 받은 순수한 데이터를 웹 환경에 맞게 "요리"합니다.

Generated typescript
    
    
    // Next.js: app/api/auth/login/[provider]/route.ts
    import { NextRequest, NextResponse } from 'next/server';
    
    export async function POST(request: NextRequest) {
      // ... (BFF 로직, 이전과 동일) ...
      // Spring Boot로부터 순수한 JWT 문자열을 받음
      const jwtToken = await backendResponse.text();
    
      // [핵심] BFF가 웹 브라우저를 위해 httpOnly 쿠키를 설정
      const response = NextResponse.json({ message: '로그인 성공' });
      response.cookies.set('accessToken', jwtToken, {
        httpOnly: true, // JavaScript에서 접근 불가 (XSS 방어)
        path: '/',
        secure: process.env.NODE_ENV === 'production',
        sameSite: 'strict',
      });
    
      return response;
    }

> **포인트** : 이 설계 덕분에 민감한 JWT가 JavaScript 코드에 노출될 위험이 원천 차단되었고, 백엔드는 웹 환경에 대한 의존성을 완전히 제거할 수 있었습니다.

### 결론: BFF, 성장을 위한 현명한 투자

BFF는 단순히 '한 단계를 더 거치는 것'이 아닙니다. **관심사의 분리(Separation of Concerns)**라는 소프트웨어 공학의 중요한 원칙을 지키는 현명한 설계입니다.

  * **Spring Boot 백엔드** 는 플랫폼에 독립적인 순수 비즈니스 로직에만 집중합니다.
  * **Next.js BFF** 는 웹이라는 특정 프론트엔드 환경에 최적화된 경험(보안, 데이터 포맷, 성능)을 제공하는 책임을 집니다.



만약 여러분의 프로젝트가 위에서 소개한 4가지 시나리오 중 하나라도 해당한다면, BFF 아키텍처 도입은 미래의 확장성과 유지보수를 위한 훌륭한 투자가 될 것입니다.

지금까지 BFF의 개념과 다양한 시나리오를 살펴보았습니다. 내용이 조금 길었나요? 여러분이 이 글을 덮고 나서도 딱 세 가지만 기억할 수 있도록 BFF의 핵심 가치를 요약해 드리겠습니다.

  * **하나, API의 통합과 가공 (Aggregation & Transformation)**
  * 프론트엔드가 필요로 하는 여러 API 요청을 BFF가 대신 처리하고, 하나의 최적화된 응답으로 묶어줍니다. 프론트엔드는 더 이상 데이터 조합을 위해 여러 번의 네트워크 통신을 하거나 복잡한 로직을 가질 필요가 없습니다.
  * **둘, 책임과 역할의 중앙화 (Centralization of Responsibilities)**
  * 데이터 가공, 외부 API 연동, 웹 환경에 특화된 처리(쿠키 등)와 같은 책임들이 모두 BFF라는 하나의 창구로 중앙화됩니다. 이는 백엔드는 순수 비즈니스 로직에, 프론트엔드는 사용자 경험(UX)에만 집중할 수 있는 이상적인 환경을 만들어 줍니다.
  * **셋, 보안 계층의 강화 (Enhanced Security Layer)**
  * API 키, 백엔드 서버 주소, 민감한 데이터 처리 로직 등 클라이언트에 노출되어서는 안 될 모든 것들을 BFF라는 안전한 성벽 뒤로 숨길 수 있습니다. BFF는 프론트엔드와 백엔드 사이의 든든한 보안 게이트웨이 역할을 수행합니다.
