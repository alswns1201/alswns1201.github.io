# BFF 환경에서 AccessToken을 쿠키에 담는 이유

JWT 기반 인증을 설계하다 보면 항상 나오는 질문이 있다.

> AccessToken과 RefreshToken이 있는데, 왜 어떤 서비스는 AccessToken을 쿠키(HttpOnly)에 넣고, 어떤 곳은 절대 쿠키에 안 넣을까?

이 글에서는 **일반적인 SPA 구조** 와 **BFF(Backend For Frontend) 구조** 를 기준으로, AccessToken 저장 방식의 차이를 보안 모델 관점에서 정리한다. 단순한 패턴 나열이 아니라, 왜 그렇게 설계하는지에 초점을 둔다.

* * *

## 1\. JWT 인증 구조 기본 정리

JWT 인증은 보통 다음 두 가지 토큰으로 구성된다.

  * **AccessToken**
    * API 접근 권한 증명
    * 짧은 만료 시간 (보통 5~15분)
  * **RefreshToken**
    * AccessToken 재발급 용도
    * 상대적으로 긴 만료 시간



이 둘의 역할은 SPA든, BFF든 동일하다. 차이는 **브라우저가 이 토큰을 직접 다루느냐** 에 있다.

* * *

## 2\. 일반적인 SPA + API 구조

### 2-1. 구조

[Browser SPA]

└─ Authorization: Bearer AccessToken

[Backend API]

이 구조에서는 프론트엔드가 API 서버와 직접 통신한다.

### 2-2. 토큰 저장 방식

  * AccessToken: **JS 메모리 (변수, 상태)**
  * RefreshToken: **HttpOnly 쿠키**



### 2-3. AccessToken을 쿠키에 넣지 않는 이유

#### (1) CSRF 공격 위험

쿠키는 브라우저가 **자동으로 전송** 한다. 만약 AccessToken이 쿠키에 있다면, 사용자가 악성 사이트에 접속했을 때 다음과 같은 요청이 가능해진다. 브라우저는 쿠키를 자동으로 포함하고, 서버는 이를 인증된 요청으로 오인할 수 있다.

> SPA 구조에서 AccessToken을 쿠키에 넣으면 CSRF 방어가 필수가 된다.

이 부담 때문에 AccessToken은 보통 헤더에 명시적으로 붙인다.

* * *

#### (2) 프론트엔드가 인증 흐름을 직접 제어해야 함

SPA 구조에서는 프론트엔드가 다음을 직접 책임진다.

  * Authorization 헤더 구성
  * 토큰 만료 감지
  * 401 발생 시 재발급 요청



이 흐름에서 AccessToken은 **프론트가 직접 다뤄야 하는 자산** 이기 때문에, 쿠키보다는 JS 메모리가 더 적합하다.

* * *

## 3\. BFF(Backend For Frontend) 구조

### 3-1. 구조

[Browser]

↓ (쿠키)

[BFF 서버]

↓ (Authorization 헤더)

[Backend API / Resource Server]

이 구조의 핵심은 명확하다.

> **브라우저는 더 이상 AccessToken을 사용하지 않는다.**

* * *

### 3-2. 역할 분리

  * 브라우저
    * 쿠키만 전송
    * 토큰의 존재를 모름
  * BFF
    * 쿠키에서 토큰 추출
    * 내부 API 호출 시 Authorization 헤더로 변환
    * 인증/인가의 책임 주체



토큰은 이제 **서버 자산** 이 된다.

* * *

## 4\. BFF에서 AccessToken을 쿠키에 담는 이유

### 4-1. XSS 위협 모델 변화

SPA 구조에서 XSS는 치명적이다.

  * JS 메모리에 있는 AccessToken 탈취 가능
  * 탈취 즉시 API 호출 가능



BFF 구조에서는:

  * AccessToken은 HttpOnly 쿠키
  * JS에서 접근 불가



즉,

> XSS로 AccessToken을 직접 탈취할 수 없다.

* * *

### 4-2. CSRF 방어를 서버에서 일관되게 처리 가능

중요한 포인트는 이것이다.

> BFF에서 AccessToken을 쿠키에 넣는다고 해서 CSRF 문제가 사라지는 것은 아니다.

다만,

  * SameSite 설정
  * CSRF Token 검증
  * Origin / Referer 검증



을 **BFF 한 곳에서만** 구현하면 된다.

다수의 API 서버를 각각 보호해야 하는 SPA 구조보다 훨씬 단순해진다.

* * *

### 4-3. 프론트엔드 단순화

프론트엔드는 이제 다음만 하면 된다.

fetch("/api/user")

  * Authorization 헤더 없음
  * 토큰 만료 처리 없음
  * 인증 로직 없음



보안과 인증 책임이 전부 서버로 이동한다.

* * *

## 5\. RefreshToken은 어디에 두는가?

BFF 구조에서는 보통 다음 중 하나를 선택한다.

토큰저장 위치

AccessToken | HttpOnly 쿠키  
---|---  
RefreshToken | HttpOnly 쿠키 (더 엄격한 옵션)  
  
또는 보안 요구사항이 높은 경우:

  * RefreshToken은 서버(DB/Redis)에만 저장
  * 쿠키에는 세션 식별자만 저장



금융, 마이데이터 계열 서비스에서 자주 쓰이는 방식이다.

* * *

## 6\. 자주 나오는 오해 정리

### ❌ "BFF니까 AccessToken을 쿠키에 넣으면 무조건 안전하다"

아니다.

  * CSRF 방어 없으면 그대로 취약
  * SameSite 설정 없으면 위험



* * *

### ❌ "쿠키에 넣으면 JWT를 쓰는 의미가 없다"

틀린 말이다.

  * JWT는 서버 확장성과 무상태성을 위한 것
  * 전달 매체가 쿠키냐 헤더냐는 별개의 문제



* * *

### ⭕ "BFF 환경에서는 AccessToken을 쿠키에 담는 것이 합리적이다"

\- **CSRF 방어를 전제로 할 때** 다.

* * *

## 7\. 결론

  * **순수 SPA + 다수 API 구조**
    * AccessToken: 메모리
    * RefreshToken: HttpOnly 쿠키
  * **BFF 구조**
    * AccessToken: HttpOnly 쿠키
    * RefreshToken: 서버 저장 또는 강화된 쿠키



BFF는 단순히 API 중계 서버가 아니다.

> 인증 책임을 브라우저에서 서버로 이동시키는 구조적 선택이다.

이 관점에서 보면, BFF 환경에서 AccessToken을 쿠키에 담는 설계는 트렌드가 아니라 **보안 모델에 따른 자연스러운 결과** 다.
