Claude Code를 실제 프로젝트에 붙이면서 정리한 내용이다.
"md 파일을 어떻게 구성했는가"(하네스)와 "대화를 어떻게 관리하는가"(컨텍스트) 두 가지로 나눠서 적는다.

## 왜 md 구성이 필요한가

AI 에이전트에게 코드를 맡기기 시작하면 금방 부딪히는 질문이 있다: 얘가 내가 원하는 대로
움직이게 하려면 뭘 줘야 하나? 프롬프트를 잘 쓰면 되는 거 아닌가?

경험상 프롬프트만으로는 오래 못 간다. 세션이 바뀌면 맥락이 날아가고, 같은 실수를 반복하고,
"이 정도는 당연히 지키겠지" 싶은 규칙(예: 엔티티에 Setter 쓰지 않기)을 매번 다시 알려줘야
한다. **하네스(Harness)**는 이 문제에 대한 답이다 — 프롬프트 한 번이 아니라, 에이전트가
매번 참조하는 "제어 구조"를 프로젝트에 미리 박아두는 접근.

> 하네스는 AI 에이전트를 억누르는 것이 아니라, 안전한 방식으로 작동하도록 설계된 제어 구조 전체를 말한다.

| 기능 | 하는 일 | 프로젝트에서 맡는 것 |
|---|---|---|
| **제어** | 허용된 범위 내에서만 행동하게 한다 | CLAUDE.md, rules, 권한(deny/ask), hooks |
| **감시** | 결과가 맞는지 바로 확인한다 | 테스트 기준선, hooks |
| **개선** | 실수를 기록하고 규칙으로 승격한다 | docs, rules 갱신 |

하네스는 처음부터 완성된 프레임워크로 등장한 게 아니다. 하시코프 창업자 미첼 해시모토도
에이전트가 실수할 때마다 규칙을 하나씩 추가하며 만들었다고 밝혔다. 즉 하네스는 "설계"라기보다
**"에이전트와 협업하며 쌓이는 축적물"**에 가깝다. 구성 예시는
[harness-100](https://github.com/revfactory/harness-100/tree/main/ko)에 100가지가 모여 있다.

## 실제 구성: `.claude/` 구조

실제 프로젝트에 적용한 구조는 이렇다.

```
{repo}/
├── CLAUDE.md         ← 진입점. 프로젝트 개요(@AGENTS.md), 파이프라인, 테스트 기준선, 브랜치/Jira 규칙
├── HOW_WE_WORK.md    ← (api만) 사람용 업무 방식 설명
├── .mcp.json         ← mcp-atlassian 서버 정의 (환경변수 참조만, 값 없음)
└── .claude/
    ├── settings.json ← 훅 등록, 권한 deny/ask
    ├── project.md    ← Jira 키/라벨, Confluence Space/페이지 ID
    ├── rules/        ← 코드 규칙 (자동 로드)
    ├── agents/       ← 서브에이전트 6개
    ├── hooks/        ← 안전장치 셸 스크립트 5개
    ├── docs/         ← GIT/JIRA/TEST 컨벤션, Spec·요구사항·기획서·API 인터페이스 템플릿, MCP_SETUP
    └── specs/        ← 작업 중 Spec (gitignore, 원본은 Jira 첨부. 앱은 디렉터리가 커밋되어 있음)
```

핵심은 **"항상 읽혀야 하는 것"과 "필요할 때만 꺼내 보는 것"을 나눈 것**이다.
문서 하나에 다 몰아넣으면 에이전트가 매 요청마다 관련 없는 규칙까지 전부 읽어야 하고,
규칙이 늘어날수록 신호 대 잡음비가 떨어진다.

### CLAUDE.md — 진입점 (제어)

Claude Code가 세션을 시작할 때 자동으로 읽는 파일이다. 여기에는 **모든 작업에 공통으로 필요한 것만** 둔다.

- 프로젝트 개요: `@AGENTS.md`처럼 `@경로`로 적으면 해당 파일 내용을 끌어와 읽는다.
  그래서 개요는 AGENTS.md에 두고 CLAUDE.md에서는 참조만 한다.
- 파이프라인, **테스트 기준선**(어떤 테스트가 통과해야 완료로 보는지)
- 브랜치·Jira 규칙

```markdown
# 프로젝트 컨텍스트
@AGENTS.md

## 아키텍처 원칙
- 레이어 구조: api → domain → infra
- 엔티티에 @Setter 사용 금지, 비즈니스 메서드로만 상태 변경

## 테스트 기준선
- 작업 완료 전 전체 테스트 통과 필수
```

"엔티티에 @Setter 금지" 같은 규칙을 명문화해두는 게 핵심이다. 사람 개발자에게는
암묵지로 통하는 컨벤션이, 에이전트에게는 문서화되지 않으면 존재하지 않는 규칙과 같다.

CLAUDE.md는 `/init`으로 초안을 만들 수도 있지만, 결국 직접 다듬어야 한다.
자동 생성 문서는 "왜 Setter를 금지하는지, 왜 레이어를 이렇게 나눴는지" 같은 이 프로젝트만의 규칙을 담지 못한다.

### HOW_WE_WORK.md — 사람용 문서

CLAUDE.md가 에이전트용이라면, 이건 **사람이 읽는** 업무 방식 설명이다.
에이전트용 규칙과 섞지 않고 따로 뒀다. (api 레포에만 있다)

### rules/ — 코드 규칙 (자동 로드)

`.claude/rules/` 안의 md 파일은 자동으로 읽힌다. 코드 컨벤션처럼 양이 많은 규칙을
CLAUDE.md에 다 적지 않고 파일별로 쪼개 두는 곳이다. CLAUDE.md는 짧게 유지된다.

### project.md / docs/ — 필요할 때만 참조

- `project.md`: Jira 프로젝트 키·라벨, Confluence Space·페이지 ID 같은 **식별자 모음**.
  Jira에 이슈를 만들거나 Confluence 문서를 찾을 때 에이전트가 여기서 값을 가져간다.
- `docs/`: GIT/JIRA/TEST 컨벤션과 Spec·요구사항·기획서·API 인터페이스 **템플릿**, MCP 설정 방법(MCP_SETUP).
  "Spec 써 줘"라고 하면 템플릿 형식대로 나오게 하는 용도다.

출력 형식을 템플릿으로 고정해 두는 이유는, 같은 내용이라도 매번 다른 형식으로 나오면
사람이 결과를 훑는 비용이 커지기 때문이다 — 하네스는 에이전트의 행동뿐 아니라 **결과물의 일관성**도 통제 대상이다.

### specs/ — 작업 중인 Spec

지금 진행 중인 작업의 Spec을 두는 곳이다. 원본은 Jira 첨부로 관리하고, api 쪽은 gitignore로 커밋하지 않는다.
(앱 레포는 디렉터리가 커밋되어 있다)

### agents/ — 서브에이전트 (역할 분리)

리뷰, 테스트 작성처럼 역할이 정해진 작업은 서브에이전트로 분리했다(6개).
서브에이전트는 **자기만의 컨텍스트**에서 돌기 때문에, 메인 대화에 관련 없는 규칙이나 탐색 과정이 쌓이지 않는다.

`.claude/agents/code-reviewer.md` 같은 파일에 frontmatter(이름·설명·쓸 수 있는 도구)와 지시를 적는다.

```markdown
---
name: code-reviewer
description: 변경된 코드를 리뷰할 때 사용
tools: Read, Grep, Glob
---

## 체크리스트
1. N+1 문제 발생 여부
2. 트랜잭션 범위가 적절한지
3. 예외 처리가 누락된 곳은 없는지
4. 엔티티에 @Setter가 사용됐는지

## 출력 형식
- [위험] 즉시 수정 필요
- [경고] 개선 권장
- [제안] 선택적 개선
```

리뷰 에이전트에는 읽기 도구만 줘서, 리뷰하다가 코드를 고쳐 버리는 일이 없게 한다.

### settings.json + hooks/ — 안전장치 (제어·감시)

md 파일은 "부탁"이라서 에이전트가 놓칠 수 있다. **반드시 지켜져야 하는 것**은 md가 아니라 설정으로 강제한다.

- **권한 deny/ask**: `settings.json`에서 특정 명령·파일 접근을 아예 막거나(deny), 실행 전에 사람에게 묻게(ask) 한다.
  예: `.env` 읽기 금지, `git push`는 확인 후 실행.

```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)"],
    "ask": ["Bash(git push:*)"]
  }
}
```

- **hooks**: 도구 실행 전후에 셸 스크립트를 자동으로 돌린다(5개). 예를 들어 위험한 명령을 실행하기 전에
  스크립트가 검사해서 막을 수 있다. 에이전트가 규칙을 "기억하는지"와 상관없이 항상 실행된다는 게 md와의 차이다.

### .mcp.json — 외부 도구 연결

Jira·Confluence에 접근하는 mcp-atlassian 서버를 정의한다. 레포에 커밋되는 파일이라
**토큰 값은 넣지 않고 환경변수 이름만** 참조한다. 각자 로컬 환경변수에 값을 넣는 방법은 `docs/MCP_SETUP`에 적어 뒀다.

## 대화(컨텍스트) 관리

md 구성이 "무엇을 알려 줄지"라면, 이쪽은 "대화가 길어질 때 어떻게 할지"다.
대화가 길어질수록 비용이 오르고 응답이 느려지고, 심하면 방금 전 지시를 까먹은 것 같은 반응이 나온다.

### 애초에 안 읽게 만들기

`node_modules`, 빌드 산출물, 대용량 로그처럼 코드 이해에 도움이 안 되면서 토큰만 잡아먹는 것은
위의 `settings.json` 권한 deny로 읽지 못하게 막아 둘 수 있다.
"다 읽고 나중에 요약한다"보다 "애초에 관련 없는 걸 안 읽게 한다"가 언제나 더 싸다.

### Skills — 반복 작업을 명령어로 굳히기

매번 같은 방식으로 시키는 작업이 있다면, 매번 프롬프트로 새로 설명하는 대신 skill로 만들어 두면
다음부터는 명령어 하나로 같은 맥락을 재사용할 수 있다. 필요한 조각만 불러 쓰게 만든다는 점에서 md 구성과 같은 원칙이다.

### /compact vs /clear — 압축이냐 초기화냐

대화가 길어지면 지금까지 나눈 모든 텍스트가 컨텍스트로 계속 쌓인다.

- **비용 증가**: 매 요청마다 이전 대화 전체가 같이 들어가므로 토큰 소모가 누적된다.
- **품질 저하**: 관련 없는 정보가 너무 많이 섞이면 방금 준 지시를 놓치거나 일관성이 떨어진다.

| 명령어 | 효과 | 적합한 상황 |
|---|---|---|
| `/compact` | 핵심 맥락(수정 사항, 결정된 로직 등)만 요약해서 남기고 나머지 정리 | 하던 작업을 계속 이어갈 때 |
| `/clear` | 컨텍스트를 완전히 삭제 | 아예 새로운 작업을 시작할 때 |

**판단 기준은 "다음 요청이 지금까지의 결정을 참조해야 하는가"다.** 참조해야 한다면
`/compact`로 압축해서 이어가고, 완전히 새로운 주제라면 `/clear`로 시작한다.
`/compact`를 새 주제에도 습관적으로 쓰면 이전 작업의 요약이 계속 남아서 오히려 방해가 된다.

`/clear`를 해도 CLAUDE.md·rules는 새 세션에서 다시 읽힌다. **세션이 바뀌어도 남아야 하는 건 대화가 아니라 md에 적어 둔다** — 그래서 md 구성이 먼저다.

**언제 compact 하나**: 응답이 느려지거나, 작업 성격이 바뀌는 전환점("A 버그는 다 고쳤고 이제 성능 최적화로 넘어간다")에
선제적으로 압축하는 편이, 컨텍스트가 꽉 찬 뒤에 압축하는 것보다 낫다.

## 정리

- 하네스는 처음부터 완벽하게 설계하는 게 아니라 **실수가 나올 때마다 규칙으로 승격시키는 축적 과정**이다.
- CLAUDE.md는 짧은 진입점으로 두고, 규칙은 rules/, 식별자·템플릿은 project.md·docs/, 역할별 작업은 agents/로 나눈다.
- 꼭 지켜야 하는 건 md가 아니라 **settings.json 권한과 hooks로 강제**한다.
- 대화는 "이어갈 것인가(`/compact`), 새로 시작할 것인가(`/clear`)"로 관리하고, 세션을 넘어 남겨야 할 건 md에 적는다.
