LLM을 붙인 사이드 프로젝트를 상용 서비스로 키워보려고 하면, 기술적으로 동작하는 것과
운영 가능한 것 사이의 간극이 빠르게 드러난다. 정리해본 고민들이다.

## 비용 구조부터 뒤집어봐야 한다

수익 구조를 짤 때 가장 먼저 봐야 하는 건 "비용(AWS + LLM 토큰)보다 수익이 커야
한다"는 당연한 명제다. 문제는 이게 프로토타입 단계에서는 잘 안 보인다는 것 —
사용자가 몇 명 없을 때는 토큰 비용이 무시할 만한 수준이지만, 사용자가 늘어나는
순간 LLM 호출 비용이 인프라 비용을 압도하기 시작한다. 로컬 서버로 어느 정도 성능
윤곽을 먼저 잡아보고, 이후 결정을 내리는 게 안전한 순서다.

현실적으로 고민해야 하는 항목들:

1. 서버 구성을 어느 시점에, 얼마나 투자해서 갖출 것인가
2. 어느 정도 윤곽이 잡힌 뒤에 로그인/보안 기능을 붙일 것인가 (처음부터 다 갖추려고
   하면 정작 핵심 기능 검증이 늦어진다)
3. 서비스 도메인에 따라 저작권 문제(예: 문제 은행, 콘텐츠 재가공)를 어떻게 확인하고
   처리할 것인가
4. 여러 비용이 누적되는 상황에서 수익성을 어떻게 만들어갈 것인가
5. 나중에 대용량 트래픽이나 장애가 났을 때의 대비(저작권 관련 데이터 로그 관리 포함)

## 오버엔지니어링을 알아채는 법

학습 목적으로 Kafka, ChromaDB, FastAPI embed-server를 구성해서 쓰고 있었는데,
돌아보면 이 선택 각각이 서비스의 실제 규모에 비해 과했다.

**Kafka**: 학습 목표가 우선이라 선택했지만, 실제로 해보니 일반 비동기 처리와 크게
다르지 않았다. 오히려 운영 관점에서는 Kafka가 메모리를 상당히 잡아먹는다는 게
체감됐다 — 실시간 통계나 대규모 데이터 유입을 처리해야 하는 요구가 없다면, Spring
Boot 내장 이벤트(`@Async`)나 단순 Job Queue로 충분하다. **"이 기술이 필요한 이유가
학습인가, 실제 요구사항인가"를 구분하는 게 오버엔지니어링을 알아채는 가장 직접적인
질문**이다. 학습 목적 자체는 나쁘지 않지만, 그걸 프로덕션 인프라 선택 기준과 섞으면
안 된다.

**ChromaDB + Embed-server**: 이 둘은 서버의 RAM을 직접 점유한다. 반면 MongoDB
Atlas 같은 SaaS는 연산과 저장을 클라우드가 대신 처리하고, 내 서버는 API 호출만
한다. 즉 로컬에 벡터 DB와 임베딩 서버를 직접 올리는 선택은 "인프라를 내가 다
통제한다"는 장점과 "내 서버 리소스를 계속 깎아먹는다"는 비용을 맞바꾸는 것이다.

```
기존: [React] ↔ [Spring Boot] ↔ [MariaDB + Kafka + ChromaDB + Embed-server]  (서버 과부하)
변경: [React] ↔ [Spring Boot] ↔ [MariaDB] + [MongoDB Atlas(외부)] + [LLM API(외부)]
```

이렇게 바꾸면 내 EC2는 Spring Boot와 React만 돌리면 되므로, 프리티어(RAM 1GB) 수준
에서도 훨씬 안정적으로 운영할 수 있다.

## 초기 단계에서 내린 결론

- **Kafka** 대신 Spring 내장 이벤트나 Redis로 구조를 단순화한다 — 별도 서버 자원을
  점유하는 컴포넌트를 실제 처리량이 필요해지기 전까지는 들이지 않는다.
- **MongoDB Atlas 같은 멀티모델 SaaS**로 벡터 데이터와 일반 데이터를 한곳에 모아
  관리 포인트를 줄인다.
- **임베딩은 로컬 모델 대신 OpenAI/Voyage AI 같은 외부 API**를 써서 서버 리소스
  확보와 모델 관리 부담을 함께 던다.
- 복잡한 인프라 컴포넌트를 SaaS로 밀어내면, 초기 단계에서는 EC2 프리티어로도
  운영 가능한 수준까지 비용을 낮출 수 있다.

## 이 경험에서 남는 원칙

기술 선택의 이유가 "배우고 싶어서"였다면, 그 선택이 서비스가 커지는 시점에 다시
검토 대상이 되는 건 자연스러운 일이다. 문제는 그 검토를 실제로 하느냐다 — 학습
목적으로 들인 컴포넌트를 프로덕션까지 관성적으로 끌고 가면, 정작 신경 써야 할
비용(서버비, LLM 토큰비)과 무관한 곳에서 인프라 복잡도만 쌓인다. "이 컴포넌트가
지금 이 서비스 규모에 필요한가"를 주기적으로 다시 묻는 게, 처음부터 완벽하게
설계하려는 시도보다 실용적이었다.
