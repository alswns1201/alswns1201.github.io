Claude API를 처음 쓰면 대부분 `/v1/messages` 하나로 시작한다. 하지만 실제 프로덕션
사용 사례로 가면 토큰 계산, 대량 처리, 파일 재사용, 에이전트 구성처럼 `/v1/messages`
바깥의 엔드포인트가 필요해지는 지점이 온다. 여기서는 GA(정식 출시) 엔드포인트와
베타 엔드포인트를 구분해서, 각각이 왜 있는지를 정리한다.

## GA 엔드포인트: 기본 흐름

| 엔드포인트 | 메서드 | 용도 |
|---|---|---|
| `/v1/messages` | POST | Claude 모델에 메시지를 보내고 응답을 받는 핵심 API |
| `/v1/messages/batches` | POST | 여러 요청을 비동기로 처리, 비용 절감·처리량 최적화 |
| `/v1/messages/count_tokens` | POST | 요청 전에 토큰 수를 계산해 비용/응답 길이 예측 |
| `/v1/models` | GET | 사용 가능한 모델 목록 및 메타 정보 조회 |

기본 흐름은 단순하다: `/v1/messages`를 호출해서 prompt를 보내고 응답을 받는다.
여기서 비용/성능이 문제가 되기 시작하면 두 엔드포인트가 추가로 들어온다 —
`count_tokens`로 요청을 보내기 전에 미리 토큰 수를 계산해 비용을 예측하고,
`batches`로 여러 요청을 한 번에 비동기 처리해서 처리량을 늘린다. 실시간 응답이
필요 없는 대량 작업(예: 문서 일괄 요약)이라면 `batches`를 쓰는 게 개별 호출보다
비용 효율이 높다.

## 베타 엔드포인트: `anthropic-beta` 헤더가 왜 필요한가

베타 엔드포인트는 `anthropic-beta` 헤더로 명시적으로 옵트인해야 호출할 수 있다.
이 구조 자체가 의도적인 설계다 — 아직 API 스펙이 확정되지 않은 기능을, 알고
쓰겠다고 명시한 클라이언트에게만 노출하는 것이다. 베타 기능을 프로덕션에 그대로
박아넣으면, 스펙이 GA로 넘어가는 과정에서 필드명이나 동작이 바뀔 때 별도 공지
없이도 코드가 깨질 수 있다는 리스크를 감수하는 셈이다 — 베타 기능을 쓸 때는
이 위험을 인지하고, 버전 헤더(예: `files-api-2025-04-14`)를 고정해서 예기치
않은 변경에 노출되는 범위를 최소화하는 게 안전하다.

### Files API

파일(PDF, 이미지 등)을 한 번 업로드해두고 여러 API 호출에서 재사용하는 기능이다.
매 요청마다 이미지를 base64로 인코딩해서 통째로 보내는 대신, 업로드된 파일 ID만
참조하면 된다 — 반복적으로 같은 문서를 참조하는 워크플로(같은 PDF에 대해 여러
질문을 연달아 던지는 경우)에서 페이로드 크기와 응답 속도 양쪽에 이득이 있다.

### Skills API

Agent에 붙이는 재사용 가능한 지식 단위다. tools가 "무엇을 할 수 있는가(행동)"를
정의한다면, Skills는 "무엇을 알아야 하는가(지식/컨텍스트)"에 가깝다. 필요할 때만
컨텍스트를 주입하는 구조(progressive disclosure)로 동작한다는 게 핵심이다 —
모든 지식을 매 요청 프롬프트에 다 밀어넣는 대신, 필요한 순간에만 관련 지식
캡슐을 불러오는 방식이라 프롬프트가 불필요하게 비대해지는 걸 막는다.

### Agents / Sessions / Environments API

세 API는 하나의 계층을 이룬다.

- **Agents**: model, system prompt, tools, MCP, skills 등을 하나로 묶은 "설정"
  단위. ID로 재사용 가능하고, 수정하면 버전(v1, v2…)이 자동으로 올라간다 —
  설정 변경 이력을 코드처럼 관리할 수 있다는 뜻이다.
- **Environments**: Session이 실행될 컨테이너 템플릿(파일 시스템, 실행 환경)을
  정의한다.
- **Sessions**: Agent를 실제로 실행하는 stateful 인스턴스. 대화 히스토리를 자동
  유지하며, `idle → running → terminated` 상태를 오간다.

이 구조를 쓰는 이유는 "정적인 설정(Agent)"과 "동적인 실행 인스턴스(Session)"를
분리하기 위해서다. 같은 Agent 정의로 여러 Session을 동시에 띄울 수 있고, Agent
설정을 바꿔도 이미 실행 중인 Session에는 영향을 주지 않는 식의 격리가 가능해진다.

## 언제 어떤 걸 쓰는가

- **단순 대화**: `/v1/messages`로 충분하다. 여기서 시작하지 않을 이유가 없다.
- **같은 파일을 반복 참조**: Files API를 도입하면 비용과 응답 속도 모두 이득이다.
- **복잡한 에이전트 시스템**(설정 재사용, 실행 상태 추적이 필요한 경우): Agents +
  Sessions 구조가 필요해진다. 단순 대화 수준에서 이 구조를 미리 도입하는 건
  오히려 불필요한 복잡도를 더하는 선택이다 — 상태 관리와 버전 관리가 실제로
  필요해지는 시점부터 옮겨가는 게 맞다.

정리하면, GA 엔드포인트는 "메시지를 주고받는 기본 계약"이고 베타 엔드포인트들은
그 위에 재사용성(Files, Skills)과 상태 관리(Agents, Sessions, Environments)를
얹는 계층이다. 프로젝트 규모가 커질수록 필요해지는 순서도 대략 이 순서를 따른다.
