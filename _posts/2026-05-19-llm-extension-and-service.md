## 프롬프트 엔지니어링: 언제 프롬프트로 풀리고, 언제 안 풀리는가

프롬프트 엔지니어링은 결국 "모델이 원하는 결과를 안정적으로 내도록 입력을
설계하는 기술"이다. [OpenAI의 공식 가이드](https://developers.openai.com/api/docs/guides/prompt-engineering)를
비롯한 여러 자료가 공통적으로 강조하는 원칙들을 정리하면서, 이게 정확히 언제
통하고 언제 안 통하는지까지 짚어본다.

### 기본 구조: Task / Context / Output

프롬프트를 세 부분으로 나눠서 생각하면 설계가 쉬워진다.

- **Task**: 무엇을 할지 명확히 정의
- **Context**: 필요한 배경 정보와 데이터 제공
- **Output**: 결과 형식, 길이, 스타일을 명확히 지정

### 왜 지시를 앞에, 데이터를 뒤에 두라고 하는가

"지시는 앞에, 데이터는 뒤에 배치한다"는 조언이 그냥 관례처럼 들릴 수 있는데,
실제로는 트랜스포머 기반 모델이 긴 입력을 처리할 때 위치에 따라 주의를 기울이는
정도가 균일하지 않다는 것과 관련이 있다. 지시사항이 데이터 한가운데 묻혀 있으면
모델이 그걸 놓치거나 덜 반영할 가능성이 커진다. 그래서 "무엇을 할지"를 먼저
명확히 던져놓고 그다음에 처리할 데이터를 주는 순서가 실제로 결과 안정성에
영향을 준다.

### 출력 형식을 지정해야 하는 진짜 이유

"출력 형식을 지정해야 일관성과 파싱이 가능하다"는 원칙은 단순 스타일 문제가
아니라 **엔지니어링 문제**다. LLM 응답을 후속 로직에서 프로그래밍적으로
처리하려면(JSON 파싱, 특정 필드 추출 등) 출력 형식이 매번 달라지면 그 자체가
장애 지점이 된다. 그래서 실무에서는 자연어 설명 대신 JSON 스키마를 명시하거나,
few-shot 예시로 정확한 출력 포맷을 직접 보여주는 방식을 함께 쓴다 — "이렇게
써줘"라는 설명보다 "이런 예시처럼 써줘"가 형식 일관성에서 훨씬 안정적이다.

### 파라미터: temperature, max_tokens, stop

- **temperature**: 결과의 창의성/랜덤성을 조절한다. 형식이 고정된 데이터 추출
  작업(예: 로그에서 값 뽑기)은 낮게, 아이디어 브레인스토밍처럼 다양성이
  필요한 작업은 높게 잡는 식으로 작업 성격에 맞춰야 한다.
- **max_tokens**: 출력 길이를 제한한다. 너무 낮으면 응답이 중간에 잘려서
  JSON이 깨지는 등의 문제가 생길 수 있다.
- **stop**: 특정 문자열이 나오면 생성을 중단시킨다. 구조화된 출력에서 다음
  섹션이 시작되기 전에 끊고 싶을 때 유용하다.

### 개발자 관점으로 옮기면 이해가 빠르다

프롬프트를 코드에 빗대면 이렇다: 프롬프트는 **함수 시그니처**, context는
**입력 인자**, output format 지정은 **반환 타입/스키마**, few-shot 예시는
**테스트 케이스**에 대응한다. 이 비유가 유용한 이유는, "테스트 케이스 없이
함수를 짜지 않는다"는 감각을 프롬프트에도 그대로 적용할 수 있어서다 — 프롬프트를
"한 번 잘 써서 끝내는 것"이 아니라, 실제 입력 샘플들을 모아 반복적으로 검증하고
개선하는 과정으로 다뤄야 한다는 뜻이다. 모델이 확률 기반으로 동작하는 이상
프롬프트 하나만으로 100% 안정된 출력을 보장할 수 없고, 결과를 안정화하려면
구조(형식 지정) + 제약(명확한 규칙) + 예시(few-shot)가 함께 필요하다.

### 프롬프트로 안 풀리는 경우: RAG와 파인튜닝은 다른 문제를 푼다

프롬프트 엔지니어링을 아무리 정교하게 해도 못 푸는 문제 두 가지가 있다.

- **모델이 애초에 모르는 사실**을 물어보는 경우 — 아무리 프롬프트를 잘 짜도
  모델 학습 데이터에 없던 정보(사내 문서, 최신 뉴스)는 지어낼 뿐이다. 이건
  프롬프트가 아니라 검색으로 자료를 넣어주는 RAG(Retrieval-Augmented
  Generation)가 푸는 문제다.
- **모델의 기본 행동/톤/판단 기준 자체**를 바꾸고 싶은 경우 — 매 요청마다
  같은 규칙을 프롬프트로 반복 주입하는 대신 모델 자체를 그 방향으로 조정하고
  싶다면 파인튜닝의 영역이다.

즉 세 가지는 서로 대체재가 아니라 **각각 다른 실패 원인을 겨냥한 도구**다:
"모델이 형식/범위를 못 잡는다" → 프롬프트, "모델이 사실을 모른다" → RAG,
"모델의 기본 동작 자체가 안 맞는다" → 파인튜닝. 문제를 이 세 축으로 먼저
분류하는 게, 무작정 프롬프트를 더 길게 쓰는 것보다 훨씬 빠른 해법으로 이어진다.

### 정리

- 지시는 앞에, 데이터는 뒤에 — 모델의 위치별 주의력 편향을 고려한 배치다.
- 출력 형식 지정은 스타일이 아니라 후속 파싱 안정성을 위한 엔지니어링이다.
- 프롬프트는 한 번 쓰고 끝내는 게 아니라 테스트 케이스처럼 반복 검증해야 한다.
- "모델이 형식을 못 잡는다"는 프롬프트로, "모델이 사실을 모른다"는 RAG로,
  "모델의 기본 행동 자체가 안 맞는다"는 파인튜닝으로 — 증상에 맞는 도구를
  먼저 구분하는 게 순서다.

## Claude API 엔드포인트 정리: /v1/messages 너머의 것들

Claude API를 처음 쓰면 대부분 `/v1/messages` 하나로 시작한다. 하지만 실제 프로덕션
사용 사례로 가면 토큰 계산, 대량 처리, 파일 재사용, 에이전트 구성처럼 `/v1/messages`
바깥의 엔드포인트가 필요해지는 지점이 온다. 여기서는 GA(정식 출시) 엔드포인트와
베타 엔드포인트를 구분해서, 각각이 왜 있는지를 정리한다.

### GA 엔드포인트: 기본 흐름

| 엔드포인트 | 메서드 | 용도 |
|---|---|---|
| `/v1/messages` | POST | Claude 모델에 메시지를 보내고 응답을 받는 핵심 API |
| `/v1/messages/batches` | POST | 여러 요청을 비동기로 처리, 비용 절감·처리량 최적화 |
| `/v1/messages/count_tokens` | POST | 요청 전에 토큰 수를 계산해 비용/응답 길이 예측 |
| `/v1/models` | GET | 사용 가능한 모델 목록 및 메타 정보 조회 |

기본 흐름은 단순하다: `/v1/messages`를 호출해서 prompt를 보내고 응답을 받는다.
여기서 비용/성능이 문제가 되기 시작하면 두 엔드포인트가 추가로 들어온다 —
`count_tokens`로 요청을 보내기 전에 미리 토큰 수를 계산해 비용을 예측하고,
`batches`로 여러 요청을 한 번에 비동기 처리해서 처리량을 늘린다. 실시간 응답이
필요 없는 대량 작업(예: 문서 일괄 요약)이라면 `batches`를 쓰는 게 개별 호출보다
비용 효율이 높다.

### 베타 엔드포인트: `anthropic-beta` 헤더가 왜 필요한가

베타 엔드포인트는 `anthropic-beta` 헤더로 명시적으로 옵트인해야 호출할 수 있다.
이 구조 자체가 의도적인 설계다 — 아직 API 스펙이 확정되지 않은 기능을, 알고
쓰겠다고 명시한 클라이언트에게만 노출하는 것이다. 베타 기능을 프로덕션에 그대로
박아넣으면, 스펙이 GA로 넘어가는 과정에서 필드명이나 동작이 바뀔 때 별도 공지
없이도 코드가 깨질 수 있다는 리스크를 감수하는 셈이다 — 베타 기능을 쓸 때는
이 위험을 인지하고, 버전 헤더(예: `files-api-2025-04-14`)를 고정해서 예기치
않은 변경에 노출되는 범위를 최소화하는 게 안전하다.

#### Files API

파일(PDF, 이미지 등)을 한 번 업로드해두고 여러 API 호출에서 재사용하는 기능이다.
매 요청마다 이미지를 base64로 인코딩해서 통째로 보내는 대신, 업로드된 파일 ID만
참조하면 된다 — 반복적으로 같은 문서를 참조하는 워크플로(같은 PDF에 대해 여러
질문을 연달아 던지는 경우)에서 페이로드 크기와 응답 속도 양쪽에 이득이 있다.

#### Skills API

Agent에 붙이는 재사용 가능한 지식 단위다. tools가 "무엇을 할 수 있는가(행동)"를
정의한다면, Skills는 "무엇을 알아야 하는가(지식/컨텍스트)"에 가깝다. 필요할 때만
컨텍스트를 주입하는 구조(progressive disclosure)로 동작한다는 게 핵심이다 —
모든 지식을 매 요청 프롬프트에 다 밀어넣는 대신, 필요한 순간에만 관련 지식
캡슐을 불러오는 방식이라 프롬프트가 불필요하게 비대해지는 걸 막는다.

#### Agents / Sessions / Environments API

세 API는 하나의 계층을 이룬다.

- **Agents**: model, system prompt, tools, MCP, skills 등을 하나로 묶은 "설정"
  단위. ID로 재사용 가능하고, 수정하면 버전(v1, v2…)이 자동으로 올라간다 —
  설정 변경 이력을 코드처럼 관리할 수 있다는 뜻이다.
- **Environments**: Session이 실행될 컨테이너 템플릿(파일 시스템, 실행 환경)을
  정의한다.
- **Sessions**: Agent를 실제로 실행하는 stateful 인스턴스. 대화 히스토리를 자동
  유지하며, `idle → running → terminated` 상태를 오간다.

이 구조를 쓰는 이유는 "정적인 설정(Agent)"과 "동적인 실행 인스턴스(Session)"를
분리하기 위해서다. 같은 Agent 정의로 여러 Session을 동시에 띄울 수 있고, Agent
설정을 바꿔도 이미 실행 중인 Session에는 영향을 주지 않는 식의 격리가 가능해진다.

### 언제 어떤 걸 쓰는가

- **단순 대화**: `/v1/messages`로 충분하다. 여기서 시작하지 않을 이유가 없다.
- **같은 파일을 반복 참조**: Files API를 도입하면 비용과 응답 속도 모두 이득이다.
- **복잡한 에이전트 시스템**(설정 재사용, 실행 상태 추적이 필요한 경우): Agents +
  Sessions 구조가 필요해진다. 단순 대화 수준에서 이 구조를 미리 도입하는 건
  오히려 불필요한 복잡도를 더하는 선택이다 — 상태 관리와 버전 관리가 실제로
  필요해지는 시점부터 옮겨가는 게 맞다.

정리하면, GA 엔드포인트는 "메시지를 주고받는 기본 계약"이고 베타 엔드포인트들은
그 위에 재사용성(Files, Skills)과 상태 관리(Agents, Sessions, Environments)를
얹는 계층이다. 프로젝트 규모가 커질수록 필요해지는 순서도 대략 이 순서를 따른다.

## Skill Prompt, Tool Use, MCP — LLM을 확장하는 세 가지 방식은 뭐가 다른가

LLM을 실제 서비스에 붙이다 보면 세 가지 개념이 계속 등장한다. Skill Prompt, Tool
Use, MCP. 이름도 쓰임도 비슷해 보이지만, "누가 무엇을 실행하는가"라는 축으로
보면 완전히 다른 층위에 있다.

### 1. Skill Prompt — 행동 규칙을 텍스트로 주입한다

`.md` 파일에 행동 규칙이나 도메인 지식을 적어두고, 그걸 System/User Prompt에
그대로 삽입하는 방식이다.

```
.md 파일 로드 → System/User Prompt에 삽입 → LLM이 읽고 규칙에 따라 응답
```

```java
@Value("classpath:skills/math-parser.md")
private Resource mathSkillResource;

// .md 파일을 읽어서 프롬프트에 삽입
this.skillPrompt = StreamUtils.copyToString(
    mathSkillResource.getInputStream(), StandardCharsets.UTF_8
);

MessageCreateParams.builder()
    .addUserMessage(skillPrompt + "\n\n" + userInput)
    .build();
```

LLM이 외부의 무언가를 호출하는 게 아니다 — 프롬프트에 담긴 지침을 읽고 **스스로
판단해서 따르는** 것뿐이다. 그래서 한계도 명확하다: LLM이 지침을 지키려고
노력하지만 보장은 없다. 문제가 복잡해질수록 형식이 흔들리거나 필드를 빠뜨릴 수
있다. 결과물이 확률적이라는 뜻이다. 분석 방법이나 답변 스타일, 도메인 규칙처럼
"어떻게 생각할지"를 지정할 때 쓴다.

### 2. Tool Use — LLM이 함수 호출을 "요청"한다

Tool Use(Function Calling)는 LLM이 외부 함수를 직접 실행하는 게 아니라, 실행을
**요청**하는 메커니즘이다. 개발자가 함수 이름·설명·입력 스키마를 JSON으로
정의해두면, LLM은 대화 중 필요하다고 판단할 때 그 함수를 이 인자로 호출해달라는
신호만 보낸다. 실제 실행은 개발자 코드가 맡는다.

```
도구 정의 (JSON 스키마)
    → LLM이 "이 도구 써야겠다" 판단
    → tool_use 블록 응답
    → 개발자 코드가 실제 API 호출
    → 결과를 LLM에 다시 전달
    → 최종 응답 생성
```

```java
// 1. 도구 정의
Tool parseTool = Tool.builder()
    .name("parse_math_problems")
    .description("이미지에서 수학 문제를 추출")
    .inputSchema(/* JSON 스키마 */)
    .build();

// 2. LLM에 도구와 함께 요청
MessageCreateParams.builder()
    .tools(List.of(ToolUnion.ofTool(parseTool)))
    .toolToolChoice("parse_math_problems") // 반드시 이 도구 사용 강제
    .build();

// 3. LLM 응답에서 tool_use 블록 꺼내서 개발자가 처리
response.content().stream()
    .flatMap(block -> block.toolUse().stream())
    .findFirst()
    .map(toolUse -> {
        // 여기서 실제 로직 실행
    });
```

Skill Prompt와 결정적으로 다른 지점은 **강제 주체**다. Skill Prompt는 LLM이
확률적으로 형식을 지키려 노력하는 반면, Tool Use는 스키마를 API 레벨에서
강제한다.

| | Skill Prompt로 형식 지정 | Tool Use 스키마 강제 |
|---|---|---|
| 강제 주체 | LLM (확률적) | API 레벨 (결정적) |
| 앞뒤 텍스트 | 붙을 수 있음 | 절대 안 붙음 |
| 필드 누락 | 가능 | required면 불가 |
| 파싱 코드 | try/catch 필수 | 바로 역직렬화 가능 |

구조화된 JSON 출력을 반드시 보장해야 하거나, 외부 API(날씨, 계산기, DB 등)를
LLM 판단에 따라 호출해야 하고, 그 호출 로직을 개발자가 직접 제어하고 싶을 때
쓴다.

### 3. MCP — 호출 로직 자체를 서버가 대신 구현해둔다

MCP(Model Context Protocol)는 Anthropic이 만든 표준 프로토콜로, LLM과 외부
서비스를 연결하는 방식을 규격화한 것이다. Tool Use와 MCP의 차이는 "중간 코드를
누가 짜는가"에 있다.

```
Tool Use:
LLM → tool_use 신호 → 개발자 코드 → 외부 API

MCP:
LLM → MCP 서버 → 외부 API
      (이미 구현된 서버)
```

Tool Use는 외부 API를 호출하는 중간 코드를 개발자가 직접 작성해야 한다. MCP는
그 중간 코드가 MCP 서버 안에 이미 구현되어 있어서, 개발자는 서버에 연결만 하면
된다.

```
MCP 서버 URL 등록 (한 번만)
    → LLM이 대화 중 필요하다고 판단
    → MCP 서버에 직접 요청
    → MCP 서버가 외부 API 호출 및 결과 반환
    → LLM이 결과로 최종 응답 생성
```

```
// 연결만 해두면 끝
mcp_servers: [
    { type: "url", url: "https://gmailmcp.googleapis.com/mcp/v1", name: "gmail-mcp" },
    { type: "url", url: "https://drivemcp.googleapis.com/mcp/v1", name: "drive-mcp" }
]
// LLM이 필요하면 알아서 Gmail, Drive 호출
```

Gmail, Google Drive, Slack처럼 이미 MCP 서버가 존재하는 서비스를 연동할 때,
호출 타이밍과 로직을 LLM에게 완전히 위임하고 싶을 때, 여러 서비스를 하나의
표준 방식으로 연결하고 싶을 때 쓴다.

### 세 가지 비교

| | Skill Prompt | Tool Use | MCP |
|---|---|---|---|
| 역할 | 행동 규칙 주입 | 함수 호출 메커니즘 | 외부 서비스 연결 표준 |
| 실행 주체 | LLM (추론) | 개발자 코드 | MCP 서버 |
| 호출 코드 작성 | 불필요 | 개발자가 직접 작성 | MCP 서버가 담당 |
| 결과 보장 | 확률적 | 결정적 (스키마 강제 시) | 결정적 |
| 재사용성 | 프롬프트 복사 | 앱마다 재구현 | 서버 하나로 공유 |

### 대립이 아니라 계층이다

셋은 서로 대체하는 관계가 아니라, 계층적으로 함께 쓰인다.

```
Skill Prompt  →  "수학 문제를 이렇게 분석해"       (행동 지침)
Tool Use      →  분석 결과를 JSON으로 반드시 반환   (출력 보장)
MCP           →  필요하면 외부 DB에 저장            (서비스 연결)
```

각각의 역할이 명확히 분리되어 있어서, "어떻게 생각할지"는 Skill Prompt가,
"결과를 어떻게 확정할지"는 Tool Use가, "외부 세계와 어떻게 연결할지"는 MCP가
맡는다. 셋 중 하나만 골라야 하는 문제가 아니라, 어떤 층위의 문제를 풀고
있는지를 먼저 구분하는 게 먼저다.

## LLM 사용 서비스, 실제로 상용화하려면 고려해야 하는 것들

LLM을 붙인 사이드 프로젝트를 상용 서비스로 키워보려고 하면, 기술적으로 동작하는 것과
운영 가능한 것 사이의 간극이 빠르게 드러난다. 정리해본 고민들이다.

### 비용 구조부터 뒤집어봐야 한다

수익 구조를 짤 때 가장 먼저 봐야 하는 건 "비용(AWS + LLM 토큰)보다 수익이 커야
한다"는 당연한 명제다. 문제는 이게 프로토타입 단계에서는 잘 안 보인다는 것 —
사용자가 몇 명 없을 때는 토큰 비용이 무시할 만한 수준이지만, 사용자가 늘어나는
순간 LLM 호출 비용이 인프라 비용을 압도하기 시작한다. 로컬 서버로 어느 정도 성능
윤곽을 먼저 잡아보고, 이후 결정을 내리는 게 안전한 순서다.

현실적으로 고민해야 하는 항목들:

1. 서버 구성을 어느 시점에, 얼마나 투자해서 갖출 것인가
2. 어느 정도 윤곽이 잡힌 뒤에 로그인/보안 기능을 붙일 것인가 (처음부터 다 갖추려고
   하면 정작 핵심 기능 검증이 늦어진다)
3. 서비스 도메인에 따라 저작권 문제(예: 문제 은행, 콘텐츠 재가공)를 어떻게 확인하고
   처리할 것인가
4. 여러 비용이 누적되는 상황에서 수익성을 어떻게 만들어갈 것인가
5. 나중에 대용량 트래픽이나 장애가 났을 때의 대비(저작권 관련 데이터 로그 관리 포함)

### 오버엔지니어링을 알아채는 법

학습 목적으로 Kafka, ChromaDB, FastAPI embed-server를 구성해서 쓰고 있었는데,
돌아보면 이 선택 각각이 서비스의 실제 규모에 비해 과했다.

**Kafka**: 학습 목표가 우선이라 선택했지만, 실제로 해보니 일반 비동기 처리와 크게
다르지 않았다. 오히려 운영 관점에서는 Kafka가 메모리를 상당히 잡아먹는다는 게
체감됐다 — 실시간 통계나 대규모 데이터 유입을 처리해야 하는 요구가 없다면, Spring
Boot 내장 이벤트(`@Async`)나 단순 Job Queue로 충분하다. **"이 기술이 필요한 이유가
학습인가, 실제 요구사항인가"를 구분하는 게 오버엔지니어링을 알아채는 가장 직접적인
질문**이다. 학습 목적 자체는 나쁘지 않지만, 그걸 프로덕션 인프라 선택 기준과 섞으면
안 된다.

**ChromaDB + Embed-server**: 이 둘은 서버의 RAM을 직접 점유한다. 반면 MongoDB
Atlas 같은 SaaS는 연산과 저장을 클라우드가 대신 처리하고, 내 서버는 API 호출만
한다. 즉 로컬에 벡터 DB와 임베딩 서버를 직접 올리는 선택은 "인프라를 내가 다
통제한다"는 장점과 "내 서버 리소스를 계속 깎아먹는다"는 비용을 맞바꾸는 것이다.

```
기존: [React] ↔ [Spring Boot] ↔ [MariaDB + Kafka + ChromaDB + Embed-server]  (서버 과부하)
변경: [React] ↔ [Spring Boot] ↔ [MariaDB] + [MongoDB Atlas(외부)] + [LLM API(외부)]
```

이렇게 바꾸면 내 EC2는 Spring Boot와 React만 돌리면 되므로, 프리티어(RAM 1GB) 수준
에서도 훨씬 안정적으로 운영할 수 있다.

### 초기 단계에서 내린 결론

- **Kafka** 대신 Spring 내장 이벤트나 Redis로 구조를 단순화한다 — 별도 서버 자원을
  점유하는 컴포넌트를 실제 처리량이 필요해지기 전까지는 들이지 않는다.
- **MongoDB Atlas 같은 멀티모델 SaaS**로 벡터 데이터와 일반 데이터를 한곳에 모아
  관리 포인트를 줄인다.
- **임베딩은 로컬 모델 대신 OpenAI/Voyage AI 같은 외부 API**를 써서 서버 리소스
  확보와 모델 관리 부담을 함께 던다.
- 복잡한 인프라 컴포넌트를 SaaS로 밀어내면, 초기 단계에서는 EC2 프리티어로도
  운영 가능한 수준까지 비용을 낮출 수 있다.

### 이 경험에서 남는 원칙

기술 선택의 이유가 "배우고 싶어서"였다면, 그 선택이 서비스가 커지는 시점에 다시
검토 대상이 되는 건 자연스러운 일이다. 문제는 그 검토를 실제로 하느냐다 — 학습
목적으로 들인 컴포넌트를 프로덕션까지 관성적으로 끌고 가면, 정작 신경 써야 할
비용(서버비, LLM 토큰비)과 무관한 곳에서 인프라 복잡도만 쌓인다. "이 컴포넌트가
지금 이 서비스 규모에 필요한가"를 주기적으로 다시 묻는 게, 처음부터 완벽하게
설계하려는 시도보다 실용적이었다.

## AI로 수학 기출문제 변형 서비스 만들기 — 1~3주차 개발일지

RAG와 LLM을 실제로 손에 익히려고 사이드 프로젝트를 하나 시작했다. 주제는 수학
기출문제 — PDF로 된 기출문제를 넣으면 벡터로 인덱싱해서 분석하고, 그 문제를
변형한 유사 문제를 만들어주는 서비스다. 문제를 관리자가 직접 PDF로 올리는
구조로 잡은 이유도 있다 — LLM이 문제를 스스로 창작하게 하면 법적/정책적으로
애매해지지만, 선생님이나 관리자가 만든 문제를 PDF로 올리는 형태면 그 문제가
없다.

### 아키텍처

```
BackEnd   - Spring Boot 3.x
MQ        - Apache Kafka (KRaft 모드, Zookeeper 없이)
Main DB   - MariaDB
Vector DB - Chroma
LLM       - Claude API (claude-haiku-4-5)
Front     - React
인프라     - Docker Compose
```

핵심 파이프라인은 네 단계다.

1. **PDF 처리**: pymupdf로 텍스트/수식을 추출하고 문제 단위로 청킹한다. 수학
   기출은 수식이 이미지로 박혀 있는 경우가 많아서, LaTeX로 변환할지 이미지
   그대로 LLM에 넘길지가 첫 번째 갈림길이었다.
2. **RAG**: 문제를 임베딩해서 Chroma(로컬)/Pinecone(배포용)에 저장한다.
   단원·난이도·연도를 메타데이터로 같이 저장해두면 "미적분 3점짜리만" 같은
   필터링이 가능해진다.
3. **변형 문제 생성**: 원본 문제 + 유사 문제들을 컨텍스트로 Claude에 넘기고
   "숫자만 바꾸지 말고 풀이 구조를 바꿔라"고 지시한다.
4. **학습 데이터 축적**: 정답률·소요 시간·오답 패턴을 쌓아서 "이 학생은
   삼각함수 치환이 약하다" 같은 분석과 맞춤 추천으로 이어간다.

PDF 파싱, 변형 문제 생성, 채점처럼 시간이 걸리는 작업들은 요청-응답으로 묶지
않고 Kafka로 비동기 처리하기로 했다. 토픽은 세 개로 나눴다 — `pdf-uploaded`
(PDF 업로드 → 파싱+임베딩), `problem-generated`(변형 문제 생성 완료 → 알림/저장),
`student-answered`(학생 제출 → 채점+피드백). 각 단계가 오래 걸려도 앞 단계가
막히지 않게 하려는 목적이다.

### 1주차 — 인프라 구성

CLAUDE.md에 넣을 기술 스택/인프라를 먼저 정리하고, Docker Compose로 MariaDB(3306),
Kafka(9092), Chroma(8000)를 띄웠다. Kafka는 Zookeeper 없이 KRaft 모드로 구성했다.

### 2주차 — 파이프라인 뼈대와 비용 추정

개발 순서를 체크리스트로 잡았다.

```
1. docker-compose.yml (MariaDB + Kafka + Chroma)
2. Spring Boot 프로젝트 세팅 (Kafka Producer/Consumer 기본 구조)
3. PDF 업로드 → 이미지 변환 → Claude Vision OCR 파이프라인
4. Chroma 벡터 저장 + 유사 문제 검색
5. 변형 문제 생성 (Claude API)
6. 학생 답변 제출 → 채점/피드백 비동기 처리
7. React UI (관리자 / 학생 페이지)
```

3번까지 진행하면서, PDF만이 아니라 학생/강사가 캡처한 이미지로도 문제를 넣을
수 있어야겠다 싶어서 파일 타입을 분기했다.

```java
public enum FileType {
    PDF, IMAGE
}

List<String> pages = event.getFileType() == FileType.PDF
        ? pdfPageExtractor.extractBase64Pages(event.getStoredPath())
        : imageFileExtractor.extractBase64Images(event.getStoredPath());
```

본격적으로 돌리기 전에 비용부터 가늠해봤다. 수능 수학 1회분(약 30문제, 15페이지)
기준으로 단계별 토큰을 계산하면:

- **Vision OCR**: 페이지당 이미지 입력 ~1,600 토큰 + 시스템 프롬프트 ~500 토큰
  + LaTeX/메타데이터 출력 ~2,000 토큰 = 페이지당 ~4,100 토큰 × 15페이지 = **약 61,500 토큰**
- **임베딩**: 문제당 ~300 토큰 × 30문제 = **약 9,000 토큰**
- **변형 문제 생성**: 문제당 입력 500 + 출력 1,500 = 2,000 토큰 × 30문제 = **약 60,000 토큰**

합치면 약 13만 토큰, Sonnet 기준(Input $3/MTok, Output $15/MTok)으로 환산하면
OCR 약 $0.15 + 임베딩 약 $0.02 + 변형 생성 약 $0.75로 **총 $0.92 정도**다. 다만
그래프/도형이 많은 페이지는 출력 토큰이 2배까지 뛸 수 있고, Kafka 재시도/에러
처리가 붙으면 전체적으로 10~20%는 더 잡아야 한다. 정확한 측정은 결국 전체를
한 번에 돌리기보다 1페이지씩 먼저 실행해서 `response.usage` 로그로 검증하는
게 제일 현실적이었다.

### 3주차 — OCR 테스트와 임베딩에서 만난 문제들

40페이지 중 3페이지만 임시로 돌려서 10문제 가공까지는 성공했는데, Chroma에
저장하는 단계에서 걸렸다.

```
{"error":"Unimplemented","message":"The v1 API is deprecated. Please use /v2 apis"}
```

최신 버전 Chroma는 v1 API가 없어졌고, v2부터는 컬렉션 경로에 `tenant`/`database`를
(기본값이라도) 반드시 넣어야 했다.

```java
String tenant = "default";
String database = "default";

ObjectNode body = objectMapper.createObjectNode();
body.put("name", collectionName);
body.put("get_or_create", true);

String response = webClient.post()
        .uri("/api/v2/tenants/{tenant}/databases/{database}/collections", tenant, database)
        .contentType(MediaType.APPLICATION_JSON)
        .bodyValue(body)
        .retrieve()
        .bodyToMono(String.class)
        .block();
```

이 문제를 풀고 나서는 유형별 저장까지는 됐는데, 임베딩 모델 선택에서 두 번째
벽을 만났다. 처음엔 태그·유형·문제 내용 세 가지를 다 임베딩에 넣었는데, 쓰고
있던 `paraphrase-multilingual-MiniLM-L12-v2`가 일반 자연어 임베딩 모델이라
수식이 섞인 "문제 내용"은 애초에 의미를 이해하지 못했다 — 그래서 문제 내용은
빼고 태그/유형만 임베딩하는 쪽으로 바꿨다.

그래프·도형을 표현하던 SVG 콘텐츠가 누락되는 문제도 있었다. 처음엔 Claude가
직접 그래프를 그리게 했는데 제대로 안 그려지는 경우가 많았다. 더 나은 방향은
Claude는 함수식(`y = x²-2x+1`) 같은 수식만 뽑아내고, 실제 렌더링은 프론트엔드의
그래핑 라이브러리(JSXGraph)가 맡는 구조였다 — 다만 JSXGraph는 프롬프트에 수식
설명을 더 자세히 써줘야 한다는 트레이드오프가 있었다.
