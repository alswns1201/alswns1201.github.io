#### RAG란?

RAG는 **Retrieval-Augmented Generation** 의 약자로, 검색한 자료로 AI 답변 능력을 강화한다 는 프로세스입니다.

> 질문 → 검색 → 답변

이 세 단계를 RAG라고 합니다.

#### 임베딩(Embedding)이란?

RAG를 이해하려면 먼저 **임베딩** 을 알아야 합니다.

임베딩은 **텍스트의 의미를 숫자(벡터)로 표현하는 방법** 입니다. 의미가 비슷한 단어나 문장일수록 벡터 공간에서 가까운 위치에 놓이게 됩니다. 강아지와 개는 가까이, 강아지와 자동차 는 멀리 위치하는 식입니다.
    
    
    텍스트 → 임베딩 모델 → 벡터 배열 [0.12, -0.34, 0.78, ...]

차원이 높을수록 의미를 세밀하게 표현할 수 있지만 처리 속도가 느려지므로, 용도에 맞는 적절한 차원을 선택해야 합니다.

#### 청킹(Chunking)이란?

문서가 많을 경우 한 번에 임베딩하지 않고 **청킹(Chunking)** 과정을 거칩니다.

  * **청크(Chunk)** : 텍스트를 잘게 나눈 정보 조각
  * RAG의 품질은 **어떻게 청킹하느냐** 에 크게 달려 있습니다
  * 정보 손실을 최소화하는 것이 핵심이며, 생각보다 쉽지 않습니다



청킹 전 단계: Parser

문서를 청킹하기 전에 Parser(파서)로 문서를 읽어야 합니다. 현재는 **Document Parsing 전용 모델** 이 가장 우수한 성능을 보입니다.

청킹 방식 2가지

방식설명  길이 기반 청킹 | 글자 수나 토큰 수로 일정하게 자르는 방식  
---|---  
의미 기반 청킹 | 문단, 문장 등 의미 단위로 자르는 방식  
  
* * *

#### 벡터 DB와 기본 파이프라인

청킹된 조각들을 임베딩으로 변환한 후 **벡터 DB** 에 저장합니다.

**전체 흐름:**

  1. 문서 → 파싱 → 청킹 → 임베딩 → 벡터 DB 저장 (사전 작업)
  2. 사용자 질문 → 임베딩 변환 → 벡터 DB에서 유사 청크 검색 → LLM에 컨텍스트로 전달 → 답변 생성 (실시간)



#### RAG가 실패하는 진짜 원인

> 문제는 생성(Generation)이 아니라 검색(Retrieval)이다.

청크 품질이 낮으면 아무리 좋은 LLM을 써도 답변 품질이 떨어집니다.

**디버깅 방법:** 실제 유입될 질문 5~10개를 직접 선정하고, 벡터 검색 결과를 눈으로 확인하며 청크 품질을 점검합니다. 이 과정을 **시멘틱 서치(Semantic Search) 디버깅** 이라고 합니다.

#### 하이브리드 서치: Dense + Sparse

시멘틱 서치만으로 해결되지 않는 경우가 있습니다. 예를 들어 제품 코드, 고유 명사, 특수 용어처럼 **정확한 키워드 일치** 가 중요한 경우입니다.

방식원리강점  Dense 임베딩 | 의미 기반 유사도 검색 | 문맥 이해, 동의어 처리  
---|---|---  
Sparse 임베딩 | 키워드(단어) 기반 검색 (BM25 등) | 정확한 단어 일치, 고유명사  
**Hybrid Search** | 둘을 결합 | 의미 + 키워드 동시 커버  
  
#### Reranker: 검색 결과를 다시 정밀 평가

하이브리드 서치로 후보 청크를 뽑은 뒤, **Reranker** 가 이를 더 정밀하게 재평가하고 순위를 재정렬합니다.

  * 벡터 검색은 빠르지만 조금 거칠 수 있습니다
  * Reranker는 느리지만 정확합니다
  * 보통 **벡터 검색 → (후보 20~50개) → Reranker → (최종 3~5개) → LLM** 순서로 사용합니다
