JWT 기반 인증/인가를 Spring Security로 구현하다 보면 **401과 403을 어떻게 나눌 것인가** 에서 대부분 한 번은 막힌다.

나도 실제 프로젝트에서 이 부분을 헷갈려서 로그가 꼬이고, 프론트에서 에러 분기가 안 맞고, Swagger 테스트 결과가 이상하게 나오는 경험을 했다.

이 글에서는 **JwtAuthenticationEntryPoint** 와 **JwtAccessDeniedHandler** 가

  * 언제 호출되는지
  * 무엇을 책임지는지
  * 실무에서는 어떻게 나눠야 하는지



을 기준으로 정리한다.

* * *

## 1\. 401과 403의 역할부터 정리

HTTP 스펙 기준으로 보면 답은 단순하다.

상태코드의미

401 Unauthorized | 인증 실패 (Authentication 실패)  
---|---  
403 Forbidden | 인가 실패 (Authorization 실패)  
  
### JWT 기준으로 해석하면

  * **401 (Authentication 실패)**
    * 토큰 없음
    * 토큰 만료
    * 토큰 위조 / 서명 불일치
    * 형식이 잘못된 토큰
  * **403 (Authorization 실패)**
    * 토큰은 유효함
    * 사용자는 인증됨
    * 하지만 해당 API에 접근할 권한(Role)이 없음



이 기준이 흔들리면

  * 프론트 분기
  * 로그 분석
  * 장애 대응



전부 꼬이기 시작한다.

* * *

## 2\. JwtAuthenticationEntryPoint란?

AuthenticationEntryPoint는 **인증 자체가 실패했을 때** 호출되는 진입점이다.

### 호출되는 시점

  * Security Filter Chain에서
  * AuthenticationException이 발생했을 때
  * 아직 인증(Authentication)이 성립되지 않은 상태



즉,

> **"너 누구야?" 단계에서 실패하면 여기로 온다**

### 대표적인 상황

  * Authorization Header 자체가 없음
  * Bearer 토큰이 없음
  * JWT 만료
  * JWT 파싱 실패



* * *

## 3\. JwtAuthenticationEntryPoint 예제
    
    
    @Component
    public class JwtAuthenticationEntryPointHandler implements AuthenticationEntryPoint {
    
    
    @Override
    public void commence(HttpServletRequest request,
    HttpServletResponse response,
    AuthenticationException authException) throws IOException {
    
    
    response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    response.setContentType("application/json;charset=UTF-8");
    
    
    if (authException instanceof ExpiredTokenException) {
    response.getWriter().write("{\"code\":\"401\", \"message\":\"token expired\"}");
    } else if (authException instanceof InvalidTokenException) {
    response.getWriter().write("{\"code\":\"401\", \"message\":\"invalid token\"}");
    } else {
    response.getWriter().write("{\"code\":\"401\", \"message\":\"authentication failed\"}");
    }
    }
    }

### 핵심 포인트

  * **무조건 401만 내려야 한다**
  * EntryPoint에서 403을 내려버리면 개념이 깨진다
  * 상세 원인은 메시지 또는 내부 코드로만 구분한다



* * *

## 4\. JwtAccessDeniedHandler란?

AccessDeniedHandler는 **인증은 성공했지만 권한이 없을 때** 호출된다.

### 호출되는 시점

  * SecurityContext에 Authentication이 이미 존재
  * 하지만 @PreAuthorize, hasRole, antMatchers 조건을 통과하지 못함



즉,

> **"너인 건 알겠는데, 여기 들어올 권한은 없어"**

* * *

## 5\. JwtAccessDeniedHandler 예제
    
    
    @Component
    public class JwtAccessDeniedHandler implements AccessDeniedHandler {
    
    
    @Override
    public void handle(HttpServletRequest request,
    HttpServletResponse response,
    AccessDeniedException accessDeniedException) throws IOException {
    
    
    response.setStatus(HttpServletResponse.SC_FORBIDDEN);
    response.setContentType("application/json;charset=UTF-8");
    
    
    response.getWriter().write(
    "{\"code\":\"403\", \"message\":\"access denied\"}"
    );
    }
    }

### 여기서는 딱 하나만 책임진다

  * **403 반환**
  * 권한 없음에 대한 명확한 신호



* * *

## 6\. SecurityConfig에서의 연결
    
    
    http
    .exceptionHandling()
    .authenticationEntryPoint(jwtAuthenticationEntryPointHandler)
    .accessDeniedHandler(jwtAccessDeniedHandler);

이렇게만 설정해두면

  * 인증 실패 → EntryPoint
  * 인가 실패 → AccessDeniedHandler



자동으로 분기된다.

* * *

## 7\. 실무에서 자주 터지는 실수

### ❌ EntryPoint에서 403 내려버리기

  * 토큰 없음인데 403
  * 만료인데 403



→ 프론트에서 **로그인 만료 판단 불가**

### ❌ 인증/인가 예외를 하나로 처리

  * CustomException 하나로 다 던짐
  * 결과적으로 항상 같은 상태코드



→ 로그와 원인 추적 불가능

* * *

## 8\. 내가 쓰는 명확한 기준

  * 인증 실패 → **AuthenticationException 계열 → EntryPoint → 401**
  * 권한 실패 → **AccessDeniedException → AccessDeniedHandler → 403**



JWT Filter 안에서는

  * 만료 → ExpiredTokenException
  * 위조 → InvalidTokenException



을 **그대로 던지고 잡지 않는다**.

Security가 처리하게 맡기는 게 가장 깔끔하다.

* * *

## 9\. 마무리

JWT 인증에서 제일 중요한 건

> **상태코드의 일관성** 이다.

  * 클라이언트는 상태코드로 분기하고
  * 서버는 로그로 원인을 추적한다



JwtAuthenticationEntryPoint와 JwtAccessDeniedHandler를 역할에 맞게 분리해두면

  * 코드가 단순해지고
  * 디버깅이 쉬워지고
  * 운영 사고가 줄어든다.



이건 이론이 아니라 **실무에서 바로 체감된다**.
