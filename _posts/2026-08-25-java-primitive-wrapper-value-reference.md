`long a = 100L`과 `Long a = 100L`은 똑같이 100을 담고 있는 것처럼 보이지만,
변수가 실제로 들고 있는 게 "값 그 자체"인지 "값이 있는 곳을 가리키는 참조"인지가
다르다. 이 차이를 모르고 `==`을 쓰면 어떤 값에서는 맞고 어떤 값에서는 틀리는,
재현이 까다로운 버그가 생긴다. `long`/`Long`을 예로 값 참조와 메모리 참조,
그리고 `==`과 `equals()`가 왜 이 축 위에서 갈라지는지 정리한다.

## long — 값 그 자체

`long`은 primitive type이다. 변수는 8바이트 값을 직접 담는다. 변수를 다른 변수에
대입하면 그 값이 복사된다 — 두 변수는 이후로 완전히 독립적이다.

```java
long a = 100L;
long b = a; // 값 복사
b = 200L;
// a는 여전히 100
```

primitive는 힙에 객체로 존재하지 않는다. 그래서 `null`을 담을 수도 없다 —
"값이 없음"을 표현할 방법 자체가 primitive 타입 시스템 안에는 없다.

## Long — 값이 아니라 값이 있는 곳을 가리키는 참조

`Long`은 wrapper class다. `Long a = 100L;`이라고 쓰면 실제로는 오토박싱이 일어나서
`Long a = Long.valueOf(100L);`처럼 힙에 `Long` 객체가 하나 만들어지고, 변수 `a`는
그 객체를 가리키는 참조(주소)를 담는다.

```java
Long a = 100L;
Long b = a; // 참조 복사 — 같은 객체를 가리키게 됨
```

여기서 `b`에 대입된 건 값이 아니라 "그 객체가 어디 있는지"다. 그래서 `Long`은
`null`을 담을 수 있다 — "참조가 아무 객체도 안 가리킨다"는 상태가 곧 `null`이니까.
DB 컬럼이 NULL 가능이면 엔티티 필드를 `long`이 아니라 `Long`으로 두는 이유가 이거다.

## `==`이 primitive냐 reference냐에 따라 완전히 다른 걸 비교한다

`==`은 두 상황에서 서로 다른 걸 비교한다.

- **primitive(`long`) 간 `==`**: 값 자체를 비교한다. `5L == 5L`은 값이 같으니 `true`.
- **reference(`Long`) 간 `==`**: 참조(주소)를 비교한다. "같은 값을 가진 두 객체"는
  값은 같아도 서로 다른 메모리 위치에 있으면 `false`다.

```java
Long a = new Long(200L);
Long b = new Long(200L);
a == b; // false — 값은 같지만 서로 다른 객체
a.equals(b); // true — Long이 값 비교로 오버라이드해둠
```

`long` vs `Long`이 "값 vs 참조"를 보여주는 예시라면, `==` vs `equals()`는 그
구도가 실제로 프로그램 동작에 어떤 차이를 만드는지 보여주는 다음 단계다.
`equals()`가 필요한 이유는 정확히 여기 있다 — reference type에서 "가리키는 객체가
같은가"가 아니라 "값이 같은가"를 물으려면, `==`이 아니라 값 비교로 오버라이드된
`equals()`를 써야 한다.

## 캐싱이 만드는 함정 — `==`이 어쩌다 맞아버리는 경우

`Long.valueOf()`(오토박싱이 내부적으로 호출하는 메서드)는 `-128 ~ 127` 범위의
값을 `LongCache`에 미리 만들어두고 재사용한다. `Integer`도 동일한 캐싱을 한다
(`IntegerCache`, 같은 범위). 그래서 이 범위 안의 값은 오토박싱해도 항상 같은
객체를 참조하게 되고, `==`이 우연히 값 비교처럼 동작한다.

```java
Long a = 100L, b = 100L;
a == b; // true — 캐시된 같은 객체를 가리킴

Long c = 200L, d = 200L;
c == d; // false — 캐시 범위 밖이라 오토박싱마다 새 객체 생성
```

이게 위험한 이유는 "작은 테스트 값으로는 통과하는데 실제 데이터에서는 깨지는"
전형적인 패턴이기 때문이다. 개발 중에 `Long id = 1L`처럼 작은 값으로 테스트하면
`==`이 우연히 맞아떨어져서 버그가 숨어 있다가, 실제 운영 데이터의 ID가 128 이상으로
커지는 순간 터진다. `Long`, `Integer`, `Short`, `Byte`, `Character`, `Boolean`
전부 wrapper라면 값 비교는 예외 없이 `equals()`로 해야 한다는 규칙을 캐싱 범위에
대한 예외 없이 지키는 게 안전한 이유가 여기 있다.

## 오토박싱/언박싱과 `NullPointerException`

`long`과 `Long`을 섞어서 `==`으로 비교하면, 컴파일러는 `Long` 쪽을 자동으로
언박싱해서 값 비교로 처리한다.

```java
Long a = null;
long b = 5L;
a == b; // a를 언박싱하려는 순간 NullPointerException
```

이건 "타입이 섞였을 때 컴파일러가 알아서 맞춰준다"는 편의가 오히려 함정이 되는
경우다. DB에서 조회한 값이 없어서 `Long` 필드가 `null`인 상태로, primitive와
비교하거나 산술 연산(`a + 1`)을 하면 예외가 난다. `Long` 필드를 다룰 때는
"이 값이 null일 수 있는가"를 먼저 확인하고, 필요하면 `Objects.equals(a, b)`처럼
null-safe한 비교를 쓰는 게 낫다.

## 정리

| | `long` | `Long` |
|---|---|---|
| 분류 | primitive | reference (wrapper) |
| 변수가 담는 것 | 값 자체 | 객체를 가리키는 참조 |
| `null` 가능 여부 | 불가능 | 가능 |
| `==`의 의미 | 값 비교 | 참조(주소) 비교 |
| 값 비교 방법 | `==` | `equals()` |
| 함정 | 없음 | 캐싱 범위(-128~127)에서만 `==`이 우연히 맞음, 언박싱 시 NPE |

`long`/`Long`은 값 참조와 메모리 참조가 자바 안에서 어떻게 갈라지는지 보여주는
가장 단순한 예시이고, `==`/`equals()`는 그 차이를 실제로 겪게 되는 지점이다.
reference type을 비교할 때 `==`을 쓰고 싶어지면, "지금 내가 궁금한 게 같은 객체인지,
같은 값인지"부터 되물어야 한다.
