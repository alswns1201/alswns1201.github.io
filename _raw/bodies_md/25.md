# [Spring] "이거 당연히 성공하는 거 아니야?" - 제대로 이해하는 단위 테스트(Unit Test)의 모든 것

안녕하세요, 개발자 여러분!  
오늘은 많은 주니어 개발자들이 처음 접할 때 가장 헷갈려 하는 주제 중 하나인 **테스트 코드** , 그중에서도 **단위 테스트(Unit Test)**에 대해 깊이 파고들어 보려고 합니다.

"테스트 코드를 왜 짜야 하나요?", "실무에서는 정말 테스트 코드를 다 짜나요?", 그리고 "이거 다 가짜로 만들어서 테스트하면 당연히 성공하는 거 아니에요?" 와 같은 질문에 대한 답을 이 글에서 찾아가실 수 있을 겁니다.

### 1\. 실무에서의 테스트 코드 작성, 현실은?

실무에서 테스트 코드를 작성하는 흐름은 크게 두 가지로 나뉩니다.

  * **TDD (테스트 주도 개발)** : **테스트를 먼저 작성** 하고, 그 테스트를 통과시키는 실제 코드를 작성하는 방식입니다. 설계의 완성도를 높이고 버그를 사전에 방지하는 데 매우 효과적이지만, 학습 곡선이 있고 초기 개발 속도가 더딜 수 있습니다.
  * **코드 작성 후 테스트** : **실제 로직을 먼저 구현** 하고, 그 기능이 의도대로 동작하는지 검증하기 위해 나중에 테스트 코드를 작성하는 방식입니다. 대부분의 개발자에게 익숙하고 속도가 빠르지만, 테스트를 누락하거나 테스트하기 어려운 구조로 코드를 짜게 될 위험이 있습니다.



현실적인 실무에서는 두 방식을 혼합하여 사용합니다. 중요한 것은 **"어떤 순서로 짜느냐"**보다 **"테스트를 통해 무엇을 검증하고 보장할 것인가"**에 대한 명확한 이해입니다.

* * *

### 2\. 단위 테스트(Unit Test)란 무엇인가? - 연극 무대 비유

단위 테스트는 말 그대로 테스트의 가장 작은 '단위'를 검증하는 것입니다. 저는 단위 테스트를 **"주인공 배우의 독백 연기 리허설"**에 비유하곤 합니다.

  * **테스트 대상 (Unit)** : 오늘 리허설을 할 **주인공 배우** (AuthService)
  * **테스트의 목표** : 주인공 배우가 자신의 **대사, 동선, 감정 표현(비즈니스 로직)**을 각본대로 정확히 수행하는지 확인하는 것
  * **의존성 (Dependencies)** : 주인공과 대화를 나눠야 할 다른 **조연 배우들** (UserRepository, JwtTokenProvider 등)



리허설에서 우리는 오직 '주인공 배우'의 연기에만 집중하고 싶습니다. 만약 조연 배우가 갑자기 대사를 까먹거나 엉뚱한 연기를 하면, 주인공의 연기를 제대로 평가할 수 없겠죠?

그래서 우리는 조연 배우들 대신, **우리가 시키는 대로만 정해진 대사를 읊어주는 '대역 배우(가짜 객체, Mock)'**를 무대에 세웁니다.

이것이 바로 Mockito와 같은 모킹(Mocking) 라이브러리를 사용하는 이유입니다.

* * *

### 3\. 단위 테스트 작성하기: @ExtendWith(MockitoExtension.class)

Spring Boot 환경에서 JUnit 5와 Mockito를 사용한 단위 테스트의 전형적인 구조를 살펴보겠습니다. AuthService의 로그인 기능을 테스트하는 예시입니다.

#### 3.1. 테스트 환경 설정: 배우 섭외 및 무대 준비 (@Mock, @InjectMocks)
    
    
    import org.junit.jupiter.api.extension.ExtendWith;
    import org.mockito.InjectMocks;
    import org.mockito.Mock;
    import org.mockito.junit.jupiter.MockitoExtension;
    
    @ExtendWith(MockitoExtension.class) // "지금부터 Mockito를 사용한 테스트를 시작하겠습니다!"
    public class AuthServiceTest {
    
        @InjectMocks // 주인공 배우 섭외 (실제 객체)
        private AuthService authService;
    
        // 대역 배우들 섭외 (가짜 객체)
        @Mock private UserRepository userRepository;
        @Mock private CrewRepository crewRepository;
        @Mock private JwtTokenProvider jwtTokenProvider;
        @Mock private OAuthProviderFactory providerFactory;
        @Mock private PasswordEncoder passwordEncoder;
        @Mock private OAuthProvider mockOAuthProvider;
    }

  * @ExtendWith(MockitoExtension.class): JUnit 5에게 Mockito 확장 기능을 사용하겠다고 알립니다.
  * @InjectMocks: 테스트의 주인공이 될 실제 객체입니다. @Mock으로 생성된 가짜 객체들이 이 객체의 필드에 자동으로 주입됩니다.
  * @Mock: 주인공이 의존하는 모든 외부 컴포넌트들을 가짜 객체로 만듭니다. 이들은 실제 DB에 접근하거나 API를 호출하지 않습니다.



#### 3.2. 시나리오 설정: 대역 배우들에게 대본 나눠주기 (when().thenReturn())

이제 각 대역 배우(Mock)가 어떤 상황에서 어떤 대사(리턴값)를 쳐야 하는지 대본을 나눠줍니다.
    
    
    import static org.mockito.Mockito.when;
    import static org.mockito.ArgumentMatchers.any;
    
    @Test
    @DisplayName("신규 유저가 크루장으로 가입하는 시나리오")
    void login_new_user_as_leader() {
        // given (상황 설정 및 대본 작성)
        // ... (OAuthLoginRequestDto 준비) ...
    
        // 대본 1: "providerFactory야, KAKAO로 getProvider()가 호출되면, mockOAuthProvider를 리턴해."
        when(providerFactory.getProvider(SocialType.KAKAO)).thenReturn(mockOAuthProvider);
    
        // 대본 2: "mockOAuthProvider야, getAccessToken()이 호출되면, 'test-access-token'을 리턴해."
        when(mockOAuthProvider.getAccessToken(any())).thenReturn("test-access-token");
        
        // 대본 3: "userRepository야, 특정 이메일로 findByEmail()이 호출되면, '사용자가 없다'는 의미로 Optional.empty()를 리턴해."
        when(userRepository.findByEmail("newuser@example.com")).thenReturn(Optional.empty());
    
        // 대본 4: "userRepository야, 어떤 User 객체든 save()가 호출되면, 그냥 받은 그대로 돌려줘."
        when(userRepository.save(any(User.class))).thenAnswer(i -> i.getArgument(0));
        
        // ... (다른 Mock 객체들의 행동도 모두 정의) ...
    }

when(가짜객체.메서드호출).thenReturn(정해진리턴값) 구문은 **"만약 이 배우가 이런 요청을 받으면, 이렇게 대답해라"** 라고 지시하는 대본과 같습니다.

### 4\. "이거 당연히 성공하는 거 아니야?" - 단위 테스트의 진짜 목적

자, 이제 모든 대역 배우들은 우리가 짠 대본대로만 연기할 준비가 끝났습니다. 이 상태에서 주인공 배우(authService)의 연기를 시작시키면, 당연히 우리가 정해놓은 시나리오대로 흘러가겠죠.
    
    
    // when (실제 연기 시작)
    String resultToken = authService.login(requestDto);
    
    // then (결과 확인)
    assertThat(resultToken).isEqualTo("fake-jwt-token"); // 당연히 성공할 것이다!

그렇다면 이 테스트는 무의미할까요? **아닙니다. 바로 이 '당연함'을 보장하는 것이 단위 테스트의 진짜 가치입니다.**

  1. **로직 흐름(Flow)에 대한 보증** : 이 테스트가 통과했다는 것은, "AuthService가 내가 예상한 순서대로 UserRepository의 findByEmail을 호출하고, 그 결과에 따라 save를 호출한 뒤, 마지막으로 JwtTokenProvider의 generateToken을 호출하는구나" 라는 **내부 로직의 흐름이 올바르다는 것을 증명** 합니다.
     * 이를 더 명확히 하려면 Mockito.verify()를 사용하여 "정말로 save 메서드가 호출되었는가?"를 직접 검증할 수 있습니다.
  2. **미래를 위한 안전망** : 6개월 뒤, 동료나 미래의 내가 이 코드를 리팩토링한다고 상상해보세요. 코드를 수정한 뒤 이 테스트를 실행해서 통과한다면, "아, 내 수정이 기존의 중요한 로직 흐름을 망가뜨리지 않았구나!" 라는 **강력한 자신감** 을 얻을 수 있습니다.
  3. **살아있는 명세서** : 이 테스트 코드는 그 자체로 AuthService.login() 메서드가 어떤 조건에서 어떤 의존성을 호출하고 어떤 결과를 내야 하는지를 보여주는 **가장 정확한 문서** 가 됩니다.



결론적으로, 단위 테스트는 단순히 '성공/실패'를 가리는 것이 아닙니다. 우리가 통제하는 완벽한 환경 속에서, 테스트 대상이 우리가 의도한 설계대로 정확히 동작하는지를 검증하고, 그 설계를 문서화하며, 미래의 변화에도 깨지지 않도록 지켜주는 **견고한 안전장치** 인 셈입니다.
