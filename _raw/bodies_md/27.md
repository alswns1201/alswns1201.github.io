  
"이 버튼을 누르면 서버가 터져요!" 라는 말을 들어보셨나요? 😅 오늘은 예외(Exception)가 발생했을 때 서버가 멈추지 않고, 사용자에게는 친절한 에러 메시지를, 개발자에게는 명확한 로그를 남기는 **'우아한 예외 처리'** 방법에 대해 이야기해 보려고 합니다.

try-catch 블록으로 가득 찬 서비스 코드를, Spring이 제공하는 @ControllerAdvice를 이용해 어떻게 깔끔하게 리팩토링할 수 있는지 함께 알아보시죠!

### 1\. 전통적인 예외 처리의 문제점: try-catch 지옥

처음에는 서비스 로직 안에서 직접 try-catch를 사용하여 예외를 처리하는 경우가 많습니다.
    
    
    // 나쁜 예: Service 계층에서 모든 것을 처리하려는 경우
    @Service
    public class CrewService {
        public void createCrew(CrewCreateDto dto) {
            try {
                // 비즈니스 로직
                if (crewRepository.existsByName(dto.getName())) {
                    // 여기서 예외를 만들고...
                    throw new IllegalStateException("이미 존재하는 크루 이름입니다.");
                }
                crewRepository.save(newCrew);
            } catch (IllegalStateException e) {
                // 잡아서 로깅하고...
                log.error("크루 생성 실패: {}", e.getMessage());
                // 사용자에게 보낼 메시지를 직접 반환하거나, null을 반환...
                // 여기서 뭘 해야 할지 애매해집니다. 서비스가 HTTP 응답을 고민하기 시작합니다.
            }
        }
    }

이 방식의 문제점은 명확합니다.

  * **책임의 모호함** : 서비스의 책임은 '비즈니스 로직 수행'인데, 'HTTP 응답'이나 '사용자에게 보낼 에러 메시지'까지 고민하게 됩니다.
  * **코드의 오염** : 모든 메서드마다 try-catch가 반복되어, 진짜 비즈니스 로직을 파악하기 어렵습니다.
  * **트랜잭션 문제** : 예외를 서비스 안에서 catch 해버리면, @Transactional이 예외를 감지하지 못해 DB 롤백이 동작하지 않을 수 있습니다.

### 2\. 현대적인 예외 처리 전략: 역할 분담과 책임 위임

우아한 예외 처리는 각 계층에 명확한 역할을 부여하는 것에서 시작합니다. 마치 회사의 업무 프로세스처럼 말이죠.

  * **Service (현장 직원)**: "문제 발생! 보고합니다!"
  * **Controller (중간 관리자)**: "내 담당 아님. 상부로 전달!"
  * **@ControllerAdvice (위기 대응팀)**: "모든 문제 보고는 이쪽으로! 메뉴얼대로 처리!"



#### 2.1. Service 계층: 예외를 만들고, throw로 던지기만 하라

서비스는 비즈니스 규칙에 맞지 않는 상황을 만나면, **명확한 커스텀 예외를 만들어서 그냥 밖으로 던지기만** 하면 됩니다.

**BusinessException.java (우리 회사만의 보고서 양식)**
    
    
    public class BusinessException extends RuntimeException {
        private final ErrorCode errorCode;
        // ... 생성자 및 getter ...
    }

**ErrorCode.java (사전에 정의된 문제 상황 코드)**
    
    
    @Getter
    @RequiredArgsConstructor
    public enum ErrorCode {
        CREW_NOT_FOUND(HttpStatus.NOT_FOUND, "해당 크루를 찾을 수 없습니다."),
        CREW_NAME_DUPLICATED(HttpStatus.CONFLICT, "이미 존재하는 크루 이름입니다.");
    
        private final HttpStatus status;
        private final String message;
    }

**AuthService.java (현장 직원의 행동)**
    
    
    @Service
    public class AuthService {
        @Transactional
        public User registerOrLoginUser(...) {
            // ... 로직 수행 ...
            crewRepository.findByName(crewNameToCreate).ifPresent(c -> {
                // 문제가 생겼다! 보고서(BusinessException)를 작성해서 던진다.
                throw new BusinessException(ErrorCode.CREW_NAME_DUPLICATED);
            });
            // ...
        }
    }

서비스는 이제 try-catch 없이 깔끔해졌습니다. 오직 비즈니스 로직과 예외 상황 '보고'에만 집중합니다.

#### 2.2. Controller 계층: 아무것도 하지 마라

컨트롤러는 서비스가 던진 예외를 그대로 통과시킵니다. 예외를 처리하는 것은 컨트롤러의 책임이 아닙니다.
    
    
    @RestController
    public class AuthController {
        @PostMapping("/login/{provider}")
        public ResponseEntity<String> socialLogin(...) {
            // authService.login()에서 예외가 발생하면,
            // 이 메서드는 그냥 즉시 중단되고 예외는 밖으로 전파됩니다.
            String jwtToken = authService.login(requestDto);
            return ResponseEntity.ok(jwtToken);
        }
    }

#### 2.3. @ControllerAdvice: 중앙 위기 대응팀

이제 컨트롤러 밖으로 나온 모든 예외를 한 곳에서 잡아 처리합니다. @RestControllerAdvice 어노테이션이 붙은 클래스가 바로 그 역할을 합니다.

**GlobalExceptionHandler.java (중앙 위기 대응팀)**
    
    
    import com.myproject.dto.ErrorResponse; // 별도 파일로 분리된 DTO
    
    @Slf4j
    @RestControllerAdvice // 모든 @RestController에서 발생하는 예외를 전역적으로 처리
    public class GlobalExceptionHandler {
    
        // BusinessException 타입의 예외 보고가 들어오면 이 메서드가 실행됨
        @ExceptionHandler(BusinessException.class)
        public ResponseEntity<ErrorResponse> handleBusinessException(BusinessException ex) {
            log.error("비즈니스 예외 발생: {}", ex.getMessage());
            ErrorCode errorCode = ex.getErrorCode();
            
            // 메뉴얼에 따라 사용자에게 보여줄 응답을 생성
            ErrorResponse response = new ErrorResponse(errorCode.name(), errorCode.getMessage());
            
            // 정해진 HTTP 상태 코드와 함께 응답 반환
            return new ResponseEntity<>(response, errorCode.getStatus());
        }
    
        // 혹시 모를 다른 모든 예외(NPE 등)는 여기서 처리 (500 에러)
        @ExceptionHandler(Exception.class)
        public ResponseEntity<ErrorResponse> handleException(Exception ex) {
            log.error("처리되지 않은 예외 발생", ex);
            ErrorResponse response = new ErrorResponse("INTERNAL_SERVER_ERROR", "서버 내부 오류입니다.");
            return new ResponseEntity<>(response, HttpStatus.INTERNAL_SERVER_ERROR);
        }
    }

이 구조를 통해 모든 예외 처리 로직이 GlobalExceptionHandler 단 한 곳으로 모이게 됩니다. 일관성 있는 에러 응답을 보장하고, 유지보수가 매우 용이해집니다.

### [번외] enum.name(): 

네, 맞습니다! Java의 모든 enum은 java.lang.Enum 클래스를 상속받기 때문에, 개발자가 따로 만들지 않아도 기본적으로 name() 메서드를 가지고 있습니다.
    
    
    ErrorCode.CREW_NOT_FOUND.name(); // "CREW_NOT_FOUND" 라는 문자열을 반환합니다.

이 메서드는 enum 상수의 이름 자체를 문자열로 반환해주므로, ErrorCode 예시처럼 API 응답의 code 값으로 사용하기에 매우 유용합니다.

### 결론

try-catch 블록으로 서비스 코드를 더럽히는 대신, 각 계층에 명확한 책임을 부여해 보세요.

  1. **Service** : 비즈니스 예외가 발생하면, 명확한 Custom Exception을 throw 한다.
  2. **Controller** : 예외를 무시하고 그대로 통과시킨다.
  3. **@ControllerAdvice** : 던져진 모든 예외를 중앙에서 처리하여 일관된 에러 응답을 반환한다.



이러한 전역 예외 처리 전략은 여러분의 코드를 훨씬 더 깔끔하고, 안정적이며, 전문적으로 만들어 줄 것입니다.
