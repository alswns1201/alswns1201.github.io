호스팅을 고려하는가"와 "그 판단을 어떤 기준으로 하는가"를 추가했습니다 — 검토 부탁드려요)*

Git은 로컬에서도 완결된 버전 관리 시스템이다. 커밋, 브랜치, 되돌리기 모두 로컬 저장소
하나로 가능하다. 그런데도 원격 저장소가 필수인 이유는 버전 관리가 아니라 **협업과
가용성** 때문이다 — 로컬 저장소가 날아가면 히스토리 전체가 사라지고, 원격 저장소가 없으면
다른 사람의 변경 사항을 받을 방법이 없다.

## 기본 흐름

```
git init                      # 로컬 저장소 생성
git remote add origin <URL>   # 원격 저장소 등록
git push -u origin <branch>   # 최초 push (이후 push/pull은 브랜치 추적됨)
```

각 명령의 역할:

- `git clone <URL>`: 원격 저장소를 로컬에 복제
- `git remote add <이름> <URL>`: 원격 저장소를 등록 (이름은 관례상 `origin`, 여러 개면 `origin`, `gitea`처럼 구분)
- `git push` / `git pull`: 로컬 변경을 반영 / 원격 변경을 가져와 병합
- `git fetch`: 원격 변경을 **가져오기만** 하고 병합은 하지 않음 — 병합 전에 변경 내용을 먼저 확인하고 싶을 때 쓴다

## GitHub/GitLab 대신 자체 호스팅(Gitea)을 고려하는 기준

Gitea는 Go로 작성된 경량 Git 서비스로, 자체 서버에 직접 설치해서 운영한다. 문제는 "가볍고
설치가 쉽다"는 게 도입 이유가 되기엔 부족하다는 것이다 — 진짜 판단 기준은 **누가 그 서버의
가용성을 책임지느냐**다.

GitHub/GitLab 같은 SaaS를 쓰면 이중화, 백업, 보안 패치, CI 러너 확장 같은 걸 플랫폼이
대신 해준다. 자체 호스팅으로 옮기는 순간, 이 책임이 전부 우리 팀으로 넘어온다. 그래서
Gitea가 합리적인 선택이 되는 경우는 보통 다음 중 하나다.

- **네트워크 격리가 필요한 경우**: 소스코드가 외부 클라우드에 나가면 안 되는 보안/컴플라이언스 요구사항이 있을 때
- **비용 구조상 자체 인프라가 이미 있는 경우**: 온프레미스 서버를 이미 운영 중이라 추가 SaaS 비용을 줄이고 싶을 때
- **팀 규모가 작고 운영 부담을 감당할 수 있을 때**: 반대로 팀이 커지고 CI/CD, 코드 리뷰 도구, 이슈 트래커까지 통합적으로 필요해지면 자체 호스팅의 관리 비용이 SaaS 대비 급격히 커진다

즉 "가볍다"는 장점은 도입 이유가 아니라 도입 이후에 체감하는 결과일 뿐이고, 실제 결정은
**가용성 책임을 누가 지는가**로 내려야 한다.

## 기존 원격 저장소에서 마이그레이션할 때: 왜 한 번에 끊지 않는가

기존에 GitWeb 같은 걸 쓰고 있다가 Gitea로 옮길 때, 바로 전환하지 않고 두 원격을 동시에
운영하는 방법이 있다.

```bash
git remote add gitea <Gitea 저장소 URL>
git push origin <branch>
git push gitea <branch>
```

이렇게 하면 로컬 저장소 하나에 `origin`(기존)과 `gitea`(신규) 두 원격이 연결된다. 이 방식이
안전한 이유는, 새 인프라(Gitea)가 안정화되기 전까지는 언제든 기존 원격으로 롤백할 수 있는
경로를 남겨두기 때문이다. 마이그레이션 중 신뢰할 수 없는 새 시스템을 "유일한 원격"으로
바로 승격시키면, 신규 시스템에 장애가 생기는 순간 협업이 전면 중단된다 — 두 원격을 병행
운영하는 기간은 그 위험을 없애는 완충 구간이다. 신규 시스템이 충분히 안정화됐다고 판단되면
그때 기존 원격을 제거한다.

## 결론

원격 저장소를 쓰는 이유는 협업과 백업이고, GitHub 대신 자체 호스팅을 택하는 이유는 "가벼워서"가
아니라 "가용성 책임을 우리가 직접 지는 게 더 낫다고 판단해서"여야 한다. 그리고 인프라를
옮길 때는 항상 롤백 경로(이 경우 이중 remote)를 먼저 확보하고 전환하는 게 안전하다.
