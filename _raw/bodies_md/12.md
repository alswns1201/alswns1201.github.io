예외(Excepiton)에 대해서 알아보기 전에, 에러(Error)와 예외(Exception)에 대한 구분 부터 하자면, 에러는 java.lang.Error 클래스의 하위 클래스들 입니다. JVM에서 주로 발생시키기 때문에 코드에서 잡아서는 안되며 이러한 부분 들은 예외처리를 할 수 없습니다.

### Exeption 예외

예외의 기본 원칙은 잡아서처리 하거나 , 처리할수 없다면 밖으로 예외를 return 하여 알려야 합니다.

기본적으로 예외에는 체크-예외(Exception) 와 언체크 -예외(Error) 가 존재 합니다.  
단 **RuntimeException은 Exception의 하위 예외 객체이지만 언체크 예외입니다.** 이름을 따서 주로 **런타임 예외** 라고 합니다.

#### **체크드 예외 vs 언체크드 예외**

**체크드 예외** : 외부 시스템과의 상호작용에서 발생할 수 있는 예외입니다. 예를 들어, 파일 I/O 작업이나 데이터베이스 연결에서 발생할 수 있는 예외는 체크드 예외로 처리해야 합니다. 컴파일러가 이를 반드시 처리하도록 요구합니다.

**언체크드 예외** : 주로 잘못된 코드나 예기치 못한 상황에서 발생하는 예외입니다. 예를 들어, 배열의 범위를 벗어난 인덱스에 접근하거나, null 값을 참조하려고 할 때 발생하는 예외입니다. 언체크드 예외는 코드 개선을 통해 발생하지 않도록 예방해야 합니다.

#### **결론**

  * 체크드 예외는 프로그램 외부에서 발생할 수 있는 예외로, 반드시 처리해야 하므로 throws나 try-catch 구문을 사용해야 합니다. 
  * 언체크드 예외는 개발자의 실수나 잘못된 코드에서 발생하는 예외로, 컴파일 시점에서 처리할 필요가 없지만, 발생 시 프로그램이 종료될 수 있습니다.



### Spring 구조 에서의 Exception

  1. DispathcerServlet 전의 Filter에서 발생하는 예외
  2. DispatcherServlet 내에서 발생하는 예외 (Controller , Servcie ,Repository)

Spring에서는 HandlerExceptionResolver를 제공하여 예외 처리를 할 수 있으며 자동으로 주입하는 어노테이션을 제공하고 있습니다.

### @ExceptionHandler (Controller에서의 처리)

@ExceptionHandler 의 예시로 Spring boot 환경에서 Entity를 조회 할 경우 간단하게 Not FOUND 를 처리해 보겠습니다. EntityNotFoundException의 경우 따로 class로 만들어 활용 하였습니다.  RuntimeException을 상속받아 적용한 이유는 이 예외가 체크 예외가 아닌 언체크 예외이기 때문에 체크-예외(Exception )취급되기를 원하기 때문입니다.
    
    
    @Getter
    @ToString
    public class EntityNotFoundException extends RuntimeException{
    
        private String message;
        private int code;
    
        public  EntityNotFoundException(String message){
            super(message);
            this.message = message;
            this.code = 404;
        }
        
    }

예외 처리 위치는 애플리케이션의 특성과 예외의 종류에 따라 결정해야 합니다. 서비스 계층에서 예외를 처리하는 것이 적절한 경우도 있고, 컨트롤러에서 처리하는 것이 적절한 경우도 있습니다.
    
    
        public TodoDTO read(Long mno){
    
            Optional<TodoDTO> result =  todoRepository.getDTO(mno);
             // TodoDTO todoDTO =  result.orElseThrow();
            // 컨트롤러 입장에서 본다면 서비스에서 예외를 처리하는것은 바람직 하지 않다.
            TodoDTO todoDTO = result.orElseThrow(()-> new EntityNotFoundException("todo not found"));
            return  todoDTO;
        }

위는 서비스에서 처리를 하였다면 , Controller에서 예외를 처리하는 @ ExceptionHandler 는 기본 적으로 Controller 내부에서 사용되며, UserController 안에서 일어나는 EntityNotFoundException 발생에만 적용되게 구현해 봅시다.
    
    
    @RestController
    public class UserController {
        @ExceptionHandler(EntityNotFoundException.class)
        public ResponseEntity<?> handleEntityNotFound(EntityNotFoundException exception) {
            Map<String, String> errors = Map.of("message", "Entity Not Found in UserController");
            return new ResponseEntity<>(errors, HttpStatus.NOT_FOUND);
        }
    }

그렇다면 전역(전체)적으로 관리해서 예외처리를 적용하는 방법은 무엇일지 알아보자.

###  @ExceptionHandler를 사용하기 (@ControllerAdvice , @RestControllerAdvice )

아래 코드를 보면 @RestControllerAdvice 를 가지고 예외처리를 구현하였습니다. 다른 parameter에 대한 예외처리를 가진 handleArgsException를 구현하였습니다. @RestControllerAdvice 는 전역으로 처리를 해주기 떄문에 해당 어노테이션이 적용된 클래스안에  @ExceptionHandler로 적용된 예외는 다른 곳에서도 적용이 된다.
    
    
    @RestControllerAdvice
    @Log4j2
    public class APIControllerAdvice {
    
        @ExceptionHandler(MethodArgumentNotValidException.class)
        public ResponseEntity<?> handleArgsException(MethodArgumentNotValidException exception){
            Map<String, Object> errors = new HashMap<>();
            exception.getBindingResult().getFieldErrors().forEach(fieldError ->
                errors.put(fieldError.getField(),fieldError.getDefaultMessage()));
            return new ResponseEntity<>(errors, HttpStatus.BAD_REQUEST);
        }
    
        @ExceptionHandler(MethodArgumentTypeMismatchException.class)
        public ResponseEntity<?> handleArgsException(MethodArgumentTypeMismatchException exception){
            Map<String, Object> errors = new HashMap<>();
            errors.put("error","Type Mismatch");
            errors.put(exception.getName(),exception.getValue()+"is not valid value");
            return  new ResponseEntity<>(errors,HttpStatus.BAD_REQUEST);
        }
    }

  
@RestControllerAdvice를 사용할 때는 이미 @Controller의 특성이 포함되어 있기 때문에, @Controller를 추가로 선언하지 않아도 됩니다. 위 코드의 예제는 restAPI에 대한 처리라서 @RestControllerAdvice 를 해주었는데 @ControllerAdvice 라는 어노테이션 역시 비슷한 성격의 어노테이션 이다. 둘의 차이를 정리해 봅시다.

  * **@RestControllerAdvice** : @ResponseBody가 포함된 메서드를 자동으로 적용하여 JSON 응답을 생성합니다.JSON 형식의 데이터를 반환하는 RESTful 서비스에서 사용됩니다.
  * **@ControllerAdvice** : 주로 HTML 뷰를 반환하는 컨트롤러에서 사용됩니다.



#### 순서 보장 (내부 @ExceptionHandler > 전역 @ExceptionHandler )

이미 @ExceptionHandler로 동일한 예외가 있다면? @RestControllerAdvice로 전역으로 구현을 해놨는데 같은 예외에 대해서   
특정 컨트롤러 내부에 @ExceptionHandler 가 따로 정의 되어 있다면, 결과는 내부에 구현된 @ExceptionHandler 가 우선적으로 적용된다.

### 예외 처리 Throw 에 대한 개인적인 결론

**기본 원칙:**

  * 예외는 발생 가능성이 있는 가장 가까운 곳에서 처리하는 것이 좋습니다.
  * 예외 처리 로직은 비즈니스 로직과 분리되어야 합니다.
  * 예외는 의미 있는 정보를 담고 있어야 합니다.
  * @ControllerAdvice는 예상치 못한 예외나 공통적으로 처리해야 하는 예외에 사용합니다.



**관심 분리** 가 핵심이며, 해당 예외가 발생한 곳을 명확히 하기 위해서 예외와 연관 있는 서비스에서 try catch 를 통해서 예외 상항에 대한 로깅을 하는것이 좋습니다. 

예를 들어 A 서비스에서 B서비스를 사용하고 있는 로직이 있을때, A 컨트롤러에서 A서비스를 호출 할 것 입니다.
