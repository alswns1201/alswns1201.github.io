테스트 코드는 “돌려보기 전에 확인하는 습관”이다. TDD(Test-Driven Development)는 이 습관을 하나의 개발 리듬으로 만든다.  
‘테스트를 먼저 짜고, 코드로 그 테스트를 만족시킨다’ — 단순하지만 지키긴 어렵다.

아래는 Spring 환경에서 TDD를 실무적으로 접근하는 방법들이다. TestCode를 `어떻게`먼저 작성을 하지? 라는 의문을 가졌었다.  
기본적인 골격(Service,Repository 등)은 구현을 한뒤에 TDD를 진행하면 된다. 즉, TDD를 구현하며 필요한 부분을 채워나가는 의미가 TDD라고 생각한다.

* * *

## 🧪 1. 단위 테스트 vs 통합 테스트

구분단위 테스트(Unit Test)통합 테스트(Integration Test)  목적 | 로직 단위 검증 | 여러 모듈이 함께 동작하는지 확인  
---|---|---  
속도 | 빠름 | 느림  
의존성 | 없음 (@Mock 사용) | 실제 Bean, DB, API 사용  
예시 | Service, Util, Domain | Controller, Repository, 외부 연동  
  
> 현실에서는 단위 테스트로 비즈니스 로직을 보호하고,  
> 통합 테스트로 시스템 연결 상태를 보장한다.  
> **둘 다 있어야 안전하다.**

* * *

## 🧩 2. @ExtendWith(MockitoExtension.class)

단위 테스트에서 가장 많이 쓰는 조합이다.  
MockitoExtension을 붙이면 @Mock, @InjectMocks 등을 사용할 수 있다.
    
    
    @ExtendWith(MockitoExtension.class)
    class OrderServiceTest {
    
        @Mock
        private OrderRepository orderRepository;
    
        @InjectMocks
        private OrderService orderService;
    
        @Test
        void 주문_생성_테스트() {
            // given
            Order order = new Order("A001", 1000);
            when(orderRepository.save(any(Order.class))).thenReturn(order);
    
            // when
            Order result = orderService.createOrder("A001", 1000);
    
            // then
            assertEquals("A001", result.getOrderId());
        }
    }

여기서 핵심은 “**가정하고, 그 가정대로 동작하는지 확인** ”하는 것이다.  
when(...).thenReturn(...)은 현실의 DB나 API를 쓰지 않고 **시뮬레이션** 하는 방식이다.

## 🌐 3. @WebMvcTest — Controller만 테스트하기

@WebMvcTest는 Spring MVC의 **Controller 계층만 로드** 한다.  
Service, Repository는 Mock으로 대체된다.
    
    
    @WebMvcTest(OrderController.class)
    class OrderControllerTest {
    
        @Autowired
        private MockMvc mockMvc;
    
        @MockBean
        private OrderService orderService;
    
        @Test
        void 주문_조회_API_테스트() throws Exception {
            OrderResponse response = new OrderResponse("A001", 1000);
            when(orderService.getOrder("A001")).thenReturn(response);
    
            mockMvc.perform(get("/orders/A001"))
                    .andExpect(status().isOk())
                    .andExpect(jsonPath("$.orderId").value("A001"))
                    .andExpect(jsonPath("$.amount").value(1000));
        }
    }

> @WebMvcTest는 Controller의 요청/응답 흐름을 검증할 때 유용하다.  
> 실제 서비스나 DB 연결이 필요하지 않다.

## 🔗 4. 외부 API TDD — MockWebServer 활용

외부 API를 연동하는 코드는 테스트가 특히 까다롭다.  
실제 서버를 호출하면 테스트가 느려지고, 예측 불가능해진다.  
이럴 때 MockWebServer를 이용하면 API 응답을 가짜로 만들어낼 수 있다.
    
    
    class ExternalApiServiceTest {
    
        private MockWebServer mockWebServer;
        private ExternalApiService apiService;
    
        @BeforeEach
        void setup() throws IOException {
            mockWebServer = new MockWebServer();
            mockWebServer.start();
            String baseUrl = mockWebServer.url("/").toString();
            apiService = new ExternalApiService(baseUrl);
        }
    
        @AfterEach
        void tearDown() throws IOException {
            mockWebServer.shutdown();
        }
    
        @Test
        void 외부_API_응답_테스트() throws Exception {
            String mockResponse = "{\"status\":\"OK\",\"data\":\"success\"}";
            mockWebServer.enqueue(new MockResponse()
                    .setBody(mockResponse)
                    .addHeader("Content-Type", "application/json"));
    
            ApiResponse result = apiService.callExternalApi();
    
            RecordedRequest request = mockWebServer.takeRequest();
            assertEquals("/external/api", request.getPath());
            assertEquals("success", result.getData());
        }
    }

> MockWebServer는 네트워크 없이도 외부 API를 흉내낼 수 있다.  
> 테스트 속도는 빠르고, 시나리오도 마음대로 조작 가능하다.

## ⚙️ 5. TDD 실전 접근법

  1. **가정 세우기** — “이 입력이면 이렇게 동작해야 한다.”
  2. **테스트 작성** — 그 가정이 코드로 명확히 표현되게 만든다.
  3. **구현하기** — 테스트를 통과할 최소한의 코드만 작성한다.
  4. **리팩터링** — 테스트가 깨지지 않는 선에서 개선한다.



이 리듬을 꾸준히 반복하는 게 핵심이다.
    
    
    // Given
    when(paymentService.pay(any())).thenReturn(true);
    
    // When
    boolean result = orderService.processPayment("A001");
    
    // Then
    assertTrue(result);
    verify(paymentService).pay(any());

> 이런 식으로 테스트를 짜면 “의존하는 모듈이 이미 잘 작동한다고 가정”하고  
> 내 로직만 집중해서 검증할 수 있다.

* * *

## 📘 마무리

TDD는 완벽한 개발 방식을 강요하는 게 아니다.  
대신, “확신을 얻는 속도”를 높여주는 도구다.  
테스트가 있으면 리팩터링이 두렵지 않고,  
협업 중 코드 변경에도 자신 있게 움직일 수 있다.
