서비스에서 쓰는 이미지를 저장하려고 S3 버킷을 만들었다.
버킷을 만들고 나서 "그럼 이미지 URL은 뭘 쓰면 되지?"를 데브옵스에 물어봤더니 두 가지 방식을 안내받았고, 그중 CloudFront 방식을 골랐다.
버킷 생성 과정과 왜 그렇게 골랐는지를 정리해 둔다.

> 글에 나오는 버킷 이름과 도메인은 예시 이름으로 바꿔 적었다.

## 왜 이미지를 S3에 두나

이미지를 애플리케이션 서버 디스크에 저장하면 금방 문제가 생긴다.

| | 서버 로컬 디스크 | S3 |
|---|---|---|
| 서버 여러 대 | 서버마다 가진 파일이 다름 | 어디서 접근해도 같은 파일 |
| 서버 교체/재배포 | 파일이 같이 날아갈 수 있음 | 서버와 무관하게 남아 있음 |
| 용량 | 디스크 크기만큼 | 사실상 무제한, 쓴 만큼 과금 |
| 내구성 | 디스크 고장 = 유실 | 99.999999999%(9가 11개) 설계 |

서버는 상태 없이(stateless) 두고, 파일은 서버 밖에 따로 두는 게 편하다. 그 "밖"이 S3다.

## S3 기본 개념만 짧게

S3는 폴더 트리가 있는 파일 시스템이 아니라 **키(이름) → 데이터**를 저장하는 객체 저장소다.

```
버킷:  s3-myservice-content-image        ← 저장소 하나 (이름은 전 세계에서 유일해야 함)
객체:  키   = banner/2026/main.png        ← 파일의 "전체 이름"
       값   = (이미지 바이트)
```

- 콘솔에 `banner/2026/` 같은 폴더가 보이지만, 실제로는 **키에 `/`가 들어 있을 뿐**이다.
- 같은 키로 다시 올리면 **덮어쓴다.**

## 버킷 생성 과정 (AWS 콘솔)

S3 콘솔 → **버킷 만들기**에서 정하는 항목들이다.

### 1. 버킷 이름 / 리전

- **이름**: 전 세계 모든 AWS 계정을 통틀어 유일해야 하고, 만든 뒤에는 바꿀 수 없다. 소문자·숫자·`-`만 쓴다.
  용도가 드러나게 `s3-{서비스}-content-image` 같은 식으로 지었다.
- **리전**: 서비스 서버와 같은 곳으로 한다. 여기서는 서울(`ap-northeast-2`).
  리전은 버킷 URL에도 들어간다 (`https://{버킷}.s3.ap-northeast-2.amazonaws.com/...`).

### 2. 객체 소유권 — ACL 비활성화 (권장)

예전에는 객체 하나하나에 ACL(접근 제어 목록)을 붙여 권한을 줬는데, 지금은 **ACL을 끄고 버킷 소유자가 모든 객체를 소유**하는 게 기본값이자 권장값이다.
권한은 ACL 대신 **버킷 정책**과 **IAM 정책**으로만 관리한다.

### 3. 퍼블릭 액세스 차단 — 모두 차단 유지

기본값은 **"모든 퍼블릭 액세스 차단" 체크**다. 이걸 켜 두면 URL을 알아도 외부에서 그냥 열 수 없다.

이미지를 사용자에게 보여 줘야 하니 "풀어야 하나?" 싶은 지점이 바로 여기다.
이 설정을 어떻게 할지가 아래 1번/2번 방식의 차이로 이어진다.

### 4. 버전 관리

켜 두면 덮어쓰거나 지운 파일의 이전 버전이 남아서 되살릴 수 있다. 대신 이전 버전도 저장 용량으로 과금된다.

### 5. 기본 암호화

기본값인 **SSE-S3**(S3가 관리하는 키로 서버 측 암호화)를 그대로 둔다. 따로 설정하지 않아도 새로 올라가는 객체는 암호화된다.

## 이미지 URL은 어떻게? — 데브옵스가 안내해 준 두 가지

### 1번: S3 URL 직접 사용 (간단)

```
https://s3-myservice-content-image.s3.ap-northeast-2.amazonaws.com/xxx.png
```

- 바로 쓸 수 있다.
- 다만 이렇게 쓰려면 **버킷을 퍼블릭으로 열어야** 한다 → 보안 점검에서 지적될 수 있다.
- URL에 S3 주소가 그대로 박히기 때문에, **나중에 방식을 바꾸면 URL도 다 바뀐다.**

### 2번: CDN(CloudFront) URL 사용 (권장)

```
https://dxxxx.cloudfront.net/xxx.png
→ 추후 https://img.example.com/xxx.png 같은 자체 도메인 연결 가능
```

- **버킷은 비공개로 두고, CDN으로만 노출**한다 → 보안상 안전하다.
- CloudFront가 캐시해 주니 로딩도 빠르다.

## 2번(CloudFront)을 고른 이유

```
1번:  사용자 ──────────────────────────> S3 (퍼블릭으로 열어 둠)
2번:  사용자 ──> CloudFront(엣지 캐시) ──> S3 (비공개, CloudFront만 접근 가능)
```

### 버킷을 열지 않아도 된다

2번에서는 버킷의 퍼블릭 액세스 차단을 **켜 둔 채로** 이미지를 보여 줄 수 있다.
S3에 "CloudFront에서 오는 요청만 읽기 허용"이라는 버킷 정책을 걸기 때문이다. 이걸 **OAC(Origin Access Control)**라고 한다.

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "cloudfront.amazonaws.com" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::s3-myservice-content-image/*",
  "Condition": {
    "StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::{계정ID}:distribution/{배포ID}"
    }
  }
}
```

- `Principal`: CloudFront 서비스에게
- `Action`: 읽기(`GetObject`)만
- `Condition`: 그중에서도 **우리 배포(distribution)에서 온 요청만**

이렇게 하면 S3 URL로 직접 들어오는 요청은 막히고, CloudFront를 통한 요청만 통과한다.

### 빠르다

CloudFront는 전 세계 엣지 서버에 이미지를 캐시해 두고, 사용자와 가까운 곳에서 내려준다.
같은 이미지를 여러 사용자가 볼수록 S3까지 가는 요청이 줄어서 S3 요청·전송 비용도 아낄 수 있다.

### URL이 S3에 묶이지 않는다

자체 도메인(`img.example.com`)을 연결해 두면, 뒤에서 저장소를 바꾸더라도 사용자에게 나가는 URL은 그대로 유지할 수 있다.
1번은 S3 주소 자체가 URL이라 이런 여지가 없다.

## 같이 정한 것: DB에는 key만 저장

URL 방식이 바뀔 수 있다는 걸 생각하면, DB에는 전체 URL보다 **객체 key만 저장**하는 편이 낫다.

```
DB:      banner/2026/main.png
응답 시:  {이미지 도메인} + "/" + key  →  https://dxxxx.cloudfront.net/banner/2026/main.png
```

이미지 도메인은 설정값으로 빼 두면, 나중에 `img.example.com`을 연결해도 설정만 바꾸면 된다.

## 한 줄 정리

> 이미지는 S3에 두되 버킷은 비공개로 유지하고, 사용자에게는 CloudFront(OAC)를 통해서만 보여 준다.
> 보안 점검에 걸리지 않고, 캐시로 빠르며, 나중에 도메인이나 저장소가 바뀌어도 URL을 지킬 수 있다.
