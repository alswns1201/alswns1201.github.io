#### [1] 세션 : 편안한 휴식 시간을 지켜줄 안정적인 백엔드

이 강의는 NHN Dooray의 정지범 님의 이야기 였다. Dooray 팀에서 고민했던 이야기를 담아 이야기 해주셨다. 사용자가 점점 많아 지면서 서버부하 및 장애가 발생하기 시작.두레인은 설계 단계에서 운영을 고민하며 최적의 서버를 구성했고, 빠른 장애 대응에 신경을 썼다고 한다.  
주요 고민 내용을 메모리 오류 주요 서비스 원인 로 세분화 하여 내용을 정리해 보았다

#### 메모리 자원의 효율적인 관리

JVM 의 Garbage Collector 는 Unreachable Object 를 우선적으로 메모리에서 제거하여 메모리 공간을 확보한다. Unreachable Object 란 Stack 에서 도달할 수 없는 Heap 영역의 객체를 말하는데, 지금의 예제에서 "https://" 문자열과 같은 경우가 되겠다. 아주 간단하게 이야기해서 이런 경우에 Garbage Collection 이 일어나면 Unreachable 오브젝트들은 메모리에서 제거된다.

👉 이러한 가비지 콜렉션 역할이 비 정상적으로 동작할때 우리는 메모리 오류라고 부른다.

Dooray에서는 장애발생시
    
    
    장애발생 - > 전파 → 관제팀에서 모니터링 → 로그 확인 → 덤프 남기기 → 서버 재기동 

위 와 같은 절차로 행동하며 해결해 나간다고 합니다.

해결하다 보니 방안을 모색하는 방법이 비슷하다고 판단하였고, 이를 배치/ 크론탭을 이용하여 반복적인 수행을 적용시켰다고 합니다.

  * 분당 한번씩 크론탭을 통해서 - process 확인 shell을 돌렸고 이상이 발생하면 서버를 재실행 시켰다.
  * JVM 실행 옵션을 추가하여 OutOfMemoryErorr를 적용하여 메모리 발생시 JVM Process를 Kill 하는 작업을 진행하였다

#### 주요 서비스 원인

두번째, 주요 서비스가 문제일 경우 이다.

cascading failure 라는 용어가 있다. 소수의 서버 문제가 점진적으로 퍼져 큰 문제로 발생하는 것을 뜻한다.

> 어떤 이유로든 서비스가 응답하지 않는 경우, 서비스에 요청을 반복적으로 보내면 대기시간이 길어지고 서비스에 불필요한 부하가 발생한다. 한 서비스의 부하는 다른 서비스의 부하로 이어지는데 이런 현상을 cascading failure라 한다.

Dooray의 로직 일부를 보여주었는데

![](https://blog.kakaocdn.net/dna/cGkee6/dJMcaivUlS9/AAAAAAAAAAAAAAAAAAAAAG7dgGWu839x3jgU9Y_1vUydrg0g3VprEVQbYTK-3ajq/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1788188399&allow_ip=&allow_referer=&signature=Ya7749Ko7v5XuVaCPklwuaWLVpQ%3D)

하나의 서버에서 문제가 생기면 다른 서비스의 부하로 번지는 것을 방지하기 위해서 **모든 문제를 가시화** 하는 것에 중점을 두었다고 한다.

가시화 방법

  * Spring boot Actuator 이용 - 메트릭
  * 그라파나 연동



Spring boot Actuator 는 헬스 체크 하는 기능이다. Dooray는 서버의 헬스 체크를 하기 위해 해당 기술을 이용 했다고 한다. 나중에 기회가 된다면 이용해 보고 싶다.✋

#### 🟠Spring boot Actuator

Actuator는 SpringBoot가 제공하는 기본적인 서버 모니터링 도구입니다. CPU사용량, 메모리사용량과 같은 간단한 자원 사용량부터 시작하여, Heap사용량, Hikari Datasource정보 등 많은 정보들을 제공하기 때문에, 이들을 적절히 사용한다면 서버의 자원을 지속적으로 모니터링할 수 있습니다.
    
    
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

[Spring 공식 문서](https://docs.spring.io/spring-boot/docs/3.0.x/actuator-api/htmlsingle/#httpexchanges) 에서 자세히 살펴 볼 수 있다 . /actuator 링크로 접속하게 되면 원하는 정보를 활용 할 수 있다고 한다.

Dooray에서는 측정 항목 대상을 **CPU 사용률** , **Active Thread** , **분당 Request 수** , **분당 메일 건수** 를 중점을 두었다고 한다.

#### 🟠HTTP 429

그 중 분당 Request 수를 이야기 하며 , HTTP 응답 오류 429(Too Many Requests)라는 개념도 설명해 주셨다. HTTP429

HTTP 429는 Error 응답이 아닌점,을 강조하였고 적용 가능한 API를 선정 하고, 많은 요청이 왔다는 Threshold(기준)점 선정 하였다고 한다.
    
    
    A가 B에게 응답을 던지고 기준점보다 많다면 429 응답처리를 적용 .

#### [2] 세션 :ES를 이용한 상품 검색 엔진 개발 일지

두번째 세션은 NHN COMMERCE 의 이야기를 전지일 님 , 기라성 님 두분이서 같이 진행을 해주셨다. 주로 ElasticSearch 엔진을 도입한 이유와 NHN COMMERCE에서 의 검색엔진 방식에 대해서 소개하고 있습니다.

#### ELK

ELK는 Elasticsearch, Logstash 및 Kibana를 의미 한다. NHN 커머스에서는 ELK 에 단일 목적 데이터 수집기 제품인 Beat 를 추가 Elastic Stack 이라고 부르고 있습니다.

![](https://blog.kakaocdn.net/dna/uFPBY/dJMcagdP1ci/AAAAAAAAAAAAAAAAAAAAAG9d4xyOr9Az-6Xvl-dqMHZ8ZVcd2ToVu2tiHmcCuL-M/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1788188399&allow_ip=&allow_referer=&signature=9gmeMhtzGUJFpgh2djOB%2FOQ%2BPK4%3D)

  * Logstash : 로그 스테이시는 실시간 파이프라인 기능을 가진 데이터 수집 엔진 오픈소스이다 데이터 수집의 역할을 맡고 있는데 원하는 형태로 데이터 입출력 변환까지 맡고 있어서 오버헤드가 컸다고 합니다. 이를 보완하기 위해서 Elastic 회사는 오로지 데이터의 수집만을 담당하는 경량화된 모듈인 Beats를 도입했다고 한다.
  * 👉 NHN 커머스는 Beat로 가공하고 필터링 하기 때문에 logstash 의 필요성이 없어 따로 쓰진 않고 Beats로만 데이터를 수집했다고 한다.



NHN SHOP BY 에서 의 업무 과정

  * 상품데이터들은 전부 Mysql DB에 저장
  * Mysql → Elasticsearch 로 데이터를 밀어 넣어주는 작업 진행
  * 색인 작업이 필요



![](https://blog.kakaocdn.net/dna/DqsWu/dJMcaivUlTb/AAAAAAAAAAAAAAAAAAAAABfURaIUrikAazOv050Zb8rhdZxnUye1WGXRP5LE6zNQ/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1788188399&allow_ip=&allow_referer=&signature=HdTTAGCBssXDKctuh%2BRVvYAwZLg%3D)

업무를 하며 고민한 내용 중 3가지를 소개 해 주셨습니다. 데이터 정합성 , 검색 품질, 성능 분석

#### 데이터 정합성

정합성을 맞추기 위해서 두가지 방식의 스케줄러를 반영했다고 합니다.

전체색인 : DB에 저장된 모든상품 데이터를 저장  
부분색인 : 실시간으로 수정된 상품에 대한 데이터 수정

  1. mysql의 데이터를 하나의 csv파일로 만들어 검색엔진에 밀어넣고 Elasticsearch에 수행 하며 이때 ElasticSearch의 alias 를 이용하여 백업용 idex를 보관을 진행.
  2. 매일 새벽에 모든 상품에 대해서 전체색인을 진행 하면서 부분색인이 진행 중인지 판단해서 중복으로 색인 발생을 방지 / 부분색인 에서는 SPRING 스케줄러 10초주기로 수정된 상품에 대해 진행.

#### 검색품질 성능

데이터 검색시 필요 없는 데이터가 검색되는 것을 방지 하기 위해서 형태소의 분리에 따라 검색이 달라질 수 있다. 라는 점을 인지하고 사용자 정의 와 동의어 사전 도입 를 도입 하여 해결 했다고 함.

사용자 사전 정의 : 사용자 사전 정의에 등록이 되어 있다면 형태소 분석이 되지 않게 방지한다.  
예) 운동화라는 단어는 운동 / 화 로 형태소 분석이 되지 않게 방지.

동의어 사전 도입 : 검색 했을 시 동의어 사전에 등록된 데이터들을 활용하여 검색에 적용

=>사용자/동의어 사전을 서버에 배포하기 위해서 자동화 배포
