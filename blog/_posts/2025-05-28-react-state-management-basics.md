React를 쓰다 보면 상태 관리 도구가 늘어난다 — `useState`에서 시작해 `useContext`, 그리고
결국 Zustand나 Redux 같은 외부 스토어까지. 이 확장이 필요한 이유를 이해하려면 먼저
React의 핵심 동작 원리부터 짚어야 한다: **상태가 바뀌면 그 상태를 가진 컴포넌트가
다시 렌더링된다.** 이 사이클을 잘 통제하는 게 상태 관리 도구를 고르는 기준이다.

## 컴포넌트화가 주는 것과 대가

React의 강점은 컴포넌트화다 — 독립적인 UI 조각을 조합해서 복잡한 화면을 만든다. 재사용성과
유지보수성이 좋아지는 대신, 상태를 어느 컴포넌트가 들고 있어야 하는지 매번 판단해야 하는
비용이 생긴다. 이 판단을 잘못하면 두 가지 방향으로 문제가 난다: 상태를 너무 낮은
컴포넌트에 두면 형제 컴포넌트끼리 공유가 안 되고(props를 위로 끌어올려야 함), 너무 높은
곳에 두면 관련 없는 하위 트리까지 리렌더링이 전파된다.

## useState — 언제까지 이걸로 충분한가

`useState`는 한 컴포넌트 안에서만 의미 있는 상태(입력값, 토글, 카운터, 모달 열림/닫힘)에
적합하다. 판단 기준은 단순하다: **이 상태를 다른 컴포넌트와 공유할 필요가 있는가?** 없다면
useState로 충분하고, 굳이 상위로 끌어올리거나 전역화할 이유가 없다. 조기에 전역 상태로
승격시키는 건 오히려 컴포넌트의 독립성을 깨는 과잉 설계다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const increment = () => setCount(prev => prev + 1);
  return <button onClick={increment}>{count}</button>;
}
```

## useEffect — 렌더링에 "반응"하는 코드, 렌더링을 "일으키는" 코드가 아니다

`useEffect`는 사이드 이펙트(데이터 페칭, DOM 직접 조작, 구독, 타이머) 를 다룬다. 핵심은
useState와의 관계다: useState의 상태 변경이 리렌더링을 유발하고, 리렌더링이 끝난 뒤에야
useEffect가 의존성 배열을 확인해서 실행 여부를 결정한다. 즉 useEffect는 렌더링을
직접 일으키지 않고, 렌더링에 반응할 뿐이다.

```jsx
useEffect(() => {
  fetchPost(postId).then(setPost);
}, [postId]); // postId가 바뀔 때만 재실행
```

여기서 흔한 실수는 의존성 배열을 누락하거나 잘못 넣어서, 필요 이상으로 자주 실행되거나
반대로 갱신이 안 되는 것이다. 의존성 배열은 "언제 재실행할지"를 정하는 게 아니라
"이 effect가 실제로 참조하는 값이 무엇인지"를 정직하게 선언하는 것에 가깝다 — 여기서
거짓말을 하면(실제로 쓰는 값을 배열에서 빼면) stale closure 버그가 생긴다.

## useCallback — 최적화 도구지, 기본값이 아니다

컴포넌트가 리렌더링되면 그 안에 정의된 함수도 매번 새로 생성된다. 이 새 함수가 자식
컴포넌트에 prop으로 전달되면, 자식이 `React.memo`로 감싸져 있어도 "prop이 바뀌었다"고
판단해 불필요하게 리렌더링된다. `useCallback`은 의존성이 바뀌지 않는 한 같은 함수
인스턴스를 유지해서 이 문제를 막는다.

```jsx
const handleClick = useCallback(() => setCount(c => c + 1), []);
```

**주의할 점**: `useCallback` 자체도 공짜가 아니다 — 의존성 비교 비용이 든다. 자식이
`React.memo`로 감싸져 있지 않다면 useCallback을 써도 어차피 자식은 리렌더링되므로 아무
효과가 없다. "함수를 자식에 prop으로 넘기고, 그 자식이 메모이제이션되어 있을 때"라는
조건이 성립할 때만 의미가 있는 최적화이지, 모든 함수에 기본으로 씌우는 습관은 오히려
코드만 복잡하게 만든다.

## useState의 한계와 전역 상태로 넘어가는 시점

컴포넌트 트리가 깊어지고, 로그인 사용자 정보나 장바구니처럼 서로 관련 없는 여러
컴포넌트가 같은 상태를 읽고 써야 할 때 useState만으로는 props를 여러 단계로 계속
전달해야 하는 props drilling이 발생한다. 이때 선택지는 크게 세 가지다.

- **React Context API**: 추가 설치 없이 되고, 자주 안 바뀌는 데이터(테마, 로그인 유저)에 적합. 단점은 Provider의 value가 바뀌면 그 값을 쓰지 않는 하위 컴포넌트까지 리렌더링될 수 있다는 것.
- **Zustand/Recoil/Jotai**: Redux보다 가볍고, 선택자(selector) 기반으로 구독해서 필요한 컴포넌트만 리렌더링되게 만들 수 있다.
- **Redux**: 가장 무겁지만 예측 가능한 상태 변경, 미들웨어, 강력한 디버깅 도구를 제공 — 상태 변경 로직이 복잡하고 팀 규모가 큰 프로젝트에 적합.

이 선택은 "지금 얼마나 자주, 얼마나 넓게 공유되는 상태인가"로 판단하는 게 맞다.
프로젝트 초반부터 Redux를 깔고 시작하는 것도, 커진 다음에도 useState로 억지로 끌어올리는
것도 둘 다 실수다.

## 요약

- 상태를 어디에 둘지는 "공유 범위"로 판단한다: 컴포넌트 내부 → useState, 트리 전역이지만 자주 안 바뀜 → Context, 자주 바뀌고 넓게 공유됨 → 외부 스토어
- useEffect는 렌더링을 일으키는 게 아니라 렌더링에 반응한다 — 의존성 배열은 실행 조건이 아니라 "이 effect가 실제로 참조하는 값"의 정직한 선언이다
- useCallback은 "자식이 memo로 감싸져 있고 함수를 prop으로 넘길 때"만 의미 있는 최적화다
