*(원제 "sonarqube". 원문은 로컬 설치 절차 메모였는데, 왜 이 도구를 코드 리뷰와
별개로 두는지에 대한 맥락을 추가했습니다.)*

## 설치와 연동

Docker로 로컬에 바로 띄워볼 수 있다.

```bash
docker run -d --name sonarqube -p 9000:9000 sonarqube:community
# 초기 접속 계정: admin/admin
```

프로젝트를 생성하고 토큰을 발급받은 뒤, `build.gradle`에 플러그인을 추가한다.

```groovy
plugins {
    id 'java'
    id 'org.sonarqube' version '4.4.1.3373'
}
```

빌드 후 아래 명령으로 분석 결과를 SonarQube 서버로 전송한다.

```bash
./gradlew sonar "-Dsonar.projectKey=appBackend" \
  "-Dsonar.host.url=http://localhost:9000" \
  "-Dsonar.login=<발급받은 토큰>"
```

## 왜 코드 리뷰와 별개로 정적 분석 도구가 필요한가

IntelliJ에서 SonarLint 플러그인을 붙이면 코드를 작성하는 동안 바로 노란 줄로 문제를
표시해준다 — 즉각적인 피드백이라는 점에서 유용하다. 하지만 SonarQube 서버까지 따로
두는 이유는 다르다. **IDE 플러그인은 그 순간 그 파일만 본다.** SonarQube 서버는
프로젝트 전체를 대상으로 하고, 시간에 따른 추이(코드 스멜이 늘고 있는지 줄고 있는지),
팀 전체의 품질 게이트(quality gate) 통과 여부, PR 단위의 신규 이슈만 걸러보는 기능
같은 걸 제공한다. 로컬 IDE에서는 "지금 이 파일이 괜찮은가"만 알 수 있지만, SonarQube는
"이 프로젝트가 시간이 갈수록 건강해지고 있는가"라는 다른 질문에 답한다.

## 정적 분석이 잡아주는 것과 못 잡는 것

정적 분석 도구가 강한 영역은 명확하다 — null 체크 누락, 사용하지 않는 변수, 복잡도가
지나치게 높은 메서드, 보안 취약 패턴(예: SQL 인젝션 가능성이 있는 문자열 조합) 같은
**패턴으로 감지 가능한 문제들**이다. 반대로 못 잡는 것도 명확하다 — 이 로직이 비즈니스
요구사항에 맞는지, 이 API 설계가 팀 컨벤션에 맞는지 같은 **맥락이 필요한 판단**은
사람이 하는 코드 리뷰의 영역이다. SonarQube를 도입한다고 코드 리뷰가 필요 없어지는
게 아니라, 리뷰어가 "이 변수 안 쓰네요" 같은 기계적으로 잡을 수 있는 지적에 시간을
안 쓰고 설계/맥락 판단에 집중할 수 있게 해주는 역할에 가깝다.

## 실무에서 흔히 놓치는 것: Quality Gate를 CI에 묶기

로컬에서 가끔 돌려보는 것과, CI 파이프라인에 Quality Gate를 통과해야만 머지되게
막아두는 것은 완전히 다른 효과를 낸다. 전자는 "확인용"이고 후자는 "강제성"이 있다.
팀 전체의 코드 품질 기준을 실제로 지키게 하려면, 결국 PR이 Quality Gate를 통과하지
못하면 머지가 막히는 구조로 CI에 통합하는 게 핵심이다 — 사람이 매번 "SonarQube
확인했어?"라고 물어보는 방식은 오래가지 못한다.

## 정리

- SonarQube는 IDE 린트와 달리 프로젝트 전체·시간 추이·PR 단위 신규 이슈를 본다.
- 패턴으로 잡을 수 있는 문제(복잡도, 미사용 코드, 보안 패턴)는 정적 분석이, 맥락이
  필요한 판단(설계, 요구사항 부합)은 여전히 코드 리뷰가 담당한다.
- 로컬에서 가끔 돌리는 것과 CI Quality Gate로 강제하는 것은 효과가 다르다 — 후자여야
  실제로 기준이 지켜진다.
