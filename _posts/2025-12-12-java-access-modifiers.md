접근 제어자는 "어디까지 접근을 허용할 것이냐"를 결정한다. 네 가지 키워드 자체는
단순하지만, 실무에서 중요한 건 표를 외우는 게 아니라 **왜 기본값이 가장 제한적인
`private`이어야 하는가**, 그리고 이게 설계에 어떤 영향을 주는가다.

## private — 클래스 내부에서만

```java
class User {
    private String name;
    private void validate() { ... }
}
```

같은 클래스 안에서만 접근 가능. 필드는 거의 대부분 `private` + getter/setter(또는
비즈니스 메서드)로 처리하는 게 기본이다. 객체지향에서 캡슐화의 핵심 — 내부 상태를
외부가 직접 건드리지 못하게 막아서, 상태 변경 경로를 그 클래스가 제공하는
메서드로만 한정한다.

## (default) — 같은 패키지 내부 공개

```java
class UserService { ... } // 접근 제어자를 안 쓰면 default
```

같은 패키지에 있는 클래스들끼리는 접근 가능, 다른 패키지에서는 불가. 외부에 노출할
필요 없는 내부 유틸 클래스나, **패키지를 하나의 모듈 경계로 쓰고 싶을 때** 유용하다.

## protected — 패키지 + 상속 관계

```java
class User {
    protected String role;
}
class Admin extends User {
    void checkRole() {
        System.out.println(role); // 가능
    }
}
```

default 범위(같은 패키지)에 더해, 다른 패키지에 있어도 **상속받은 클래스라면**
접근할 수 있다. 상속 구조에서 서브클래스가 필요한 정보만 열어줄 때 쓴다.

## public — 전역 접근

```java
public class UserController {
    public void createUser() { ... }
}
```

어디서든 접근 가능. API 엔드포인트, 외부에 공개할 라이브러리 클래스 등에 쓴다.
불필요하게 public을 쓰면 모듈 경계가 흐려지고, 나중에 그 필드/메서드를 바꿀 때
"누가 이걸 쓰고 있는지" 알 수 없어서 유지보수 난이도가 올라간다.

## 비교표

| | 같은 클래스 | 같은 패키지 | 상속받은 클래스 | 외부 |
|---|---|---|---|---|
| private | ✔️ | ❌ | ❌ | ❌ |
| default | ✔️ | ✔️ | ❌ | ❌ |
| protected | ✔️ | ✔️ | ✔️ | ❌ |
| public | ✔️ | ✔️ | ✔️ | ✔️ |

## 원문을 넘어서: 접근 제어자는 "설계 도구"다

접근 제어자를 단순 문법으로만 보면 이 정도에서 끝나지만, 실무에서 이게 왜 중요한지는
**설계 관점**에서 봐야 드러난다.

**1) 기본값이 제한적이어야 하는 이유**: 필드/메서드를 만들 때 접근 범위를 최대한
좁게(`private`부터) 시작하고, 정말 필요할 때만 넓히는 게 원칙이다. 반대로 시작하면
— 처음에 `public`으로 만들었다가 나중에 좁히려고 하면 — 이미 그 필드/메서드를
참조하는 다른 코드가 생겨 있어서 좁히기가 어렵다. 접근 범위는 넓히긴 쉬워도
좁히긴 어렵다는 게 이 판단을 기본값으로 굳혀야 하는 이유다.

**2) default(package-private)는 "테스트 가능한 캡슐화"를 만든다**: 어떤 메서드를
외부에 노출하고 싶지 않지만 같은 패키지의 테스트 클래스에서는 검증하고 싶을 때,
`private` 대신 `default`로 두면 API로는 안 보이면서도 테스트는 가능하다. 이게
"패키지를 모듈 경계로 쓴다"는 말의 실질적인 의미다 — 패키지 안에서는 서로 믿고
접근하되, 패키지 밖에는 계약(public API)만 노출한다.

**3) 한계: package-private은 "약속"이지 강제가 아니다**: 같은 패키지 이름으로
클래스를 새로 만들면(클래스패스만 다르면) `default` 멤버에 접근할 수 있다 —
JAR 안의 패키지와 이름이 같은 패키지를 다른 곳에 만들어서 끼워 넣는 것도 이론적으로
가능하다(패키지 스플리팅 문제). 이 한계를 기술적으로 강제하고 싶다면 Java 9+의
모듈 시스템(JPMS)이 `exports` 선언으로 더 강한 경계를 제공한다 — 접근 제어자가
"클래스/패키지 단위의 약속"이라면, 모듈 시스템은 "컴파일러가 강제하는 경계"라는
차이가 있다.

## 정리

- 기본값은 항상 가장 좁은 범위(`private`)에서 시작해서, 필요할 때만 넓힌다.
- `default`는 "패키지를 작은 모듈처럼 쓰고 싶을 때"의 실질적인 도구다.
- 접근 제어자는 결국 코드가 아니라 **설계 의도를 컴파일러가 검증해주는 장치**다 —
  누가 이 필드/메서드에 의존할 수 있는지를 명시적으로 선언하는 것.
