Redisson을 통한 데이터 관리 를 하기전에 사전 지식으로서 동기/비동기 동시성 thread 프로세스에 대한 개념을 정리해봅시다.

\- 사전 지식 - 

더보기

**[1] 동기 방식 : Synchronous**

\- 하나의 작업이 완료될 때까지 다음 작업을 시작하지 않습니다  
**[2] 비동기 (Asynchronous)**  
\- "일단 시켜놓고 다른 일 함" 방식

**[3] 동시성 (Concurrency) - "여러 일을 번갈아 가며" 방식**

비유: 당신은 한 번에 여러 일을 매우 빠르게 번갈아 가며 처리합니다. 예를 들어 라면 면 넣고 -> 볶음밥 재료 볶고 -> 설거지 접시 닦고 -> 다시 라면 확인하고...

[4] **병렬성 (Parallelism) - "여러 일을 동시에" 방식**

비유: A는 thread-1을, B는thread-2을, C는 thread-3를 각자 독립적으로 동시에 진행합니다.

  
일단 일을 시켜놓고 다른일을 진행하는 일에는 비동기 처리가 적합합니다. 즉 일단 시켜놓고 다른 일을 하는" **비동기 처리** 에 매우 적합합니다. 예시로 이메일을 보내는 예시로 구현해보려 합니다.

위의 사전 지식을 가지고 thread 와 프로세스에 대한 개념도 알아봅시다. 

**\- 프로세스 / 스레드 개념 간단히 이해하기 -**

: 하나의 앱이 실행되면 하나의 프로세스가 실행됩니다. 하나의 프로세스 에서는 여러명이 일을하게 됩니다. 이 일하는 사람들을 thread가 부릅니다.

Spring에서 보통 Tomcat을 사용한다고 가정한다면, Tomcat은 기본 tomcat-Thread 가 동작합니다. 이를 `tomcat 스레드 풀` 이라 부릅니다.

  * **Tomcat 스레드 풀:**
    * **역할:** 사용자로부터 HTTP 요청을 받아 컨트롤러(@RestController)의 메소드를 실행하는 데 사용됩니다. 즉, EmailController의 sendEmailsList 메소드는 Tomcat 스레드에서 실행됩니다.
    * **목표:** 최대한 빠르게 HTTP 요청에 응답하여 사용자 경험을 좋게 하고, 다음 HTTP 요청을 받아들일 수 있도록 스레드를 빨리 반환하는 것이 중요합니다.
    * **문제점 (동기 처리 시):** 만약 sendEmail과 같은 오래 걸리는 작업을 Tomcat 스레드에서 직접 처리하면, 해당 Tomcat 스레드가 블로킹되어 다른 HTTP 요청을 처리하지 못하게 됩니다.



보통의 tomcat 실행후 사용되는 http 요청에 대한 일을 진행합니다. 하지만 작업이 오래걸리는 일을 Tomcat Pool의 thread에 맡기면, 블로킹되어 문제가 발생할수 있습니다. 이를 위해서 우리는 별도의 Thread-Pool을 관리하여 특정 업무에 대한 thread를 미리 전담팀을 만들어 사용 할 수 있습니다.

@Async 를 이용하여 비동기 처리를 하는 Email 메도스가 있다고 가정하면, 해당 EmailExecutor를 이용하여 해당 업무는 해당 전단팀에 있는 Thread가 일을 처리하도록 진행하는 것 입니다. 이를 통해 기존 Tomcat Pool에서 일하는 Thread는 해당 업무를 관여하지 않아 Email 업무는 다른 업무에 피해를 주지 않습니다. 

해당 전담업무(이메일 업무)를 하는 Pool 의 정책은 아래와 같으며, **10명이 있고 안 바쁘면 최종적으로 5명만 일을 하거나 대기하게 됩니다.**

setCorePoolSize(5) (상시 근무 직원: 5명)

setQueueCapacity(25) (대기실/대기표: 25개)

setMaxPoolSize(10) (최대 직원: 10명)
    
    
    @Bean(name = "EmailExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);   // 기본 스레드 수
        executor.setMaxPoolSize(10);   // 최대 스레드 수
        executor.setQueueCapacity(25); // 큐 용량
        executor.setThreadNamePrefix("EmailAsync-"); // 스레드 이름 접두사
        executor.initialize();
        return executor;
    }
    
    
    @Async("EmailExecutor") // 이메일 전송 작업을 별도의 스레드에서 실행
    public CompletableFuture<String> sendEmail(String email) { // 반환 타입을 String으로 변경하여 결과 메시지를 전달
        String lockKey = "lock:email:" + email;
        RLock lock = redissonClient.getLock(lockKey); // 이메일 주소별로 락 생성
    
        String resultMessage;
        try {
            // 락을 획득하되, 기다리지 않고 즉시 시도 (0초 대기)
            // 락 획득에 성공하면 10초 후에 자동으로 락이 해제되도록 설정
            if (lock.tryLock(0, 10, TimeUnit.SECONDS)) {
                try {
                    System.out.println(Thread.currentThread().getName() + " - 이메일 전송 시작: " + email);
                    Thread.sleep(2000); // 이메일 전송 시뮬레이션 (2초 소요)
                    System.out.println(Thread.currentThread().getName() + " - 이메일 전송 완료: " + email);
                    resultMessage = "이메일 전송 성공: " + email;
                } finally {
                    // 락이 현재 스레드에 의해 보유 중인 경우에만 해제
                    // (autoUnlock 기능이 있어도 명시적으로 해제하는 것이 안전)
                    if (lock.isHeldByCurrentThread()) {
                        lock.unlock();
                    }
                }
            } else {
                // 락 획득 실패 (다른 스레드/서버에서 이미 처리 중)
                System.out.println(Thread.currentThread().getName() + " - 이미 락이 걸려 있어 이메일 전송 스킵: " + email);
                resultMessage = "이메일 전송 스킵 (이미 처리 중): " + email;
            }
        } catch (Exception e) {
            e.printStackTrace();
            resultMessage = "이메일 전송 중 오류 발생: " + e.getMessage();
        }
    
        return CompletableFuture.completedFuture(resultMessage);
    }

    @GetMapping("/send-emails")
    public String sendEmailsConcurrent(@RequestParam("emails") List<String> email) {
        // 동일 이메일로 3개의 비동기 이메일 전송 요청 시작
        // 각 CompletableFuture는 작업의 결과를 담음
        CompletableFuture<String> future1 = emailService.sendEmail(email.get(0));
        CompletableFuture<String> future2 = emailService.sendEmail(email.get(1));
        CompletableFuture<String> future3 = emailService.sendEmail(email.get(2));
    
        // 모든 비동기 작업이 완료될 때까지 기다림
        // 실제 운영 환경에서는 이렇게 컨트롤러에서 직접 기다리는 것은 좋지 않을 수 있습니다.
        // 여기서는 테스트를 위해 결과를 취합합니다.
        List<String> results = Stream.of(future1, future2, future3)
                .map(CompletableFuture::join) // 각 Future의 결과를 블로킹 방식으로 가져옴
                .collect(Collectors.toList());
    

### 

CompletableFuture는 Java 8에서 도입된 기능으로, **비동기 프로그래밍** 을 위한 강력한 도구입니다. 이를 이용하면 @Async 로 비동기 호출만 가능하던 부분을 비동기의 작업 결과를 활용 할수 있습니다.

  * **정의:** "아직 완료되지 않은 비동기 작업의 결과"를 나타내는 객체입니다. 미래에 어떤 값이 나올 것인데, 지금 당장 그 값이 필요하지 않거나, 값이 언제 나올지 모를 때 사용합니다.
  * **비유:** 레스토랑에서 음식을 주문하고 받은 **"주문 번호표"** 와 같습니다.
    * 주문 번호표를 받으면, 당신은 요리가 나올 때까지 기다리지 않고 다른 일을 할 수 있습니다. (비동기)
    * 나중에 요리가 완성되면, 번호표를 가지고 가서 음식을 받습니다. (결과 확인)
    * 만약 요리가 나오기 전에 다른 친구에게 번호표를 주면서 "이거 나오면 나한테 가져다줘"라고 할 수도 있습니다. (연속 작업)
    * 요리가 실패하면, 번호표를 통해 "요리 실패"를 통지받을 수도 있습니다. (예외 처리)



하지만 위 코드에서 보면 /send-emals 를 수행하는 thread는 tomcat Pool에서 나온 thread 입니다 이 thread 가 각각의 비동기 

를 호출하고 끝나지만 마지막 코드에서는 map 을 수행하기 위해서 블로킹 됩니다. 각각의 completeFuture 수행 값들을 join을 하기 위해 기다려야 하기 때문 입니다.

**map(CompletableFuture::join) (블로킹 방식):**

  * **동작 방식:** Stream 내에서 map 연산이 순차적으로 각 CompletableFuture에 대해 join()을 호출합니다.
  * **스레드 동작:** future1.join()이 호출되면, **현재 이 코드를 실행하고 있는 스레드(컨트롤러의 요청 처리 스레드)**는 future1이 완료될 때까지 **자신의 실행을 멈추고 대기(블로킹)합니다.** future1이 완료되면 다음 future2.join()을 호출하고, 또 다시 future2가 완료될 때까지 블로킹합니다. 이 과정이 future3까지 반복됩니다.
  * **결과적으로:** 컨트롤러의 요청 처리 스레드가 모든 비동기 작업이 끝날 때까지 묶여 있게 됩니다. 이 스레드가 다른 요청을 처리할 수 없게 되어 서버의 동시성 및 확장성에 문제가 발생합니다.



이또한 논 블로킹 하여 처리하기 위해서 아래와 같이 thenApply로 변경합니다.
    
    
    @GetMapping("/send-emails-nonblocking")
    public CompletableFuture<List<String>> sendEmailsNonBlocking(@RequestParam("emails") List<String> email) {
        CompletableFuture<String> future1 = emailService.sendEmail(email.get(0));
        CompletableFuture<String> future2 = emailService.sendEmail(email.get(1));
        CompletableFuture<String> future3 = emailService.sendEmail(email.get(2));
    
        // 모든 CompletableFuture가 완료될 때 비동기적으로 List<String>을 반환
        return CompletableFuture.allOf(future1, future2, future3)
                .thenApply(v -> Stream.of(future1, future2, future3)
                        .map(CompletableFuture::join) // 여기서는 이미 allOf가 완료되었으므로 join은 즉시 반환됩니다.
                        .collect(Collectors.toList()));
    }

이는 /send-emails-nonblocking을 수행한 Thread는 해당 thenApply만 진행하고 결과를 기다리지 않고 Pool로 돌아가게 되어 blocking 되지 않습니다. thread 논블로킹과 관계 없이 결과가 return 되면 해당 api 호출에 자동으로 response가 나옵니다.
