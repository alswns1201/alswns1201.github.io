영속성 컨텍스트는 JPA를 처음 배울 때 "1차 캐시, 더티 체킹" 같은 용어로 외우고 넘어가기
쉬운데, 이 개념을 모르고 코드를 짜면 실제로 두 가지 사고가 난다: **의도하지 않은 UPDATE
쿼리**와 **`LazyInitializationException`**. 개념보다 이 두 사고가 왜 나는지부터
짚는 게 이해에 도움이 된다.

## 영속성 컨텍스트: 트랜잭션 범위의 "임시 저장소"

영속성 컨텍스트는 엔티티를 관리하는 논리적 공간이고, 트랜잭션이 시작할 때 생기고
끝날 때 같이 사라진다. 하나의 요청이 하나의 `EntityManager`와 매핑되므로, **영속성은
트랜잭션 범위 안에서만 유지된다**는 게 핵심이다 — 이 범위를 벗어나면(트랜잭션이
끝나면) 엔티티는 더 이상 추적되지 않는다. 뒤에 나올 사고 두 개가 전부 이 "범위"를
넘나들 때 발생한다.

## 엔티티 생명주기 4단계

- **비영속(Transient)**: `new`로 만들었을 뿐, 컨텍스트와 무관한 상태
- **영속(Persistent)**: `persist()`나 `find()`로 컨텍스트가 추적 중인 상태
- **준영속(Detached)**: `detach()`를 호출했거나 트랜잭션이 끝나 추적이 끊긴 상태
- **삭제(Removed)**: `remove()` 호출, 커밋 시 실제로 DB에서 삭제

```java
Member member = new Member(); // 비영속
em.persist(member);           // 영속 — 이 시점에 바로 INSERT 쿼리가 나가지 않는다
```

`persist()` 호출 시점에 쿼리가 바로 나가지 않는다는 점이 중요하다. 실제 쿼리는
커밋(또는 flush) 시점에 나간다 — 그래서 "언제 쿼리가 실행되는가"를 트랜잭션 코드만
보고 예측하려면 이 지연 실행 개념을 알아야 한다.

## 1차 캐시: 같은 트랜잭션 안에서 같은 엔티티를 여러 번 조회해도 쿼리는 한 번

```java
Member member1 = em.find(Member.class, memberId); // SELECT 실행
Member member2 = em.find(Member.class, memberId); // 캐시에서 반환, 쿼리 없음
System.out.println(member1 == member2); // true — 같은 객체
```

이건 단순 성능 최적화가 아니라 **동일성 보장**이다. 같은 트랜잭션 안에서 같은 PK를
조회하면 항상 같은 객체 참조가 나온다는 걸 보장하기 때문에, 여러 서비스 메서드를
거치면서 같은 엔티티를 여러 번 조회해도 상태 불일치를 걱정할 필요가 없다.

## 더티 체킹: 이게 왜 "의도하지 않은 UPDATE"의 원인이 되는가

JPA는 엔티티를 조회할 때 최초 상태의 스냅샷을 떠 두고, 커밋 시점에 현재 상태와
스냅샷을 비교해서 다르면 UPDATE를 자동으로 날린다. 편리해 보이지만, 이게 문제가
되는 순간은 **컨트롤러나 다른 계층에서 실수로 영속 상태의 엔티티 필드를 건드렸을
때**다 — `save()`를 호출하지 않았는데도, 트랜잭션이 끝나는 시점에 그 변경이 그대로
DB에 반영된다. "왜 호출하지도 않은 update가 나가지?"라는 질문의 답은 대부분 이거다.

## LazyInitializationException: 트랜잭션 경계를 넘어서 발생하는 사고

`FetchType.LAZY`로 설정된 연관관계를 서비스 계층에서 조회한 뒤 컨트롤러나 뷰에서
접근하면, 이미 트랜잭션이 끝나 영속성 컨텍스트가 닫혀 있으므로 예외가 난다. 이건
"버그"라기보다 **영속성 컨텍스트의 생존 범위가 트랜잭션과 같다는 원칙이 지켜지지
않은 상황**이다 — Lazy 필드는 그 필드에 접근하는 시점에 컨텍스트가 살아있어야 한다.

## DTO를 쓰는 진짜 이유

이 두 사고(의도하지 않은 UPDATE, LazyInitializationException)의 공통 원인은
**Entity를 트랜잭션 경계 밖으로 그대로 들고 나가는 것**이다. DTO 변환은 단순히
"필요한 필드만 골라 담는" 작업이 아니라, Entity를 영속성 컨텍스트 안에 가두고
그 밖으로는 순수한 데이터만 내보내는 경계 역할을 한다. `@Query`나 QueryDSL에서
DTO Projection을 바로 조회하는 것도 같은 이유다 — Entity로 조회한 뒤 변환하는
대신, 애초에 컨텍스트 관리 대상이 아닌 형태로 조회를 끝낸다.

```java
@Query("SELECT t FROM TodoEntity t WHERE t.mno = :mno")
Optional<TodoDTO> getDTO(@Param("mno") Long mno);
```

정리하면: 영속성 컨텍스트를 이해한다는 건 "1차 캐시가 뭐다"를 외우는 게 아니라,
**엔티티의 생존 범위가 트랜잭션이라는 것과, 그 범위를 넘기려면 반드시 DTO로
변환해야 한다는 규칙**을 체득하는 것이다.
