**이벤트 소싱**은 "지금 상태"를 저장하는 대신 "무슨 일이 있었는지"를 순서대로
저장하는 방식이다. 상태가 필요하면 그 기록들을 처음부터 순서대로 다시 재생해서
계산한다. 정의만 보면 추상적인데, [유효기간이 있는 적립금(포인트)](https://github.com/alswns1201/event-sourcing-practice)
하나만 놓고 보면 왜 이런 방식이 필요한지 바로 감이 온다.

## 예제: 적립금이 저절로 줄어드는 상황

규칙은 두 가지뿐이다.

- 포인트는 적립될 때마다 "언제 적립됐는지"가 남고, 적립일 기준 유효기간이 지나면
  자동으로 소멸한다.
- 사용할 땐 오래된 포인트부터 먼저 쓴다.

이제 커맨드를 몇 번만 실행해보자.

```bash
curl -X POST localhost:8080/api/rewards/u1/earn -d '{"amount":1000,"validForSeconds":2592000}' # 30일짜리
curl -X POST localhost:8080/api/rewards/u1/earn -d '{"amount":500,"validForSeconds":2}'         # 2초짜리
curl localhost:8080/api/rewards/u1/balance
# → {"usableBalance":1500, ...}

# 3초 동안 아무것도 안 함 — 적립도, 사용도 하지 않았다

curl localhost:8080/api/rewards/u1/balance
# → {"usableBalance":1000, ...}
```

아무 요청도 안 보냈는데 1500이 1000으로 줄었다. 2초짜리 포인트 500이 시간이 지나서
저절로 사라졌기 때문이다.

## 왜 `balance` 컬럼 하나로는 안 되는가

일반적인 CRUD 방식이라면 `balance`라는 컬럼 하나를 두고, 적립할 때 `+=`, 사용할 때
`-=`를 한다. 그런데 이 방식으로는 "포인트가 저절로 사라지는" 상황을 표현할 수 없다
— 아무도 `balance`를 건드리지 않았는데 값이 바뀌어야 하니까.

반면 "언제 얼마가 적립됐는지"를 전부 기록해두면(이게 이벤트다), "지금 몇 개나
쓸 수 있는지"는 그 기록들을 보고 **그때그때 계산**하면 된다.

```java
public long usableBalance(Instant asOf) {
    return batches.values().stream()
            .filter(batch -> batch.expiresAt.isAfter(asOf))  // 아직 안 지난 것만
            .mapToLong(batch -> batch.remaining)               // 남은 만큼만
            .sum();
}
```

같은 기록을 두고 "지금 기준"으로 계산하면 1000, "3초 전 기준"으로 계산하면 1500이
나온다. **값을 하나 저장해뒀다가 그대로 보여주는 게 아니라, 물어볼 때마다 다시
계산한다**는 게 핵심이다.

## 정리

- 이벤트 소싱은 "현재 상태"가 아니라 "무슨 일이 있었는지"를 저장한다.
- 이게 진짜 필요해지는 경우는, 현재 상태가 단순히 "이벤트를 더하고 빼서" 나오지
  않고, **"언제"라는 정보까지 있어야 계산되는 경우**다 — 이번 예제의 유효기간이
  그렇다.
- 상태가 필요할 때마다 기록을 처음부터 다시 계산(재생)하는 게 기본 동작이다.

## 조금 더 들어가면: 실제로 짜면서 생긴 문제들

여기부터는 위 개념을 실제 코드로 옮기면서 부딪힌 세부사항이다. 핵심 개념과는
별개로, 구현하려면 반드시 풀어야 했던 것들만 간단히 남긴다.

**"어느 포인트를 썼는지"도 같이 기록해야 한다.** 사용 이벤트에 "얼마를 썼다"만
남기면 안 된다 — "어느 적립분에서 얼마를 뺐는지"까지 남겨야 한다. 어떤 적립분이
아직 유효했는지는 그 순간의 "지금"에 달려 있어서, 나중에 다시 계산하면 그때 결과랑
달라질 수 있기 때문이다. 그래서 이 결정은 계산이 아니라 **기록**으로 남긴다.

```java
public record PointsRedeemedEvent(long amount, List<BatchConsumption> consumptions, Instant redeemedAt)
        implements RewardEvent { }
```

**기록이 많아지면 매번 처음부터 계산하기 부담스럽다.** 그래서 중간중간 "이 시점까지
계산한 결과"를 스냅샷으로 저장해두고, 다음엔 그 이후 기록만 이어서 계산한다.

**조회 전용으로 값을 미리 계산해두는 것(캐시)도 조심해야 한다.** 캐시해둔 숫자
하나만 두면, 포인트가 저절로 만료될 때 그 숫자를 갱신할 계기가 없어서 캐시가
틀린 값이 돼버린다. 그래서 캐시는 "포인트 배치별로" 만들어두고, 조회할 때마다
유효기간을 다시 확인해서 합산한다 — 여전히 전체 기록을 다시 계산하는 것보다는
훨씬 싸다.

**"지금/미래"와 "과거"는 답하는 방법이 다르다.** 캐시를 이용한 빠른 조회는 지금이나
미래를 물어볼 때만 정확하다. "그때는 얼마였는지" 같은 과거 질문에는 그 시점까지의
기록만 골라서 다시 계산해야 한다.
