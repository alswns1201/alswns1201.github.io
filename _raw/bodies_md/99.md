### 오버 엔지니어링 에 대한 고찰.

현재 kafka, chromadb , fastAPI embed-server 를 사용하고 있다.

  
[1] 학습목표가 우선이여서 kafka를 선택했지만 사실 일반 비동기와 크게 다르지 않았다. 오히려 추후 서버운영시 kafka는 메모리 를 너무 많이 잡아먹고 있기 때문에 실시간으로 통계를 내거나 대규모로 데이터가 들어와 여러 기능들을 처리해야 하는 기능이 없다면 오버 엔지니어링으로 판단된다.

-> Spring Boot 내부의 Events나 단순한 Job Queue만으로도 충분

[2] ChromaDB와 Embed-server

Embedding: 로컬 embed-server 대신 OpenAI나 Voyage AI의 API 호출 (서버 RAM 절약). ChromaDB와 Embed-server는 서버의 RAM을 직접 점유합니다. 반면, MongoDB Atlas는 **SaaS(Software as a Service)** 형태이므로, 내 서버는 API 호출만 할 뿐 실제 연산과 저장은 MongoDB 클라우드 서버가 대신 처리. 만약 MongoDB Atlas로 바꾼다면 전체 시스템은 다음과 같이 더 가벼워 진다.

  * **기존:** [React] ↔ [Spring Boot] ↔ **[MariaDB + Kafka + ChromaDB + Embed-server] (서버 터짐)**
  * **변경:** [React] ↔ [Spring Boot] ↔ **[MariaDB]** \+ **[MongoDB Atlas (외부)]** \+ **[LLM API (외부)]**



이렇게 하면 내 EC2 서버는 **Spring Boot와 React만** 돌리면 되므로, 프리티어에서도 훨씬 안정적으로 인프라이다.

결론 

  * **Kafka:** 별도 서버 자원을 많이 점유하는 Kafka 대신 Spring Boot 내장 이벤트(@Async)나 **Redis** 를 사용하여 서버 메모리 부하를 줄이고 구조를 단순화합니다.
  * **MongoDB Atlas (Multi-model):** ChromaDB와 MariaDB를 **MongoDB Atlas** 하나로 통합하여 인프라 관리 포인트를 줄이고, 일반 데이터와 벡터 데이터를 한곳에서 효율적으로 관리합니다.
  * **Embedding:** 로컬 메모리를 사용하는 embed-server 대신 **OpenAI나 Voyage AI 같은 외부 API** 를 활용하여 서버의 CPU/RAM 리소스를 확보하고 모델 관리 부담을 없앱니다.
  * **초기 운영 장점:** 복잡한 인프라 서비스를 모두 외부 SaaS(클라우드)로 돌려 **EC2 프리티어(RAM 1GB)에서도 안정적인 운영** 이 가능하며 결제나 관리 비용을 최소화할 수 있습니다.
