    README.md
    # 프로젝트 문서
    
    아키텍처, 결정, 스펙, 태스크를 한곳에 모은 공간.
    코드는 `../src`에 있고, 이 폴더는 *왜(why)* 와 *계획(plan)* 을 담는다.
    
    ## 구성
    
    | 폴더 | 담는 것 | 언제 추가하나 |
    |---|---|---|
    | [`architecture/`](./architecture/) | 시스템 설계 노트, 컴포넌트 맵, 데이터 흐름 정리 | 코드 주석만으로 설명이 부족한 하위 시스템의 구조를 설명해야 할 때 |
    | [`decisions/`](./decisions/) | ADR — 중요한 결정 하나당 파일 하나(`NNNN-title.md`) | 훗날 누군가 "왜?"라고 물을 만한 선택을 내렸을 때 |
    | [`specs/`](./specs/) | 구현 전 기능 스펙 / 요구사항 | 범위에 대한 합의가 먼저 필요한 기능을 시작할 때 |
    | [`tasks/`](./tasks/) | 카드 형태의 작업 항목, 폴더 기반 칸반(아래 참고) | 추적할 작업 단위가 생길 때마다 |
    
    ## 태스크 보드
    
    `tasks/`는 칸반 보드다 — 카드는 상태가 바뀌면 폴더 사이를 이동한다:
    
    ```
    backlog → in-progress → done
    ```
    
    - 카드 하나 = 마크다운 파일 하나, [`tasks/template/task.md`](./tasks/template/task.md)에서 복사.
    - 이름: `NNN-short-slug.md` (예: `012-scanned-pdf-grounding.md`).
    - 상태를 바꾸려면 **파일을 이동**해 다음 폴더로 옮긴다. 폴더가 곧 상태다.
    - `review`와 `blocked`는 전용 폴더가 없다 — 카드의 `status:` front-matter로 표현한다
      (`review`는 `done/`으로 옮기기 전 단계; `blocked`는 `in-progress/`에서 멈춰 있는 동안).
    - 각 카드는 `status:` front-matter 필드도 갖는다 — 폴더와 항상 일치시켜 트리 순회 없이 grep으로 찾을 수 있게 한다.
    
    ## 규칙
    
    - **경로에 공백 금지.** 폴더와 파일은 `kebab-case`를 쓴다. 셸, git, 코딩 에이전트 모두에게 편하다.
    - **파일 하나에 아이디어 하나.** 작은 파일은 diff와 리뷰가 깔끔하다.
    - **날짜 형식은 어디서나 `YYYY-MM-DD`.** 자연스럽게 정렬된다.
    - 모든 폴더는 `.gitkeep`을 유지해 빈 뼈대가 `git clone` 후에도 남게 한다.
    
    ## 워크플로 (코딩 에이전트는 이것을 따른다)
    
    권위 있는 코드 동작 계약은 `../CLAUDE.md`다. 이 폴더는 의도(intent)와 이력(history)을 담는다.
    **강제 가능한 게이트별 체크리스트**는 [`CONTRIBUTING.md`](./CONTRIBUTING.md)이며, 아래 단계는 그 요약이다.
    
    **1. 파악.** `project-status.md`를 읽는다. 작업과 관련된 스펙/ADR을 모두 읽는다.
    
    **2. 계획을 어디에 둘지 고른다:**
    - 설계/합의가 먼저 필요함(기능, 사소하지 않음) → `specs/NNN-slug.md` 작성.
    - 선택지 중 하나를 고르는 결정 → ADR `decisions/NNNN-slug.md` 작성.
    - 작고 명확함 → 곧바로 태스크 카드로.
    
    **3. 태스크 카드 생성.** `tasks/template/task.md` → `tasks/backlog/NNN-slug.md`로 복사.
    `Goal`(성공 기준), `Context`(스펙/ADR 링크 + `path:line`), `Plan`, `Acceptance criteria`를 채운다.
    
    **4. 시작.** 카드를 `→ tasks/in-progress/`로 이동, front-matter `status: in-progress` + `updated:` 날짜 설정.
    
    **5. 구현.** 카드의 `Plan`을 따르고 진행하며 박스를 체크한다. 막히면 → `status: blocked`로 설정하고 이유를 기록.
    
    **6. 검증.** 완료 조건 실행: `./gradlew test`.
    green이 아니면 → 완료가 아니다. 검증될 때까지 반복.
    
    **7. 마무리.** 카드에서 완료한 체크리스트 항목을 모두 완료 표시 — `- [ ]` → `- [x]`
    (`Plan`과 `Acceptance criteria`); 구현 중 진행하며 체크하고, 완료 시점에는 모든 박스가
    `[x]`여야 한다(`tasks/done/`에 미체크 박스가 있다면 실제로 안 했거나 카드가 거짓말을 하는 것).
    리뷰 단계에서는 `status: review`로 설정하고, 그다음 카드를 `→ tasks/done/`으로 이동, `status: done` 설정.
    `project-status.md` 업데이트(항목을 "Recently shipped"로 옮기고 "Now"에서 제거).
    
    **8. 커밋.** 커밋 하나에 논리적 변경 하나. 새 경로에 공백 없음. 푸시는 요청받을 때만.
    
    **황금률:** 폴더가 곧 상태이고 `status:` front-matter가 이를 반영한다 — grep과 트리가 일치하도록 둘을 항상 동기화한다.
    
    ## 버그 & 개선
    
    버그나 개선은 **특별한 것이 아니다** — `tasks/` 안의 태스크 카드이며, 별도 폴더가 아니라
    태그로 구분된다. 기능과 같은 보드, 같은 생애주기를 따른다.
    
    **접수:** `tasks/backlog/`(분류 대기열)에 올바른 태그를 붙인 카드를 넣는다:
    
    | 태그 | 용도 |
    |---|---|
    | `bug` | 기대 동작 대비 무언가 깨진 경우 |
    | `improvement` | 동작은 하지만 더 나아질 수 있는 경우(UX, 출력 품질) |
    | `tech-debt` | 내부 정리, 리팩터, 사용자에게 보이는 변화 없음 |
    | `feature` | 새로운 기능 |
    
    그다음 일반 흐름을 따른다: `backlog` → `in-progress` → `done`.
    다음에 무엇을 할지는 별도의 ready 폴더가 아니라 `project-status.md`("Next")에서 정한다.
    
    **필요하면 먼저 상위 단계로 올린다:**
    - 설계/합의가 필요한 큰 개선 → `specs/NNN-slug.md` 작성 후 카드가 이를 링크.
    - 설계 선택을 강제하는 수정 → `decisions/`에 ADR 작성 후 카드가 이를 링크.
    
    **버그 카드는 반드시 추가한다** (`Context` / `Acceptance criteria`에):
    - 재현 단계, 기대값과 실제값, 의심되는 `path:line`;
    - 완료 조건에 **회귀 테스트** — 테스트로 고정되기 전까지 수정은 완료가 아니다.
    
    ## 태스크 추적: 단일 진실 공급원(source of truth) 하나만 고른다
    
    팀이 **GitHub Issues**를 쓴다면, 같은 항목을 `tasks/` 카드로도 **중복** 관리하지 않는다 —
    그것은 이중 추적이다(아래 참고). 한 가지 모델만 정해 그것을 고수한다.

CONTRIBUTING.md
    
    
    # CONTRIBUTING — 에이전트 작업 체크리스트
    
    이 저장소를 건드리는 모든 사람(사람이든 코딩 에이전트든)을 위한 작업 규칙.
    [`README.md`](./README.md)의 워크플로를 강제 가능한 형태로 정리한 것이다.
    
    > **원칙:** 카드 없이는 코드를 변경하지 않는다. 검증이 통과(green)되지 않은 카드는
    > `tasks/done/`에 도달하지 못한다. 상태는 파일에 남기며, 채팅에만 남기지 않는다.
    
    아래 각 단계는 **게이트**다 — 모든 항목이 체크되기 전에는 다음 단계로 넘어가지 않는다.
    
    ## Gate 0 — 파악 (편집 전)
    
    - [ ] `project-status.md` 읽기(현재 상태, 알려진 이슈).
    - [ ] `../CLAUDE.md`(코드 동작 계약)와 이 영역에 관련된 스펙/ADR 읽기.
    - [ ] 이미 추적 중인 작업이 아닌지 확인(`tasks/` grep, 이슈 기반이면 GitHub Issues 확인).
    
    ## Gate 1 — 계획 (코드 작성 전)
    
    - [ ] 산출물 결정:
      설계 필요 → `specs/NNN-slug.md`; 선택 사항 → `decisions/NNNN-slug.md`; 작고 명확함 → 카드만.
    - [ ] `tasks/template/task.md`로부터 카드를 만들어 `tasks/backlog/NNN-slug.md`에 둔다.
    - [ ] 카드 구성: 한 문장짜리 `Goal`(활동이 아니라 성공 기준),
      `Context`(스펙/ADR 링크 + 의심되는 `path:line`), `Plan`, `Acceptance criteria`.
    - [ ] 올바른 `tags:` 설정(`bug` / `improvement` / `tech-debt` / `feature`).
    - [ ] 버그 카드: `Context`에 재현 단계 + 기대값과 실제값; 완료 조건에 **회귀 테스트**.
    
    ## Gate 2 — 시작
    
    - [ ] 카드를 `tasks/backlog/` → `tasks/in-progress/`로 이동.
    - [ ] Front-matter `status: in-progress`와 `updated:` 날짜 설정(폴더와 일치시킴).
    - [ ] 진행 중인 카드는 한 번에 하나의 논리적 작업 단위만.
    
    ## Gate 3 — 구현
    
    - [ ] 카드의 `Plan`을 따르고, 완료한 단계를 체크한다.
    - [ ] `Goal`을 충족하는 최소한의 코드. 추측성 작업 금지. 필요한 부분만 건드린다.
    - [ ] 외부 요인으로 막혔는가? Front-matter `status: blocked`로 설정하고 `Notes`에 블로커를 기록. 중단.
    
    ## Gate 4 — 검증 (반복 — 건너뛰지 말 것)
    
    - [ ] `./gradlew test` 통과.
    - [ ] 모든 `Acceptance criteria` 항목이 객관적으로 충족됨.
    - [ ] 버그 수정 → 회귀 테스트가 존재하며, 수정 전에는 실패하고 수정 후에는 통과한다.
    - [ ] green이 아니면 ⇒ 완료가 아니다. Gate 3으로 돌아간다.
    
    ## Gate 5 — 마무리
    
    - [ ] 리뷰 단계 → front-matter `status: review`; 리뷰 후 → 카드를 `tasks/done/`으로 이동, `status: done`.
    - [ ] `project-status.md` 업데이트: 항목을 "Recently shipped"로 옮기고 "Now"에서 제거.
    - [ ] 진행 중에 내린 결정이 있는가? `decisions/`에 기록되어 있어야 한다.
    
    ## Gate 6 — 커밋
    
    - [ ] 커밋 하나에 논리적 변경 하나; 메시지에는 *무엇을* 그리고 *왜* 를 적는다.
    - [ ] 새 경로는 `kebab-case`, 공백 없음.
    - [ ] 커밋은 카드 id를 참조한다.
    - [ ] **푸시는 사용자가 요청할 때만.** 요청 없이 `main`에 푸시하지 않는다.
    
    ---
    
    ### 안티패턴 (이것은 바이브 코딩이지, 제대로 된 에이전트 엔지니어링이 아니다)
    
    - 카드도 없고 문서화된 목표도 없이 코드를 편집하는 것.
    - 검증 루프를 돌리지 않고 완료로 표시하는 것.
    - 상태를 채팅에만 남기는 것 — 폴더와 `status:`가 갱신되지 않음.
    - 카드 하나에 트래커 둘(같은 항목에 카드 **와** GitHub Issue 동시 사용).
    - 조용한 범위 확장 — 카드의 `Plan`에 없는 추가 변경.

    ## 동작 원칙
    
    1. 추측하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.
    2. 문제를 푸는 최소한의 코드. 추측성 작업 금지.
    3. 반드시 필요한 것만 건드릴 것. 네가 만든 것만 정리할 것.
    4. 성공 기준을 정의할 것. 검증될 때까지 반복할 것.
    5. 코드베이스를 이해하기 위해 검색·읽기·목록 조회를 현명하게 활용할 것.
    6. 하드코딩 금지. 조정 가능한 값은 config에 둘 것
    7. 주석은 간결하고 정확하게, 필요할 때만. 길거나 장황한 블록 금지.
