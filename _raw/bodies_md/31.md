#### Next.js와 Spring Security, Middleware로 httpOnly JWT를 '진짜' 검증하기까지

[ Spring Security와 Next.js(BFF) 환경에서 JWT 토큰을 관리하기.] 

이전  httpOnly 쿠키로 XSS 공격을 막고, Next.js Middleware로 페이지 접근을 제어하는 방법을 이야기했습니다. 하지만 거기서 끝이 아니었습니다. "쿠키가 존재하긴 하는데, 이 토큰이 정말 위조되지 않고 만료되지 않은 유효한 토큰일까?"   
  


#### Middleware에서 Spring Security API를 통해 토큰을 '진짜' 검증하기.

#### httpOnly 쿠키와 BFF

  * 문제: Local Storage는 XSS에 취약하여 JWT 저장소로 부적합.
  * 해결책: 자바스크립트 접근이 불가능한 httpOnly 쿠키를 사용.
  * 나의 아키텍처:
    * 브라우저 ↔ Next.js (BFF) ↔ Spring Security (API 서버)
    * 로그인 시, Next.js 서버가 Spring API로부터 JWT를 받아 httpOnly 쿠키를 설정해 브라우저로 전달.


    
    
    // pages/api/login.js (Next.js의 API Route)
    // ... Spring API와 통신하여 jwtToken을 받아온 후 ...
    
    const response = NextResponse.json({ message: "Login successful" });
    response.cookies.set('accessToken', jwtToken, {
      httpOnly: true,
      path: '/',
      secure: process.env.NODE_ENV === 'production',
      maxAge: 60 * 60, // 1시간
      sameSite: 'lax'
    });
    return response;

#### 반쪽짜리 해결책: Middleware에서의 단순 존재 확인
    
    
    // middleware.ts (초기 버전)
    import { NextResponse } from 'next/server';
    import type { NextRequest } from 'next/server';
    
    export function middleware(request: NextRequest) {
      // 보호된 경로로 접근 시, 단순히 쿠키가 있는지 없는지만 확인
      const accessToken = request.cookies.get('accessToken')?.value;
    
      if (!accessToken && request.nextUrl.pathname.startsWith('/dashboard')) {
        return NextResponse.redirect(new URL('/login', request.url));
      }
    
      return NextResponse.next();
    }

Next.js Middleware에서 단순히 쿠키의 존재 여부만 확인하게 된다면, 비로그인 사용자를 막는 데는 효과가 있겠지만, 심각한 문제점이 있습니다.

  * 만약 토큰이 만료되었다면?
  * 만약 토큰의 내용(payload)이 위조되었다면?
  * 만약 서버에서 강제로 해당 사용자를 로그아웃 처리했다면?



이 경우, 사용자는 유효하지 않은 토큰을 가진 채로 페이지에 접근하게 되고, 페이지는 깨지거나 API 호출이 모두 실패하는 등 비정상적으로 동작할 것입니다. 이것은 진정한 의미의 '보호'가 아니었습니다.

#### Spring Security

해답은 명확했습니다. 토큰을 발급한 주체인 Spring Security 서버만이 그 토큰의 유효성을 100% 보장할 수 있다. 그래서 다음과 같은 검증 흐름을 설계했습니다.

  1. [Spring] 토큰 검증 전용 API 엔드포인트를 만든다. (/api/auth/validate)
  2. [Next.js] Middleware는 페이지 요청을 가로챌 때마다 이 API를 호출한다.
  3. [Spring] API는 요청에 담긴 쿠키의 JWT를 검증하고, 결과(성공/실패)를 응답한다.
  4. [Next.js] Middleware는 Spring의 응답에 따라 요청을 계속 진행시키거나, 로그인 페이지로 리다이렉트한다.



#### Step 1: Spring Security에 검증 엔드포인트 만들기

먼저 Spring Boot에 쿠키의 토큰을 받아 유효성을 검사하는 간단한 Controller 엔드포인트를 추가했습니다.
    
    
    // AuthController.java
    @RestController
    @RequestMapping("/api/auth")
    @RequiredArgsConstructor
    public class AuthController {
    
        private final JwtUtil jwtUtil; // 직접 구현한 JWT 유틸리티 클래스
    
        @GetMapping("/validate")
        public ResponseEntity<?> validateToken(
                // ✨ HttpServletRequest 대신 @CookieValue를 사용하면 더 간편합니다.
                @CookieValue(name = "accessToken", required = false) String accessToken
        ) {
            if (accessToken == null || !jwtUtil.validateToken(accessToken)) {
                // 토큰이 없거나 유효하지 않으면 401 Unauthorized 응답
                return ResponseEntity.status(HttpStatus.UNAUTHORIZED).body("Invalid or expired token");
            }
    
            // 토큰이 유효하면 사용자 정보(예: username)를 반환할 수도 있습니다.
            // 여기서는 간단히 200 OK만 응답합니다.
            String username = jwtUtil.getUsernameFromToken(accessToken);
            return ResponseEntity.ok().body(Map.of("username", username, "isValid", true));
        }
    }

중요: 이 /api/auth/validate 엔드포인트는 Spring Security 설정에서 인증 없이도 접근이 가능해야 합니다. 이 엔드포인트 자체가 인증을 수행하는 역할을 하기 때문입니다.
    
    
    // SecurityConfig.java
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // ...
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/login", "/api/auth/validate").permitAll() // ✨ 검증 API 허용
                .anyRequest().authenticated()
            );
            // ...
        return http.build();
    }

#### 

Middleware가 Spring API를 호출하도록 적용.
    
    
    // middleware.ts (최종 완성 버전)
    import { NextResponse } from 'next/server';
    import type { NextRequest } from 'next/server';
    
    // Spring Boot API 서버의 주소
    const API_BASE_URL = process.env.SPRING_API_URL || 'http://localhost:8080';
    
    export async function middleware(request: NextRequest) {
      const { pathname } = request.nextUrl;
      const protectedPaths = ['/dashboard', '/profile'];
    
      // 보호된 경로에 대한 요청인지 확인
      if (protectedPaths.some(path => pathname.startsWith(path))) {
        // 1. 요청에서 accessToken 쿠키를 가져옵니다.
        const accessToken = request.cookies.get('accessToken')?.value;
    
        // 2. 쿠키가 없으면 바로 로그인 페이지로 리다이렉트
        if (!accessToken) {
          return NextResponse.redirect(new URL('/login', request.url));
        }
    
        try {
          // 3. ✨ 핵심: Spring 검증 API에 토큰 유효성 확인 요청
          const response = await fetch(`${API_BASE_URL}/api/auth/validate`, {
            // GET 요청이지만, 헤더에 쿠키를 포함시켜 보냅니다.
            headers: {
              'Cookie': `accessToken=${accessToken}`
            }
          });
    
          // 4. Spring API가 200 OK를 반환하면(유효하면) 요청을 그대로 통과
          if (response.ok) {
            return NextResponse.next();
          }
    
          // 5. 유효하지 않은 토큰이면(401 등) 로그인 페이지로 리다이렉트
          return NextResponse.redirect(new URL('/login', request.url));
    
        } catch (error) {
          console.error('Token validation error:', error);
          // API 서버에 연결할 수 없는 등 네트워크 에러 발생 시
          return NextResponse.redirect(new URL('/login', request.url));
        }
      }
    
      return NextResponse.next();
    }

사용자가 페이지를 이동할 때 브라우저는 **Next.js 서버** 에 요청 후 Next.js 서버는 **Spring 서버에 검증을 요청** 하고 만료되거나 위조된 토큰으로는 절대 보호된 페이지에 접근할 수 없습니다.

결론 

JWT 인증 아키텍처는 다음과 같은 흐름

  1. 로그인: 사용자가 로그인하면 Next.js(BFF)가 Spring API로부터 JWT를 받아 httpOnly 쿠키에 담아 브라우저에 저장합니다. (XSS 방어)
  2. 페이지 접근: 사용자가 /dashboard 같은 보호된 페이지로 이동을 시도합니다.
  3. Middleware 가로채기: Next.js Middleware가 요청을 가로채고, 브라우저가 보낸 accessToken 쿠키를 확인합니다.
  4. 실시간 검증: Middleware는 fetch를 통해 Spring Security의 /api/auth/validate 엔드포인트로 토큰 검증을 요청합니다.
  5. 서버 단 검증: Spring 서버는 토큰의 서명, 만료 시간, 유효성을 모두 검사하고 결과를 응답합니다. (200 OK or 401 Unauthorized)
  6. 접근 제어: Middleware는 Spring의 응답에 따라 요청을 통과시키거나 로그인 페이지로 리다이렉트합니다.
  7. UI 렌더링: (검증 통과 시) 페이지가 안전하게 렌더링되고, 필요하다면 클라이언트 측에서 /api/me 같은 API를 호출하여 사용자 정보를 화면에 표시합니다.
