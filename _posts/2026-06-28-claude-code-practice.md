## Claude Code 컨텍스트 관리: .claudeignore, skills, /compact

Claude Code를 매일 쓰다 보면 결국 마주치는 문제는 기능이 아니라 **컨텍스트 관리**다.
대화가 길어질수록 비용이 오르고 응답이 느려지고, 심하면 방금 전 지시를 까먹은 것 같은
반응이 나온다. 여기서 실질적으로 쓰이는 세 가지 도구 — `.claudeignore`, skills,
`/compact` — 를 왜 쓰는지 중심으로 정리한다.

### .claudeignore — 애초에 안 읽게 만들기

`.gitignore`처럼, Claude Code가 대화 중 참조하지 말아야 할 폴더/파일을 지정할 수 있다.
`node_modules`, 빌드 산출물, 대용량 로그 파일처럼 코드 이해에 도움이 안 되면서 토큰만
잡아먹는 디렉토리를 미리 걸러두는 것이다.

컨텍스트 관리의 첫 단계는 "다 읽고 나중에 요약한다"가 아니라 "애초에 관련 없는 걸
안 읽게 한다"는 걸 명확히 해두는 게 좋다 — 사후 압축(`/compact`)보다 사전 차단이
언제나 더 싸다.

### Skills — 반복 작업을 명령어로 굳히기

매번 같은 방식으로 시키는 작업(코드 리뷰 기준, 테스트 코드 생성 규칙 등)이 있다면
그걸 매번 프롬프트로 새로 설명하는 대신 skill로 만들어두면, 다음부터는 명령어 하나로
같은 맥락을 재사용할 수 있다. 이건 앞서 다룬 [하네스 엔지니어링]({{ '/posts/harness-engineering/' | relative_url }})
글의 "역할별 문서 분리" 원칙과 같은 맥락이다 — 매번 전체 맥락을 새로 주입하는 대신,
필요한 조각만 불러 쓰게 만드는 것.

### /compact vs /clear — 압축이냐 초기화냐

대화가 길어지면 지금까지 나눈 모든 텍스트가 컨텍스트로 계속 쌓인다. 이건 두 가지
문제를 만든다.

- **비용 증가**: 매 요청마다 이전 대화 전체를 다시 전송해야 하므로 토큰 소모가 누적된다.
- **품질 저하**: 관련 없는 정보가 너무 많이 섞이면 방금 준 지시를 놓치거나 일관성이
  떨어지는 응답이 나올 가능성이 커진다.

이걸 해결하는 두 명령어의 차이는 명확하다.

| 명령어 | 효과 | 적합한 상황 |
|---|---|---|
| `/compact` | 핵심 맥락(수정 사항, 결정된 로직 등)만 요약해서 남기고 나머지 정리 | 하던 작업을 계속 이어갈 때 (연속성 필요) |
| `/clear` | 컨텍스트를 완전히 삭제 | 아예 새로운 작업을 시작할 때 (완전 초기화) |

**판단 기준은 "다음 요청이 지금까지의 결정을 참조해야 하는가"다.** 참조해야 한다면
`/compact`로 압축해서 이어가고, 완전히 새로운 주제라면 `/clear`로 시작하는 게 낫다 —
`/compact`를 새 주제에도 습관적으로 쓰면 이전 작업의 요약이 계속 컨텍스트에 남아서
오히려 새 작업에 방해가 될 수 있다.

**언제 compact 해야 하는가**: 응답이 평소보다 느려지거나 머뭇거리는 느낌이 들 때,
또는 작업의 성격이 바뀌는 전환점("A 버그는 다 고쳤고 이제 성능 최적화로 넘어간다"
같은 시점)에 선제적으로 압축해두는 편이, 컨텍스트가 꽉 찬 뒤에 반응적으로 압축하는
것보다 낫다.

### 정리

- `.claudeignore`로 애초에 무관한 걸 안 읽게 하는 게 가장 싼 컨텍스트 관리다.
- skills는 반복되는 지시를 명령어로 굳혀서 매번 맥락을 새로 설명하지 않게 해준다.
- `/compact`와 `/clear`는 "이어갈 것인가, 새로 시작할 것인가"를 기준으로 고른다 —
  컨텍스트가 꽉 찬 뒤보다는 작업 전환 시점에 선제적으로 쓰는 게 효율적이다.

## BFS 문제를 풀어보고 Claude Code한테 피드백 받기

백준 1261번(알고스팟) 문제를 직접 풀어본 뒤, Claude Code에게 피드백을 받아본 기록이다.

### 문제와 접근

N×M 미로에서 벽은 이동할 수 없지만 무기로 부술 수 있다. `(0,0)`에서 `(N-1,M-1)`까지
가는 데 필요한 최소 무기(벽을 부수는 횟수) 개수를 구하는 문제다.

먼저 입력 범위부터 따져봤다. N, M이 최대 100이라 전체 셀 수는 최대 10⁴, 웬만한 O(N²)
탐색으로도 여유가 있다. 그리고 미로 값이 0 또는 1뿐이라 `int`로 충분하다는 것도 미리
짚고 들어갔다 — 문제를 풀기 전에 제약 조건부터 훑어보는 습관이 나중에 오버엔지니어링
(예: 불필요하게 `long`을 쓰거나 과도한 최적화를 고민하는 것)을 막아준다.

핵심 판단은 "이게 BFS냐 DFS냐"가 아니라, **가중치가 있는 최단 경로 문제**라는
것이었다. 벽을 부수는 것(비용 1)과 빈 칸으로 이동하는 것(비용 0)이 섞여 있어서,
단순 BFS(모든 간선의 가중치가 1이라고 가정하는 탐색)로는 최소 비용을 보장할 수 없다.
그래서 우선순위 큐를 쓰는 **0-1 BFS류의 다익스트라 변형**으로 접근했다.

```java
private static int bfsService() {
    PriorityQueue<int[]> priorityQueue =
        new PriorityQueue<>(Comparator.comparingInt(value -> value[0]));

    priorityQueue.offer(new int[]{0, 0, 0}); // {비용, row, col}

    while (!priorityQueue.isEmpty()) {
        int[] current = priorityQueue.poll();
        int curCost = current[0], curRow = current[1], curCol = current[2];

        if (curRow == N - 1 && curCol == M - 1) return curCost;

        for (int i = 0; i < 4; i++) {
            int nextRow = curRow + dr[i];
            int nextCol = curCol + dc[i];
            if (nextRow < 0 || nextCol < 0 || nextRow >= N || nextCol >= M) continue;

            int nextCost = curCost + maze[nextRow][nextCol];
            if (nextCost < dist[nextRow][nextCol]) {
                dist[nextRow][nextCol] = nextCost;
                priorityQueue.offer(new int[]{nextCost, nextRow, nextCol});
            }
        }
    }
    return -1;
}
```

우선순위 큐를 쓰면 항상 "지금까지 발견된 것 중 비용이 가장 낮은 경로"부터 꺼내게
되고, `dist` 배열로 이미 더 나은 경로가 기록된 칸은 걸러낸다. 벽(1)과 빈 칸(0)이
섞인 상황에서 이 방식이 단순 BFS보다 확실히 맞는 접근이라는 확신은 있었지만, 머릿속
시뮬레이션만으로는 코드가 실제로 그렇게 동작하는지 완전히 검증하기 어려웠다.

### 왜 AI에게 시뮬레이션을 부탁했나

알고리즘 문제를 풀 때 어려운 지점은 "로직을 설계하는 것"보다 "이 로직이 엣지 케이스에서도
맞는지 손으로 추적하는 것"일 때가 많다. 특히 우선순위 큐처럼 상태가 계속 바뀌는 구조는
머릿속 시뮬레이션의 한계가 금방 온다. Claude Code에게 이 코드를 입력값과 함께 단계별로
시뮬레이션해달라고 요청해서, 큐에 뭐가 들어가고 어떤 순서로 빠지는지, `dist` 배열이
어떻게 갱신되는지를 직접 추적받았다. 이 과정에서 실제로 버그도 하나 잡았다.

### 이 방식이 "그냥 정답 코드 받기"와 다른 이유

Claude Code에게 처음부터 "이 문제 풀어줘"라고 했다면 아마 더 빠르고 정확한 코드를
받았을 것이다. 하지만 그렇게 받은 코드는 내 사고력에 남는 게 없다 — 우선순위 큐를
왜 써야 하는지, 단순 BFS가 왜 이 문제에서는 틀리는지에 대한 판단을 스스로 안 해봤기
때문이다. 반대로 **먼저 스스로 풀고, 그 다음 검증/피드백만 AI에게 맡기는 순서**는
문제를 푸는 능력 자체를 기르는 데 도움이 된다. AI를 학습 도구로 쓸 때 이 순서(직접
풀이 → 검증)가 반대 순서(AI가 먼저 풀이 → 이해 없이 수용)보다 남는 게 많다는 걸
체감한 경험이었다.

토큰 소모에 대한 걱정도 있었는데, 실제로는 적당한 예시 하나로 충분히 버그를 찾고
피드백을 받을 수 있었다 — 전체 테스트 케이스를 다 돌려달라고 할 필요는 없었다.

## 하네스 엔지니어링이란? — AI 에이전트를 '풀어놓지 않고' 쓰는 법

### 왜 이 얘기가 필요한가

AI 에이전트에게 코드를 맡기기 시작하면 금방 부딪히는 질문이 있다: 얘가 내가 원하는 대로
움직이게 하려면 뭘 줘야 하나? 프롬프트를 잘 쓰면 되는 거 아닌가?

경험상 프롬프트만으로는 오래 못 간다. 세션이 바뀌면 맥락이 날아가고, 같은 실수를 반복하고,
"이 정도는 당연히 지키겠지" 싶은 규칙(예: 엔티티에 Setter 쓰지 않기)을 매번 다시 알려줘야
한다. **하네스(Harness)**는 이 문제에 대한 답이다 — 프롬프트 한 번이 아니라, 에이전트가
매번 참조하는 "제어 구조"를 프로젝트에 미리 박아두는 접근.

### 하네스가 하는 일: 제어·감시·개선

여러 참고 자료의 정의를 종합하면 이렇다.

> 하네스는 AI 에이전트를 억누르는 것이 아니라, 안전한 방식으로 작동하도록 설계된 제어 구조 전체를 말한다.

핵심 기능 세 가지:

- **제어**: 허용된 범위 내에서만 행동하게 한다
- **감시**: 동작의 상태와 출력을 실시간으로 기록한다
- **개선**: 오류나 이상 행동을 감지하고 피드백한다

이 세 가지가 왜 필요한지는 반대 상황을 생각하면 명확해진다. 하네스가 없으면 AI는
데이터 유출, 품질 불균형, 책임 소재 불명확 같은 문제를 그대로 안고 간다. 이걸 막는
기술적 장치가 **가드레일**이다 — 설계된 목적 범위 밖의 동작을 통제하는 것. 가드레일이
없으면 할루시네이션이 그대로 실행되어 보안 사고로 이어질 수 있다.

흥미로운 점은, 하네스 엔지니어링이 처음부터 완성된 프레임워크로 등장한 게 아니라는
것이다. 하시코프 창업자 미첼 해시모토도 처음부터 설계한 게 아니라 에이전트가 실수할
때마다 규칙을 하나씩 추가하며 만들었다고 밝혔다. 즉 하네스는 "설계"라기보다
**"에이전트와 협업하며 쌓이는 축적물"**에 가깝다 — 그래서 완벽한 하네스를 처음부터
설계하려고 하기보다, 실수가 나올 때마다 규칙을 추가하는 쪽이 현실적이다.

최근에는 이걸 공식화한 참고 저장소도 나온다. 대표적으로
[harness-100](https://github.com/revfactory/harness-100/tree/main/ko) —
100가지 하네스 구성 예시를 모아둔 레포.

### 세 가지 기본 골격과 각자의 역할

```
project-root/
├── AGENTS.md (또는 CLAUDE.md)   # 지켜야 할 규칙
├── tests/                        # 결과를 즉시 검증하는 피드백 장치
└── docs/                         # 행위 기록
```

이 세 개가 왜 하필 이 조합인지가 중요하다. 각각이 하네스의 "제어·감시·개선" 세 기능에
대응한다.

**1) 지시 문서 (AGENTS.md / CLAUDE.md) — 제어**

좋은 지시 문서의 조건: 목차형으로 구성, 구체적인 규칙 명시, 금지사항 명시, 짧고 명확한
내용. 프로젝트 전체를 문서 하나로 관리하기보다 **폴더·기능 단위로 쪼개는 쪽**을 선호한다
— 이유는 단순하다. 문서 하나에 다 몰아넣으면 에이전트가 매 요청마다 관련 없는 규칙까지
전부 읽어야 하고, 규칙이 늘어날수록 신호 대 잡음비가 떨어진다. 역할별로 나누면 해당
작업에 필요한 규칙만 짧고 정확하게 전달된다 — 아래 "역할 분리" 절이 이 원칙의 실제
적용 사례다.

**2) tests/ — 감시**

테스트 케이스를 넣어두고, 에이전트가 스스로 테스트를 돌려 통과 여부를 확인하며
성공할 때까지 수정하게 한다. 사람이 매번 결과를 검증하지 않아도 "맞았는지 틀렸는지"를
에이전트 스스로 판단할 수 있는 센서 역할이다. 하네스에서 테스트가 필수인 이유는,
사람이 개입하지 않는 루프(에이전트가 스스로 고치고 다시 검증하는 과정)를 가능하게
하는 유일한 장치이기 때문이다 — 테스트가 없으면 매 수정마다 사람이 확인해야 해서
자동화된 개선 루프가 성립하지 않는다.

**3) docs/ (결정 기록, ADR) — 개선**

에이전트가 잘못된 방향을 제안하거나 오류를 냈을 때 그 사실을 기록하고 AGENTS.md에
연결해두면, 같은 실수가 반복되는 걸 막을 수 있다. 이게 바로 "제어·감시·개선" 중
개선에 해당한다 — 한 번 걸린 오류가 규칙으로 승격되는 구조. 이 피드백 루프가 없으면
매 세션마다 같은 실수를 처음부터 다시 겪는다.

### 실전: Claude Code 프로젝트에 적용하기

개념은 좋다 쳐도, 실제로 어떻게 구성하는지가 관건이다. 아래는 Java/Spring 기반
프로젝트를 기준으로 한 예시다.

#### 패키지 구성

```
my-project/
│
├── .claude/                          # Claude Code 전용 설정
```

핵심 진입점은 `CLAUDE.md`고, 나머지는 그걸 보조하는 참조 문서로 배치했다.
`docs/ai/agents/`처럼 역할별로 문서를 쪼갠 이유는 위에서 말한 신호 대 잡음비
문제 때문 — 코드 리뷰를 시킬 때 쿼리 생성 규칙까지 같이 읽힐 필요는 없다.

#### CLAUDE.md — 프로젝트 전체 규칙

```markdown
# 프로젝트 컨텍스트

## 기술 스택
- Java 17, Spring Boot 3.x
- JPA / QueryDSL
- Redis, Kafka, Elasticsearch
- MariaDB

## 아키텍처 원칙
- 레이어 구조: api → domain → infra
- 도메인 레이어는 인프라에 의존하지 않는다
- 엔티티에 @Setter 사용 금지, 비즈니스 메서드로만 상태 변경

## 코딩 컨벤션
- 메서드명은 동사로 시작 (find, create, update, delete)
- Repository는 인터페이스로 정의
- 예외는 GlobalExceptionHandler에서 처리

## 참고 문서
- 아키텍처: docs/ai/architecture.md
- 코딩 컨벤션: docs/ai/coding-convention.md
- 도메인 용어: docs/ai/domain-glossary.md
```

"엔티티에 @Setter 금지" 같은 규칙을 명문화해두는 게 핵심이다. 사람 개발자에게는
암묵지로 통하는 컨벤션이, 에이전트에게는 문서화되지 않으면 존재하지 않는 규칙과
같다.

#### 역할별 에이전트 문서 — "무엇을 체크할지"와 "어떻게 답할지"를 분리

**code-reviewer.md**

```markdown
# 코드 리뷰 에이전트

## 역할
코드 리뷰 시 아래 항목을 순서대로 체크한다

## 체크리스트
1. N+1 문제 발생 여부
2. 트랜잭션 범위가 적절한지
3. 예외 처리가 누락된 곳은 없는지
4. 엔티티에 @Setter가 사용됐는지
5. 인덱스 활용 여부

## 출력 형식
- [위험] 즉시 수정 필요
- [경고] 개선 권장
- [제안] 선택적 개선
```

**query-builder.md**

```markdown
# QueryDSL 쿼리 생성 에이전트

## 역할
QueryDSL 기반 동적 쿼리를 생성한다

## 규칙
- BooleanBuilder 사용
- Fetch Join 시 distinct 적용
- Pagination은 커버링 인덱스 서브쿼리 방식 사용
- 조건이 null이면 where절에서 제외

## 출력 형식
Repository 인터페이스 + Impl 구현체 세트로 생성
```

두 문서 모두 "체크리스트/규칙"과 "출력 형식"을 분리해서 명시한다. 출력 형식까지
고정해두는 이유는, 같은 리뷰 결과라도 매번 다른 형식으로 나오면 사람이 결과를
훑는 비용이 커지기 때문이다 — 하네스는 에이전트의 행동뿐 아니라 **결과물의 일관성**도
통제 대상으로 삼아야 한다.

#### 구성 순서

**1. 설치 및 실행** — `claude init` 같은 명령어는 없다. `claude`를 실행하면 바로
대화가 시작된다.

```bash
npm install -g @anthropic-ai/claude-code
cd my-project
claude
```

**2. CLAUDE.md는 직접 작성** — 자동 생성 기능에 기대지 않는 이유는, 자동 생성된
문서는 프로젝트 고유의 암묵적 컨벤션(왜 Setter를 금지하는지, 왜 레이어를 이렇게
나눴는지)을 담지 못하기 때문이다. 하네스의 가치는 "일반론"이 아니라
"이 프로젝트만의 규칙"에서 나온다.

```bash
touch CLAUDE.md
```

**3. commands 폴더 구성** — `.claude/commands/` 안에 `.md` 파일을 만들면 자동으로
슬래시 커맨드로 등록된다.

```bash
mkdir -p .claude/commands
touch .claude/commands/review.md
touch .claude/commands/test.md
```

```
.claude/commands/review.md  →  /review 로 사용 가능
.claude/commands/test.md    →  /test 로 사용 가능
```

**4. 실제 사용**

```bash
claude
/review OrderService.java
/test MemberService.java
```

### 요약

- 하네스는 "완벽하게 설계하고 시작하는 것"이 아니라 **실수가 나올 때마다 규칙으로
  승격시키는 축적 과정**이다.
- 세 요소(지시 문서·테스트·기록)는 각각 제어·감시·개선이라는 다른 역할을 맡는다 —
  하나라도 빠지면 루프가 끊긴다 (예: 테스트 없이 지시 문서만 있으면 에이전트가
  스스로 검증하지 못한다).
- 문서를 역할별로 쪼개는 이유는 신호 대 잡음비 — 관련 없는 규칙을 매번 읽히지
  않기 위해서다.
- 실제로 하네스를 구성하고 `build a harness for this project`를 실행해보면,
  절반 이상은 하네스를 구성했다고 볼 수 있다.
