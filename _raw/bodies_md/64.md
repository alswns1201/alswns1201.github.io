## ExchangeFilterFunction으로 요청·응답 로그 분리하기

외부 API 연동이 들어간 순간부터 로그 전략은 바뀌어야 한다.  
Controller Filter에서 찍히는 로그만으로는 **외부 API 장애, 지연, 재시도 상황을 절대 파악할 수 없다.**

Spring WebClient를 사용하는 경우,  
외부 API 로그는 **ExchangeFilterFunction 레벨에서 관리하는 것이 사실상 표준** 이다.

이 글에서는

  * 왜 Controller 로그와 외부 API 로그를 분리해야 하는지
  * ExchangeFilterFunction이 정확히 무엇인지
  * 실무에서 사용하는 로그 구성 패턴  
을 정리한다.



## 1\. 왜 Controller 로그만으로는 부족한가

보통 Spring 프로젝트에는 다음과 같은 로그가 있다.

  * 요청 URL
  * HTTP Method
  * 처리 시간
  * 응답 코드



이 로그는 **“우리 API가 호출됐다”**는 사실만 알려준다.

하지만 외부 API 연동이 들어오면 다음 정보가 필요해진다.

  * 외부 API 호출 여부
  * 실제 외부 요청 URL
  * 응답 상태 코드
  * 타임아웃 발생 여부
  * 재시도 횟수
  * 실패 원인 (네트워크 / 5xx / timeout)



이 정보는 **Controller Filter에서는 절대 알 수 없다.**

그래서 외부 API 로그는 **외부 호출 계층(WebClient)에서 따로 관리해야 한다.**

## 2\. ExchangeFilterFunction이란?

ExchangeFilterFunction은 WebClient 요청/응답 흐름에 끼어드는 **Interceptor** 다.

  * 요청 전
  * 응답 후
  * 예외 발생 시



모두 가로챌 수 있다.
    
    
    public interface ExchangeFilterFunction {
        Mono<ClientResponse> filter(ClientRequest request, ExchangeFunction next);
    }

👉 개념적으로는  
**RestTemplate의 ClientHttpRequestInterceptor** 와 같은 역할이다.

* * *

## 3\. WebClient에 로그 필터 적용 구조

실무에서는 WebClient를 Bean으로 등록하면서 필터를 같이 붙인다.
    
    
    @Configuration
    public class WebClientConfig {
    
        @Bean
        public WebClient webClient(WebClient.Builder builder) {
            return builder
                    .filter(logRequest())
                    .filter(logResponse())
                    .build();
        }
    }

이렇게 하면 **해당 WebClient를 사용하는 모든 외부 API 호출에 로그가 자동 적용된다.**

* * *

## 4\. 외부 API 요청 로그 필터

### 요청 시점에 찍어야 할 정보

  * HTTP Method
  * 요청 URL
  * traceId (있다면)


    
    
    private ExchangeFilterFunction logRequest() {
        return ExchangeFilterFunction.ofRequestProcessor(request -> {
            log.info(
                "[External-Request] method={} url={}",
                request.method(),
                request.url()
            );
            return Mono.just(request);
        });
    }

> ❗ 요청 바디(body)는 찍지 않는다  
> 개인정보, 카드 정보, 토큰 유출 위험 때문이다.

* * *

## 5\. 외부 API 응답 로그 필터

### 응답 시점에 찍어야 할 정보

  * HTTP Status
  * 성공/실패 여부


    
    
    private ExchangeFilterFunction logResponse() {
        return ExchangeFilterFunction.ofResponseProcessor(response -> {
            log.info(
                "[External-Response] status={}",
                response.statusCode()
            );
            return Mono.just(response);
        });
    }

이 로그 덕분에:

  * 외부 API가 200을 줬는지
  * 4xx / 5xx인지  
를 바로 확인할 수 있다.



## 6\. 재시도(retry) 로그는 반드시 별도로

외부 API에서 **가장 중요한 운영 지표는 재시도 횟수** 다.
    
    
    .retryWhen(
        Retry.fixedDelay(3, Duration.ofSeconds(1))
            .doBeforeRetry(signal -> 
                log.warn(
                    "[External-Retry] retryCount={} reason={}",
                    signal.totalRetries() + 1,
                    signal.failure().getClass().getSimpleName()
                )
            )
    )

이 로그가 없으면:

  * 외부 API가 느린지
  * 내부에서 재시도를 반복하는지  
운영에서 절대 알 수 없다.



* * *

## 7\. traceId 연동 (중요)

Controller Filter에서 생성한 traceId를  
외부 API 로그에서도 같이 찍어야 **요청 흐름을 추적할 수 있다.**

보통은 MDC를 사용한다.
    
    
    log.info(
        "[External-Request] traceId={} url={}",
        MDC.get("traceId"),
        request.url()
    );

이렇게 하면:

  * 하나의 사용자 요청
  * 하나의 외부 API 호출
  * 재시도 로그  
를 **모두 하나의 traceId로 묶을 수 있다.**



* * *

## 8\. 로그 레벨 전략 (실무 기준)

상황로그 레벨  외부 요청 시작 | INFO  
---|---  
정상 응답 | INFO  
재시도 발생 | WARN  
timeout / 실패 | ERROR  
  
이 기준으로 안 나누면:

  * 로그가 너무 많거나
  * 장애 로그가 묻힌다.



* * *

## 9\. 절대 찍지 말아야 할 것

실무에서 명확한 금지 항목이다.

  * 요청/응답 Body 전체
  * Authorization 헤더
  * 카드번호, 주민번호, 토큰



외부 API 로그는 **“상태 확인용”**이지  
**“데이터 확인용”이 아니다.**

* * *

## 10\. 정리

  * Controller 로그와 외부 API 로그는 목적이 다르다
  * 외부 API 로그는 WebClient 레벨에서 관리한다
  * ExchangeFilterFunction은 외부 연동 로그의 표준적인 해결책이다
  * retry / timeout 로그는 반드시 분리해서 남긴다
  * traceId 연동 없으면 운영에서 의미 없다



* * *

## 한 줄 결론

> **외부 API 로그를 ExchangeFilterFunction으로 분리하지 않으면  
>  장애가 났을 때 “감”으로 디버깅하게 된다.  
> 분리해두면 로그만 보고 원인을 바로 알 수 있다.**
