## Shard Key 선택과 Snowflake ID

대규모 서비스에서는 단순히 AUTO_INCREMENT를 사용한 Primary Key 전략이 한계에 부딪히는 경우가 있습니다.  
특히 **데이터가 여러 DB로 분산되는 Sharding 환경** 에서는 ID 생성 전략과 Shard Key 설계가 매우 중요합니다.

이번 글에서는 아래 대해서 정리하려고 합니다.

  1. 왜 ShardKey를 articleId가 아니라 boardId로 선택했는지 ? 
  2. 왜 AUTO_INCREMENT와 UUID를 사용하지 않았는지 ?
  3. Snowflake 알고리즘이 무엇인지 ?
  4. Snowflake가 분산 시스템에서 왜 유리한지?

이 테이블에서 중요한 컬럼은 두 가지입니다.

  * article_id : Primary Key
  * board_id : Shard Key



# 1.ShardKey를 articleId가 아니라 boardId로 선택했는지 ? 

Sharding에서는 **데이터를 어느 기준으로 분산할지 결정해야 합니다.**

Shard Key 후보는 보통 다음 두 가지 입니다.

article_id  
board_id

여기서 board_id를 선택한 이유는 **데이터 접근 패턴 때문입니다.**  
추후에 게시판을 조회 할경우 사용할 조회의 형태는 아래로 예상 합니다. 

## 1-1 실제 서비스 조회 패턴

게시판 서비스의 대부분 조회는 다음과 같은 형태입니다.

게시판 목록 조회
    
    
    select *
    from article
    where board_id = ?
    order by article_id desc
    limit 20;

즉 대부분의 트래픽이 board_id 기준 조회 됨을 생각해보았습니다.

## 1-2 만약 articleId로 Sharding하면 발생하는 문제

Shard Key를 article_id로 선택하면 데이터는 다음처럼 분산됩니다.
    
    
    Shard1
    article_id 1 ~ 1000
    
    Shard2
    article_id 1001 ~ 2000
    
    Shard3
    article_id 2001 ~ 3000

그래서 조회할때 모든 shard를 조회 -> 결과를 merge 해야한다. 이는 매우 비효율적입니다.

## 1-3 boardId를 Shard Key로 선택하면

데이터가 이렇게 분산된됩니다.
    
    
    Shard1
    board_id 1 ~ 100
    
    Shard2
    board_id 101 ~ 200
    
    Shard3
    board_id 201 ~ 300

이 경우
    
    
    select *
    from article
    where board_id = 10

Shard1 하나만 조회하면 됩니다.

# 2\. AUTO_INCREMENT와 UUID를 사용하지 않았는지 ?

Primary Key 후보를 AUTO_INCREAMENT , UUID , Snowflake 3가지로 생각해봤다. 

**2-1 AUTO_INCREAMENT**

AUTO_INCREMENT는 단일 DB에서는 매우 편리하다. 하지만 분산 환경에서는 각각 DB가 

AUTO_INCREAMENT를 사용하게 된다면. 
    
    
    DB1 → id = 1
    DB2 → id = 1
    DB3 → id = 1

중복이 발생할 우려가 있다. 이를 해결하려면 ID 생성 서버를 구성해야하고, 이 경우엔 또 성능적으로 

병목이 생길 우려가 있습니다.

2-2 UUID를 사용하지 않는 이유 

UUID는 매우 간단하게 고유 ID를 생성할수 있다. 하지만 DB에서는 여러 문제가 있습니다.

예시
    
    
    a8f3...
    19bc...
    7ff1...

\- INDEX 문제 
    
    
     MySQL의 InnoDB 는 B-tree 구조로 저장한다. 그렇기 때문에  AUTO_INCREMENT처럼 항상 뒤에 삽입하는 것이 아닌
    중간 삽입(랜덤삽입)을 시도하여 디스크 I/O 작업에 부담이 된다.

또한, Page Split 문제가 발생합니다.
    
    
    B-Tree 페이지가 가득 찬 상태에서 중간 위치에 새로운 값이 삽입되면
    기존 페이지를 두 개로 분리하는 Page Split이 발생한다.
    이 과정에서 추가적인 디스크 I/O가 발생하며 인덱스 단편화가 증가한다.

# 3\. Snowflake 알고리즘이 무엇인지 ?

Snowflake는 **시간 기반 증가 값** 입니다.
    
    
    190234234234
    190234234235
    190234234236

그래서 AUTO_INCERMENT와 동일하게 INSERT는 항상 맨 뒤에 적재 됩니다. 따라서 PAGE SPLIT 도 거의 없습니다.

구조 
    
    
    timestamp + nodeId + sequence

snowflake 의 흐름
    
    
    현재 시간 확인
    ↓
    같은 ms면 sequence 증가
    ↓
    sequence overflow → 다음 ms 대기
    ↓
    timestamp + nodeId + sequence 합치기

또한 자바에서는 만들어진 라이브러리를 사용 할수도 있습니다. 하지만 실무에서는 nodeId 값도 중요하기 떄문에

간단하게 회사 자체에서 만들어진 로직으로 구현 됩니다.
