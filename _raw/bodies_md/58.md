JWT 기반 인증 구조를 이야기하면 꼭 나오는 질문이 있다.

> “Access Token을 쿠키에 넣을까? 아니면 Header로 보낼까?  
> Refresh Token은 왜 보통 쿠키에 넣는 걸까?”

이 질문에 답하려면 **CSRF** 를 정확히 이해해야 한다. 특히 “왜 쿠키가 문제가 되는가”를 명확하게 보는 게 포인트다.

* * *

## 1\. CSRF: 공격자가 ‘내 로그인 상태’를 악용하는 공격

CSRF(Cross-Site Request Forgery)의 본질은 아주 간단하다.

> “로그인된 사용자의 브라우저가, 공격자가 만든 요청을 내 서버로 보내버리는 것.”

사용자가 어떤 서비스에 로그인하면 브라우저는 해당 도메인의 모든 요청에 자동으로 쿠키를 붙인다. 이 자동 전송이 CSRF를 가능하게 만드는 핵심이다.

즉, **다른 사이트에서 api.myapp.com으로 요청 보내서 악의적으로 공격하는 행위.**

**그렇기 때문에 samSite 적용을 해놓아도 다른 사이트에서 해당 도메인에 대해 쿠키는 같은 domain 요청으로 적용되어 악의적으로 api 가 호출된다.**

### ✔️ 시나리오로 보면 바로 이해된다

  1. 사용자는 나의 서비스에 로그인 → 쿠키 저장됨
  2. 사용자가 악성 사이트(evil.com) 방문
  3. 해당 사이트에 숨겨진 코드:


    
    
    <form action="https://my-service.com/api/transfer" method="POST">
      <input type="hidden" name="to" value="attacker">
      <input type="hidden" name="amount" value="1000000">
    </form>
    <script>document.forms[0].submit();</script>

  1. 브라우저는 “my-service.com으로 가는 요청이네?” 하고 **자동으로 쿠키 삽입**
  2. 서버는 “로그인 상태네”라고 판단하고 실행



공격자는 쿠키 값을 모른다. 심지어 보고 싶어도 못 본다.  
하지만 **자동으로 보내진다는 사실** 이 문제다.

* * *

## 2\. Access Token을 쿠키에 넣으면 안 되는 이유

Access Token이 쿠키에 들어가는 순간 CSRF 타깃이 된다.

쿠키는 자동으로 전송되기 때문에 사용자가 원치 않아도 API가 실행될 수 있다.  
즉, Access Token이 쿠키에 있다면:

### ❌ 공격 가능한 시나리오

  * 게시글 삭제
  * 사용자 정보 수정
  * 결제 API 호출
  * 파일 삭제
  * 계정 탈퇴



이 API들은 Access Token만 있으면 호출할 수 있으므로, CSRF 위협에 바로 노출된다.

* * *

## 3\. Access Token은 Header에 넣는 이유

Header는 브라우저가 자동으로 붙이지 않는다.

즉, 악성 사이트에서는:

  * fetch()로 요청을 보내도
  * 임의로 Authorization 헤더를 설정할 수 없다 (CORS 정책이 막음)
  * <form> POST로도 불가능
  * <img>, <script>, <iframe> 같은 태그로도 불가능



공격자가 절대 Access Token을 **요청에 실어 보낼 수 없다.**

그래서 Access Token은 **반드시 Header에 넣어야 한다.**

Authorization: Bearer <access_token>

이렇게 되면 CSRF는 구조적으로 원천 차단된다.

* * *

## 4\. 그럼 Refresh Token은 왜 쿠키에 넣지?

계속 묻는 질문이 있다.

> “Refresh Token도 쿠키에 넣으면 F12에서 보이는데… 그럼 탈취 위험 커지는 거 아닌가?”

여기서 핵심은 오해가 있다.

### ❗ Refresh Token은 쿠키에 넣는 게 더 안전하다

왜냐하면 Refresh Token은 **자바스크립트에서 접근하지 못해야** 하기 때문이다.  
그래서 httpOnly 쿠키를 사용한다.

### ✔️ httpOnly + Secure + SameSite 로 보호

  * **httpOnly** → JS에서 절대 못 읽음
  * **Secure** → HTTPS 요청에서만 전송
  * **SameSite=Lax/Strict** → 기본적으로 CSRF 공격에서 자동 쿠키 전송 자체가 막힘



즉, refresh 쿠키는 안전하게 보호된 쿠키가 전제다.

그리고 Refresh Token은 **사용 빈도가 매우 낮고** ,  
사용하더라도 보통 Access Token 재발급 API 하나뿐이다.

이 API는 기본적으로:

  * POST 방식
  * CSRF 토큰 검증 or Double Submit Cookie
  * SameSite=Lax/Strict 적용



위와 같은 보호조치를 통해 안전하게 만들 수 있다.

* * *

## 5\. 최종 결론: 구조적으로 이렇게 나뉘는 게 최선

정리하면 이렇다.

토큰 종류저장 위치이유  **Access Token** | **Header** | 자동 전송 방지 → CSRF 예방, 사용 빈도 높음, JS가 읽어야 함  
---|---|---  
**Refresh Token** | **httpOnly 쿠키** | JS 접근 금지 → 탈취 방지, 사용 빈도 낮음, 재발급 시 보안 절차 수월  
  
* * *

# 🔚 마무리

Access Token과 Refresh Token을 어디에 넣을지 논쟁은 많지만,  
결국 중요한 것은 “**쿠키는 자동으로 붙고, Header는 자동으로 안 붙는다** ”  
이 차이가 CSRF 위협을 완전히 갈라놓는다.

그래서 대부분의 실서비스는 다음 구조로 간다:

  * Access Token → Header
  * Refresh Token → httpOnly 쿠키
  * Access 만료 → Refresh로 재발급
  * Refresh 만료 → 재로그인



이 구조가 보안/실용/개발 편의성 모두에서 가장 균형이 좋기 때문이다.
