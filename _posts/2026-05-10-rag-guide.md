RAG의 개념부터 벡터 DB, 청킹·하이브리드 서치·리랭커까지 한 글에 모았다.
아래 3개 글을 원문 그대로 섹션으로 묶었다.

1. RAG란 무엇인가 — 그리고 언제 도움이 안 되는가
2. 벡터 DB는 왜 필요한가 — ChromaDB로 보는 임베딩 검색의 실체
3. RAG 실전: 청킹 전략, 하이브리드 서치, 그리고 Reranker

## RAG란 무엇인가 — 그리고 언제 도움이 안 되는가

### RAG가 푸는 문제

RAG(Retrieval-Augmented Generation)는 LLM의 두 가지 약점을 겨냥한다.

- **지식 컷오프**: 학습 시점 이후 정보를 모른다.
- **환각(Hallucination)**: 모르는 걸 모른다고 하지 않고 그럴듯하게 지어낸다.

해법은 단순하다 — 답변을 생성하기 전에 관련 자료를 먼저 검색해서 그걸 근거로
답하게 만드는 것. "모델을 다시 학습시키지 않고도 최신/사내 지식을 반영할 수 있다"는
게 RAG가 fine-tuning보다 먼저 시도되는 이유다.

### 4단계 파이프라인

1. **질문을 벡터로 변환** — 임베딩 모델이 질문을 고차원 숫자 벡터로 바꾼다. 의미가
   비슷한 문장은 벡터 공간에서 가까이 위치한다.
2. **벡터DB에서 유사 문서 검색** — Pinecone, Chroma 같은 벡터 DB에서 코사인 유사도
   등으로 가장 가까운 문서를 찾는다.
3. **검색 결과 + 질문을 LLM에 전달** — 찾아온 문서를 컨텍스트로 붙여서 넘긴다.
4. **근거 기반 답변 생성** — LLM이 제공된 문서를 근거로 답한다.

여기까지가 RAG를 소개하는 대부분의 글이 멈추는 지점이다. 그런데 실제로 RAG를 붙여봐도
여전히 틀린 답이 나오는 경우가 많다 — 문제는 대개 이 4단계 중 **1단계와 2단계**,
즉 "얼마나 잘 찾아오는가"에 있다.

### RAG가 실패하는 지점: 검색 품질

RAG의 답변 품질은 생성(Generation) 단계가 아니라 검색(Retrieval) 단계에서 대부분
결정된다. LLM은 준 자료를 근거로 답할 뿐이라, **틀린 자료를 주면 그럴듯하게 틀린
답을 만든다** — 이건 여전히 환각이지만, 이번엔 모델이 아니라 검색이 원인이다.

검색 품질을 떨어뜨리는 대표적인 원인들:

- **청킹(chunking) 전략**: 문서를 얼마나 크게, 어디서 자르느냐가 검색 정확도를
  좌우한다. 문단을 기계적으로 500자 단위로 자르면 하나의 완결된 개념이 두 청크로
  쪼개져서, 질문과 관련된 청크가 검색되어도 맥락이 잘려 나간 상태로 LLM에 전달된다.
  표나 코드 블록처럼 구조가 있는 콘텐츠는 특히 취약하다.
- **임베딩 모델과 도메인의 불일치**: 범용 임베딩 모델은 일반적인 의미 유사도는
  잘 잡지만, 법률·의료처럼 전문 용어가 밀집된 도메인에서는 "의미상 가까운 문서"와
  "실제로 관련 있는 문서"가 어긋나기 시작한다.
- **벡터 유사도만으로는 부족한 경우**: 벡터 검색(semantic search)은 "의미가 비슷한
  텍스트"를 찾는 데 강하지만, 정확한 키워드/코드/제품명 매칭에는 약하다. 그래서
  실무에서는 벡터 검색과 키워드 기반 검색(BM25 등)을 함께 쓰는 **하이브리드 검색**이
  자주 쓰인다 — 벡터 검색이 놓치는 정확 매칭을 키워드 검색이 보완한다.
- **검색 결과 개수(top-k)의 트레이드오프**: k를 늘리면 정답이 포함될 확률(재현율)은
  올라가지만, 관련 없는 문서가 컨텍스트에 섞여 들어가 LLM이 오히려 헷갈릴 수 있다.
  k를 줄이면 반대 문제가 생긴다. 이 값은 도메인마다 실험으로 맞춰야 하는 값이지,
  고정된 정답이 없다.

### RAG가 애초에 안 맞는 경우

RAG는 "지식이 없어서 틀리는" 문제에는 강하지만, "추론이 필요해서 틀리는" 문제에는
크게 도움이 안 된다. 예를 들어 여러 문서에 흩어진 정보를 종합해서 계산하거나
추론해야 하는 질문(예: "이 세 분기 보고서를 비교해서 성장률 추세를 설명해줘")은
단순 검색-삽입으로는 잘 안 풀린다 — 관련 청크를 다 찾아왔다고 해도, 그걸 종합하는
건 여전히 LLM의 추론 능력에 달려 있고 RAG는 그 능력 자체를 개선해주지 않는다.
이런 경우엔 검색 전략을 더 정교하게(multi-hop retrieval, 질문 분해) 가져가거나,
애초에 RAG보다 긴 컨텍스트 윈도우에 문서 전체를 넣는 게 나을 수도 있다.

### 데이터 인입(Ingestion)이 실제로 가장 중요한 이유

```
PDF/문서 → 파싱 → 구조화된 데이터(JSON/DTO) → Vector DB 저장
```

파싱 단계에서 표, 이미지 캡션, 문서 구조(제목/본문 구분)가 깨지면, 이후 단계가 아무리
정교해도 복구가 안 된다. RAG 품질 문제를 디버깅할 때 실제로 가장 먼저 봐야 할 곳은
프롬프트나 임베딩 모델이 아니라 **이 인입 단계에서 원문이 얼마나 온전하게 살아남았는가**다.

### 실전 스택

- **LangChain / LlamaIndex** — RAG 파이프라인 오케스트레이션, 문서 인덱싱
- **Pinecone** — 관리형 벡터 DB
- **Chroma** — 오픈소스 로컬 벡터 DB

실무에서는 LangChain(또는 LlamaIndex) + FastAPI + 벡터DB 조합이 백엔드 AI 서비스의
표준 스택으로 자리 잡았다.

### 정리

- RAG = 검색으로 근거를 확보한 뒤 그걸 바탕으로 생성 → 지식 컷오프와 환각을 줄이는 접근.
- 답변 품질은 생성이 아니라 **검색 품질**(청킹, 임베딩 모델, 하이브리드 검색, top-k)에
  좌우된다.
- 여러 자료를 종합하는 **추론이 필요한 질문**에는 RAG만으로 부족하다 — 검색 전략을
  더 정교하게 가져가거나 다른 접근을 검토해야 한다.
- 디버깅 우선순위: 프롬프트보다 먼저 **데이터 인입/청킹 품질**을 의심할 것.

## 벡터 DB는 왜 필요한가 — ChromaDB로 보는 임베딩 검색의 실체

*(RAG의 전체 흐름과 검색 품질 문제는 앞의 "RAG란 무엇인가" 섹션에서
다뤘다. 여기서는 그 파이프라인의 한 조각인 **벡터 DB**가 정확히 뭘 하는 물건인지를 판다.)*

### "그냥 DB에 벡터 컬럼 하나 추가하면 안 되나?"

이 질문에 답하려면 벡터 검색이 실제로 어떤 연산인지 봐야 한다. 임베딩 모델은 텍스트를
고차원 숫자 벡터로 바꾸고, 의미가 비슷한 텍스트는 벡터 공간에서 가까운 위치에 놓인다.
질문이 들어오면 그 질문도 벡터로 바꾼 뒤, 저장된 모든 벡터와의 거리(코사인 유사도
등)를 계산해서 가장 가까운 것을 찾는다.

문제는 "모든 벡터와 거리를 계산"하는 부분이다. 문서가 수천 개면 이 브루트포스
계산도 감당할 만하지만, 수백만 개가 되면 질문 하나마다 수백만 번의 거리 계산이
필요해진다 — 일반 RDB에 벡터를 blob이나 배열 컬럼으로 넣고 애플리케이션 레벨에서
전수 비교하면 이 비용을 고스란히 떠안는다. 벡터 DB가 실제로 하는 일은 이 전수
비교를 피하기 위한 **근사 최근접 이웃(ANN, Approximate Nearest Neighbor) 인덱스**를
구축하고 관리하는 것이다 — HNSW(계층적 그래프 탐색) 같은 자료구조로, 정확도를 아주
약간 희생하는 대신 검색 속도를 몇 자릿수 끌어올린다. "벡터를 저장하는 DB"가 아니라
"벡터를 빠르게 찾기 위한 인덱스를 관리하는 DB"라고 이해하는 게 더 정확하다.

### ChromaDB가 하는 일

ChromaDB는 이 역할을 하는 오픈소스 경량 벡터 DB다. 컬렉션(collection) 단위로
데이터를 격리해서 관리하고, 각 항목에 문서(document), 임베딩(embedding),
메타데이터(metadata)를 함께 저장한다.

```
질문 → 임베딩 변환 → 벡터 DB에서 유사 문서 검색 → LLM에 context로 전달 → 답변 생성
```

로컬에서도 가볍게 띄울 수 있고 임베딩 자동 생성 기능도 있어서, RAG 프로토타입
단계에서 특히 많이 쓰인다.

### Java에서 호출하기 (v2 REST API)

ChromaDB는 공식 Java SDK보다 REST API 기반 호출이 일반적이다.

```java
public class ChromaCollectionManager {
    private final String baseUrl = "http://localhost:8000/api/v2";
    private final RestTemplate restTemplate = new RestTemplate();

    public void createCollection(String collectionName) {
        Map<String, String> request = new HashMap<>();
        request.put("name", collectionName);
        request.put("get_or_create", "true");
        restTemplate.postForEntity(baseUrl + "/collections", request, String.class);
    }

    public void addDocument(String collectionId, String id, List<Double> embedding, String document) {
        Map<String, Object> request = new HashMap<>();
        request.put("ids", Collections.singletonList(id));
        request.put("embeddings", Collections.singletonList(embedding));
        request.put("documents", Collections.singletonList(document));
        restTemplate.postForEntity(baseUrl + "/collections/" + collectionId + "/add", request, String.class);
    }

    public String queryVector(String collectionId, List<Double> queryEmbedding, int nResults) {
        Map<String, Object> request = new HashMap<>();
        request.put("query_embeddings", Collections.singletonList(queryEmbedding));
        request.put("n_results", nResults);
        return restTemplate.postForObject(baseUrl + "/collections/" + collectionId + "/query", request, String.class);
    }
}
```

데이터 흐름은 단순하다: 컬렉션 생성 → 임베딩 모델로 벡터 생성 → ChromaDB에 POST →
쿼리 시 결과에서 문서와 거리(distance) 값을 추출. v2 API는 배치(batch) 처리에서
성능 이점이 있다.

### 메타데이터 필터링에서 흔히 놓치는 함정

ChromaDB는 벡터 유사도뿐 아니라 메타데이터로도 필터링할 수 있다(예: `category: "법률"`인
문서만 검색). 여기서 필터를 **언제** 적용하느냐가 결과 품질을 크게 좌우한다.

- **사후 필터링(post-filter)**: 일단 유사도 top-k를 뽑은 뒤 메타데이터 조건에
  안 맞는 것을 걸러낸다. 문제는, top-k 안에 조건에 맞는 문서가 하나도 없으면
  필터링 후 결과가 텅 비거나 k보다 훨씬 적어질 수 있다는 것이다.
- **사전 필터링(pre-filter)**: 메타데이터 조건을 먼저 적용한 부분집합 안에서만
  유사도 검색을 한다. 결과 개수는 보장되지만, 인덱스 구조에 따라 이게 항상
  효율적으로 지원되는 건 아니다.

"검색 결과가 이상하게 적게 나온다"는 문제를 겪으면, 사후 필터링 때문에 top-k에서
필터에 걸러진 게 아닌지부터 의심해봐야 한다 — 벡터 DB를 프로덕션에 붙일 때 실제로
가장 자주 만나는 버그 패턴 중 하나다.

### 언제 벡터 DB가 과한 선택인가

문서가 수백~수천 건 수준이고 검색어가 대체로 정확한 키워드 매칭으로 충분하다면,
벡터 DB와 임베딩 파이프라인을 새로 구축하는 비용이 오히려 배보다 배꼽이 클 수
있다. 전문 검색(full-text search) 엔진(Elasticsearch, PostgreSQL의 `tsvector` 등)의
기본 기능만으로 충분한 경우가 많다. 벡터 DB가 진짜 값을 하는 지점은, 정확한
키워드가 아니라 **의미**로 찾아야 하고 코퍼스가 커서 브루트포스 비교가 부담스러운
경우다.

### 프로토타입과 프로덕션의 간극

ChromaDB(특히 임베디드/로컬 모드)는 설치 없이 바로 실험하기 좋지만, 다중 인스턴스
클러스터링이나 복제 같은 프로덕션급 가용성 기능은 Pinecone, Qdrant, Weaviate 같은
관리형/분산 벡터 DB에 비해 약하다. 로컬 프로토타입에서 검증한 로직을 그대로
프로덕션 트래픽에 노출하기 전에, 가용성과 확장성 요구사항에 맞는 벡터 DB로
옮겨야 하는지를 별도로 검토해야 한다.

### 정리

- 벡터 DB의 본질은 "벡터 저장소"가 아니라 **ANN 인덱스로 유사도 검색을 빠르게
  만드는 인프라**다.
- ChromaDB는 컬렉션 단위로 document+embedding+metadata를 함께 관리하는 경량
  구현체다.
- 메타데이터 필터를 언제(사전/사후) 적용하는지가 결과 개수와 품질에 직접 영향을
  준다.
- 코퍼스가 작고 키워드 매칭으로 충분하면 벡터 DB는 과한 선택일 수 있다.

## RAG 실전: 청킹 전략, 하이브리드 서치, 그리고 Reranker

RAG의 개념(질문 → 검색 → 답변)과 검색 품질이 왜 중요한지는 [RAG란 무엇인가]({{ '/posts/rag-basics/' | relative_url }})에서
다뤘다. 여기서는 그 검색 품질을 실제로 어떻게 끌어올리는지 — 청킹, 하이브리드 서치,
Reranker — 세 가지 실전 기법을 정리한다.

### 임베딩: 의미를 벡터로 압축한다

임베딩은 텍스트의 의미를 숫자 벡터로 표현하는 방법이다. 의미가 비슷한 문장일수록
벡터 공간에서 가까운 위치에 놓인다("강아지"와 "개"는 가깝고 "강아지"와 "자동차"는 멀다).

```
텍스트 → 임베딩 모델 → 벡터 배열 [0.12, -0.34, 0.78, ...]
```

차원이 높을수록 의미를 세밀하게 표현할 수 있지만 처리 속도는 느려진다 — 무조건 고차원
모델을 쓰는 게 정답이 아니라, 검색 정확도와 지연시간 사이에서 용도에 맞는 차원을
고르는 문제다.

### 청킹(Chunking): RAG 품질을 가장 많이 좌우하는 단계

문서를 통째로 임베딩하지 않고 잘게 나누는 과정이 청킹이다. 청킹 전에는 반드시
Parser로 문서를 먼저 읽어야 하는데, 표나 이미지 캡션이 섞인 문서일수록 이 파싱
품질이 이후 모든 단계의 상한선이 된다 — 파싱이 깨지면 청킹도, 검색도 다 같이 무너진다.

| 방식 | 설명 |
|---|---|
| 길이 기반 청킹 | 글자 수/토큰 수로 일정하게 자름 |
| 의미 기반 청킹 | 문단, 문장 등 의미 단위로 자름 |

길이 기반은 구현이 간단하지만 문장 중간에서 잘릴 수 있다는 게 문제다. 의미 기반은
정보 손실이 적지만 "어디가 의미 단위의 경계인가"를 판단하는 비용이 든다. 정답은
콘텐츠 성격에 달려 있다 — 표/코드처럼 구조가 뚜렷한 문서는 의미 기반이 유리하고,
자유 형식 텍스트는 길이 기반으로도 충분한 경우가 많다.

### 전체 파이프라인

```
[사전 작업] 문서 → 파싱 → 청킹 → 임베딩 → 벡터 DB 저장
[실시간]   질문 → 임베딩 변환 → 벡터 DB에서 유사 청크 검색 → LLM 컨텍스트로 전달 → 답변 생성
```

### 디버깅은 생성이 아니라 검색을 봐야 한다

> 문제는 생성(Generation)이 아니라 검색(Retrieval)이다.

청크 품질이 낮으면 아무리 좋은 LLM을 붙여도 답변 품질은 떨어진다. 실전에서 쓰는
디버깅 방법은 단순하다 — 실제로 들어올 법한 질문 5~10개를 직접 골라서, 벡터 검색
결과를 눈으로 직접 확인하며 청크 품질을 점검한다("시멘틱 서치 디버깅"). 프롬프트를
먼저 손대기 전에 이 단계부터 봐야 한다.

### 하이브리드 서치: Dense + Sparse

시멘틱 서치(벡터 검색)만으로는 안 되는 경우가 있다 — 제품 코드, 고유 명사, 특수
용어처럼 **정확한 키워드 일치**가 중요한 질의다.

| 방식 | 원리 | 강점 |
|---|---|---|
| Dense 임베딩 | 의미 기반 유사도 검색 | 문맥 이해, 동의어 처리 |
| Sparse 임베딩 (BM25 등) | 키워드 기반 검색 | 정확한 단어 일치, 고유명사 |
| Hybrid Search | 둘을 결합 | 의미 + 키워드 동시 커버 |

둘 중 하나만 쓰면 상호 보완이 안 된다 — Dense만 쓰면 "정확히 이 제품 코드"를 찾아야
하는 질의에서 엉뚱한 결과가 섞이고, Sparse만 쓰면 동의어나 문맥적 유사어를 놓친다.

### Reranker: 빠른 검색 뒤에 정밀한 재평가

하이브리드 서치로 후보 청크를 뽑은 뒤, Reranker가 그 후보들을 다시 정밀하게
재평가하고 순위를 재정렬한다.

- 벡터 검색은 빠르지만 다소 거칠다 (대규모 후보군에서 대략적인 후보를 빠르게 추림)
- Reranker는 느리지만 정확하다 (소수 후보를 놓고 정밀 비교)

그래서 보통 **벡터 검색(후보 20~50개) → Reranker → 최종 3~5개 → LLM** 순서로 쓴다.
이 2단계 구조 자체가 트레이드오프의 산물이다 — 처음부터 모든 문서에 Reranker급 정밀
비교를 돌리면 느려서 못 쓰고, 벡터 검색만으로 끝내면 최종 결과의 정밀도가 아쉽다.
빠른 1차 필터링과 느리지만 정확한 2차 정제를 나눠서 각자의 장점만 취하는 구조다.

### 정리

- 청킹 전략(길이 기반 vs 의미 기반)은 콘텐츠 구조에 맞춰 고른다 — 하나가 항상
  우월하지 않다.
- 검색 품질이 안 나올 때는 프롬프트가 아니라 **청크를 직접 눈으로 확인**하는 게
  먼저다.
- 정확한 키워드 매칭이 중요한 도메인이라면 벡터 검색만으로는 부족하고 하이브리드
  서치가 필요하다.
- Reranker는 "빠른 대량 후보 추림 + 느리지만 정확한 소수 정제"라는 2단계 구조로
  속도와 정확도를 동시에 잡는 장치다.
