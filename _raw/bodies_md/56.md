비동기 작업을 @Async로 돌리다 보면 한 번쯤은 겪어봤을 것이다.

> “비동기는 ControllerAdvice 를 통해서 예외 처리가 적용 되지 않는다.”

이게 정상이다.  
비동기 메서드는 별도 스레드에서 실행되기 때문에 일반적인 예외 처리 흐름(@ControllerAdvice, try-catch, filter chain)과는 단절된다. 그래서 별도 예외 처리 전략이 필요하고, 그 핵심이 바로 **AsyncUncaughtExceptionHandler** 다.

오늘은 이걸 실무에서 어떻게 쓰는지, 어떻게 구조화하면 좋은지, 내가 직접 프로젝트에서 겪은 기준으로 정리해본다.

* * *

## 💥 왜 비동기 예외는 기본 로그에 안 잡힐까?

@Async 메서드는 스프링이 만든 **TaskExecutor 스레드풀** 에서 실행된다.  
컨트롤러나 서비스 호출 스레드와 완전히 분리되어 있기 때문에 다음이 발생한다.

  * ControllerAdvice로 예외가 전달되지 않음
  * 부모 스레드의 try-catch에 영향 없음
  * AOP 예외 로깅 로직에도 안 걸릴 수 있음
  * 그냥 조용히 잡아먹힘



그래서 의도적으로 “비동기 전용 예외 처리기”를 등록해줘야 한다.

* * *

# ⭐ 해결책: AsyncUncaughtExceptionHandler

스프링이 기본적으로 지원하는 인터페이스고, 딱 “void 리턴 타입 비동기 함수에서 발생하는 예외”를 잡아준다.

구조는 간단하다.

  * void 메서드 비동기 예외 처리 → AsyncUncaughtExceptionHandler
  * CompletableFuture 반환하는 비동기 예외 → .exceptionally, .handle 등 Future 기반 처리



여기서는 **핵심인 void 기반 비동기 로직 처리** 기준으로 설명한다.

* * *

## 🧩 1. 비동기 예외 처리기 구현
    
    
    @Slf4j
    public class CustomAsyncExceptionHandler implements AsyncUncaughtExceptionHandler {
    
        @Override
        public void handleUncaughtException(Throwable ex, Method method, Object... params) {
            log.error("[Async Exception] method={} params={}", method.getName(), params, ex);
        }
    }

이 핸들러는 비동기 메서드에서 터진 예외를 싹 다 모아준다.  
여기서 원하는 대로:

  * 로그 남기고
  * Slack/Webhook 알림 보내고
  * APM 커스텀 에러 전송하고
  * DB에 쌓아도 되고



진짜 그냥 “모아주는 곳”이라고 생각하면 된다.

* * *

## 🧩 2. 스프링에 등록
    
    
    @Configuration
    @EnableAsync
    public class AsyncConfig implements AsyncConfigurer {
    
        @Override
        public Executor getAsyncExecutor() {
            ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
            executor.setCorePoolSize(5);
            executor.setMaxPoolSize(10);
            executor.setQueueCapacity(50);
            executor.setThreadNamePrefix("async-exec-");
            executor.initialize();
            return executor;
        }
    
        @Override
        public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
            return new CustomAsyncExceptionHandler();
        }
    }

여기서 중요한 건 **getAsyncUncaughtExceptionHandler()**.

이걸 등록해야 비동기 예외가 몽땅 이리로 떨어진다.

* * *

## 🧩 3. 테스트용 비동기 코드
    
    
    @Service
    public class AsyncTestService {
    
        @Async
        public void runAsyncJob() {
            throw new RuntimeException("비동기에서 일부러 터뜨린 예외!");
        }
    }

그리고 실행하면:
    
    
    @Service
    public class AsyncTestService {
    
        @Async
        public void runAsyncJob() {
            throw new RuntimeException("비동기에서 일부러 터뜨린 예외!");
        }
    }

딱 이렇게 핸들러로 모인다.

* * *

# 🧨 그럼 try-catch는? 로그만 찍고 return 해도 되는가?

  * @Async 메서드 안에서 try-catch로 잡으면 예외는 당연히 전파되지 않는다.
  * 즉, 직접 핸들링하고 끝내버리면 AsyncUncaughtExceptionHandler까지 오지 않는다.
  * 그래서 **비동기 내부 로직을 try-catch로 감싸면 핸들러는 무력화된다.**



정리하면:

상황예외 흐름  try-catch 있음 | 내부에서 처리 끝 → 핸들러로 안 감  
---|---  
try-catch 없음 | AsyncUncaughtExceptionHandler가 처리함  
  
실무에서는 이렇게 한다:

  * “진짜 복구 가능한 예외”는 try-catch로 잡고
  * “예상치 못한 예외”는 일부러 던져서 핸들러에서 통합 처리



* * *

# 🙋 그럼 ‘비동기 전체 예외를 하나로 모을 수 있는가?’

가능하다.  
AsyncUncaughtExceptionHandler는 **void-return 비동기 함수 전체에 대해 글로벌하게 동작** 한다.

즉,

  * 해당 비동기 함수 내부에서 호출되는 모든 private/public 함수
  * 비동기 흐름 안의 예외



전부 여기로 떨어진다.

내 경험 기준으로는, 비동기 흐름 중 어느 단계에서 터져도 100% 잡혔다.

* * *

# 📌 실무 팁 (중요)

### ✔ 1) 비동기 로직은 가급적 "예측 가능한 예외"만 try-catch

오히려 try-catch를 남발하면 에러 추적 난이도만 올라간다.

### ✔ 2) 비동기 처리기에서는 비즈니스 처리 절대 하지 말 것

여긴 로깅, 알림, 모니터링만.

### ✔ 3) 중요한 비동기 로직은 CompletableFuture 기반 설계 추천

void 기반은 위험할 때가 많고, Future 기반은 예외 제어가 더 정교함.

* * *

# 📄 마무리

비동기 예외는 기본 흐름에서 완전히 분리되어 있기 때문에,  
Spring Boot가 제공하는 AsyncUncaughtExceptionHandler로 별도 예외 흐름을 만들어줘야 한다.

이걸 적용하면:

  * 비동기 예외가 사라지지 않고
  * 전체 로깅 체계로 흘러가고
  * 알림이나 모니터링이 가능해지고
  * 디버깅 난이도가 확 떨어진다



실무에서 비동기 처리 쪽 문제 잡을 때 진짜 체감되는 효과가 있다.
